# Changelog

## [Unreleased]

### Added

- **ADR-003 fixes the model-routing contract before any of its code.** Four strategies and their weight table, the catalog unit `role + harness + model + effort`, the overlay layers and their precedence, the four availability states with their reason codes and TTLs, the resolver rules and tie-break, and the rule that no task, worktree or participant is written before a candidate exists. The routing decision lives in participant `metadata`, so the protocol version does not move. Nine tasks build on it; the contract is fixed once instead of re-derived nine times (PB-11).
- **Model-routing contracts land before the resolver.** Four JSON schemas under `schemas/model-routing/` — catalog, overlay, availability snapshot and the `models --json` decision — with the CLI surface, the reason codes, the exclusion, adjustment and warning codes, and the error codes written once into the CLI reference. Golden fixtures pin an input pair (catalog, snapshot) and its output pair (decision JSON, `models` text), compared under the normalisation their README states, so the nine tasks that follow implement against fixed shapes instead of inventing them. A check pins that argv with none of the new flags takes today's path exactly, and the golden comparisons that need a command nobody has written yet are marked pending rather than red (PB-12).
- **Routing can ask what the account can actually run.** An availability adapter is one method a driver declares (`probe({ host, timeoutMs, refresh })` → a verdict with state, reason, message, `checkedAt`, source and, when the harness gives them, a reset time, a model inventory and limit windows); the preflight runs every adapter at once under one 15 s budget and hands back the availability snapshot, so a harness that never answers is `probe_timeout` instead of a command that hangs; and the cache keeps that snapshot at the file the host names, mode `0600`, written whole, with a TTL per entry — an hour for auth and inventory, a minute for limit windows, five minutes for a failed probe, a confirmed exhaustion until its reset, and one with no reset until `--clear-exhausted` lifts it. A verdict is projected field by field onto the closed snapshot shape before it is written, so a token an adapter attached beside the contract — or threw inside an error — never reaches disk. A driver with no adapter answers `unknown` / `probe_failed`, which the resolver penalises rather than blocks, so the three real adapters can land one at a time (PB-14).
- **The package ships a model catalog, and overlays sit above it.** `models/catalog.json` holds the first rated matrix — nineteen `role + harness + model + effort` tuples across the three harnesses, each with a source and evidence a later maintainer can check; a model the harness exposes and nobody could rate from a named source gets no row and stays a runtime `unrated` line. `loadCatalog()` merges the shipped catalog with every overlay the host names, lowest precedence first, then the caller's constraints: a weight set is replaced whole, an allow or deny list whole per selector kind, everything else field by field, and a missing overlay file is normal. `validate()` is the library behind `models validate` — layer shapes, duplicate ids, harnesses and efforts checked against the drivers' own dictionaries, weight sums, references and contradictory allow/deny as errors; stale ratings and the canonical-priority convention as warnings that never stop a run. Production reads no JSON Schema: the grammar is written out and a parity check keeps it one grammar with `schemas/model-routing/`. Every finding names the layer that wrote the key it is about, and a warning carries `code` and `message` — the two fields a decision document may hold — so nothing downstream translates. Cursor carries effort inside the model id and nothing validates one before liftoff, so each Cursor row is pinned against a captured `cursor-agent models` listing. The overlay a person copies is in [guides/model-routing.md](docs/guides/model-routing.md) (PB-13).
- **Routing can ask the Claude Code account what it can run.** The Claude Code driver declares an availability adapter: the binary and its version come from `resolveToolBin`, auth from `claude auth status --json` — the one non-interactive check the binary offers today, of whose nine keys exactly one, the `loggedIn` boolean, is read, so the email and the open account id it prints beside it stop at the adapter — and the model inventory from the driver's own alias set plus its default model, because the binary publishes no listing at all and an unrecognised word after `claude` is taken as a prompt rather than refused. No binary is `binary_missing`, a logged-out account `not_authenticated`, and a logged-in one `unknown` / `quota_unknown` with no limit windows: Claude Code exposes no stable source for the remaining limit, so the adapter reports none rather than modelling one, and the resolver penalises that instead of blocking the harness. An answer the adapter cannot read — an older build with no `auth` subcommand, a moved shape — is `quota_unknown` saying auth could not be verified, never a guessed logout that would take every Claude tuple out of routing. The auth check is spawned asynchronously and killed on the adapter's own deadline: an adapter that blocked the event loop would stop the preflight's one budget timer from firing, and the ceiling of a routed command would become the sum of its adapters instead of one budget. A lift refused because the limit was spent between the preflight and the launch marks the harness exhausted from the driver's existing limit-refusal pattern — `subscription_exhausted` when the harness said the limit resets, `manual_exhaustion` when it explained nothing, both with no reset time invented out of the harness's own words and both therefore cleared only by hand — and the refusal names the file that mark went into and the way out of it, because nothing reads that file yet (PB-15).
- **Codex answers what the account can run, without starting a thread.** The Codex driver carries an availability adapter: a fresh `codex app-server --stdio` under the same isolated environment a lift uses, `initialize`, the limit, the model list, and the process killed again — no `thread/start`, no turn, so asking costs neither a session nor a run. The limit comes from the `account/rateLimits/read` request, which answers at once: measured on codex-cli 0.146.0, the `account/rateLimits/updated` notification the lift waits for never arrives after `initialize` alone (10 s and 30 s on a live account saw only `remoteControl/status/changed`), so a probe built on it would report no window ever; the bounded wait for the notification is kept for a binary without the request. `primary` and `secondary` become windows under the names the payload gives them, with `lengthSec` from `windowDurationMins` and `resetAt` from `resetsAt` in unix seconds; a reached limit is `subscription_exhausted` with the reset of the window that was reached; a refusal of the limit read that is not a missing method is `not_authenticated`; no snapshot from either source stays `unknown` / `quota_unknown`, because "no notification" has never been a refusal. Models come from `model/list` with the hidden ones left out. `getAuthStatus` and `account/read` are never called — one hands back a token, the other the account e-mail — and the child is given no stderr pipe at all, so the `base_instructions` cache ERROR a healthy app-server writes cannot be read as a failure. The lift's own refusal is untouched; the two gates share the protocol reading, not a copy of it (PB-17).
- **Routing can see the Cursor account.** The Cursor driver declares an availability adapter: `cursor-agent status` for auth, `cursor-agent models` for the inventory, both under the one preflight budget the whole probe shares — the deadline starts before the binary is resolved — with ANSI stripped before anything is parsed. The exit code of `status` is never consulted: it is 0 signed in and signed out alike, so the text is the answer, and text that says neither thing is `probe_failed` rather than a logged-out account. Model ids are taken whole with their effort suffix, because in Cursor the level is a suffix of the id and not a flag, and a `(NO ZDR)` mark travels as `flags: ['no-zdr']` on that row for an overlay to act on — the package judges it not at all. A logged-in account is `unknown` / `quota_unknown` rather than `available`: Cursor exposes no limit source, so no `windows` are reported and nothing is modelled in their place. A missing binary is `binary_missing`, a signed-out one `not_authenticated`, and a slow one `probe_timeout` — never `unavailable`, which would drop every Cursor tuple out of a run over a machine being busy. A listing that refused or came back unreadable is `probe_failed`, not an account with no models. Nothing the binary printed reaches the verdict message: `status` prints the account address, and the adapter counts and classifies instead of quoting. A Cursor limit hit at start is still not marked in the cache — the start path names no limit, and a mark hooked to what it does say would fire on a wrong model id (PB-16).
- **The pick itself: a resolver and the text it prints.** `resolve({ role, strategy, constraints, policy, snapshot, liveParticipants, now })` answers one decision document — the chosen tuple and every candidate it considered, each with its availability, its four score components, its adjustments or its exclusion reason — and `render(decision)` is that document as the terminal shows it. Filtering follows ADR-003's order and the first step that matches is the reason reported; a harness the snapshot does not carry is filtered out rather than excluded, because the snapshot's harness set is what the workspace declared. Ratings normalise from 1–5, `quotaCost` inverts, `remaining` is `100 − max(usedPercent)` over the harness's windows, and a harness that exposes none — or that is `unknown` — counts as a neutral 50 % and takes the penalty instead of blocking the run. Every weight, penalty, bonus and the reviewer floor is read from the merged policy, so an overlay moves them and no number is written twice. The reviewer floor is a choice rule rather than a filter: a candidate below it keeps its place and its score, and when nothing reaches the floor the best remaining candidate is taken with a warning. The tie-break — effective score, confirmed availability, canonical priority, tuple id — is total, so input order never reaches the result. Both golden fixtures are reproduced: the decision JSON after the normalisation their README states, the `models` text byte for byte. No command is wired yet; PB-21 does that (PB-18).
- **The commands that use all of it.** `promptobus models` prints what the resolver would pick right now — the chosen tuple, every candidate with its score components or its exclusion reason, the models the account exposes that the catalog does not rate, and the warnings — as text or, with `--json`, as the decision document; `models validate` checks the catalog and every overlay layer, and `models --clear-exhausted <harness>` lifts an exhaustion the cache holds with no known reset. `models` has no `--dry-run` because it is one: it reads the cache and asks no harness anything, and `--refresh` is the only flag that probes and therefore the only one that writes. `spawn` and `review` gain `--strategy <quality|balanced|speed|economy>`, `--allow-payg` and `--refresh`: the resolver picks harness, model and effort, while an explicit `--harness`, `--model` or `--effort` becomes a constraint on that choice and is never replaced by a neighbour. Without `--strategy` the path is exactly what it was, down to the driver's own defaults. Routing joins the gate order those commands already state — everything before the first disk write — so a strategy with no candidate ends with the rendered decision and leaves no task, no worktree and no participant behind; explicit constraints are checked against the merged catalog and the workspace declaration BEFORE the resolver is asked, because the resolver cannot tell a harness this workspace never declared from nothing surviving. A dry run reads the cache and writes neither a cache entry nor task state, and `--refresh --dry-run` probes and still writes nothing. The decision is kept in the participant's `metadata.routing` and printed per routed participant by `promptobus status` — strategy, tuple, score, snapshot age and warnings — through the accessor the protocol declares for it, so the strategy envelope is auditable during a run and not only at its start. A decision is aged from the oldest availability entry's own `checkedAt` rather than from the moment the command ran, so "12 s old" says how old the facts are — and a preflight that probed nothing no longer rewrites the cache under a fresh stamp. A snapshot nothing in which was ever checked prints as `never checked` rather than as an age counted from the epoch; the JSON keeps both literals. The nine routing error codes are registered in `ERROR_CODES`, and the drift check now reads the reference table against them (PB-21).

- **The orchestrating agent now has the rubric that turns a task into one strategy.** `skills/orchestrate` carries the `auto` rubric — contracts, architecture, security, migrations, incidents and any still-ambiguous statement are `quality`; ordinary development is `balanced`; reconnaissance and a small precise change are `speed`; bulk low-risk routine is `economy`; and the price of a mistake moves a track up one row — together with the strategy envelope agreed before the first spawn (strategy per track, allowed harnesses, PAYG policy), where a fallback inside the envelope needs no second approval and leaving it does. A `--harness`, `--model` or `--effort` the person named travels to the CLI unweakened and is never rewritten into a strategy; two review rounds without progress step the track up once, named in the run's result; `promptobus models` is how the pick is seen before spawning and `promptobus status` how the envelope is audited during the run. `skills/solo-review` gets the reviewer's default `quality` and the diversity rule — a reviewer off the worker's harness or model scores higher, and a second reading with the same blind spot is not a review. A consumer layers its own policy on top in its own skills (PB-19).

### Changed

- **The Cursor driver declares its binary as `cursor-agent`, not `cursor`.** `options.tool` is the name the package hands to `host.resolveToolBin` and from there straight to `run`, so it must be the name of the binary that actually starts; it said `cursor`, which is the harness name, and the driver's own search order puts `cursor-agent` and `agent` ahead of it. A host that switches on that name meets `cursor-agent`; the harness id, `--harness cursor` and the `tools` list are unchanged, and consumers meet this once, at the release that closes the routing series (PB-2).
- **Host contract: `PromptobusHost` gains a required `harnessStateHome(harness)`.** A second required method, and a consumer meets both at the same closing tag. It names where the package keeps its session registry for one harness — the records `inspect`, `stop` and the wake path read and write — and may answer `null`. Precedence at the call site is `PROMPTOBUS_<HARNESS>_HOME`, then the host, then a refusal naming both; there is no default any more. The default is what went wrong: the package fell back to `~/.promptobus/<harness>` when the variable was unset, and a consumer that had named its own variables instead had two harness registries writing into the operator's real home while `inspect` read the sandbox — two halves of one test in different directories, with no error anywhere. The standalone host answers the same `~/.promptobus/<harness>`, so a single-user checkout notices nothing. The host is bound for the process by `runPromptobus`, because the registry helpers are reached from call sites with no host at hand, and the first binding wins so a later host cannot move the registries mid-run; that is the one exception to "no process-wide singleton", and it is written at the top of `lib/cli.js` (PB-2).
- **Host contract: `PromptobusHost` gains a required `routingPaths()`.** The host names the availability cache and the ordered overlay layers; an existing host implementation must add the method, and `tsc` refuses until it does. Those files are account-scoped, not workspace-scoped, so they do not hang off `promptobusHome()` — a per-store cache would re-probe three harnesses for every checkout of the same account. An ordered list rather than a getter per layer, so a consumer can insert its own policy layer without another change to the interface. No release is cut until the routing series ends, so a consumer meets this once, at the closing tag (PB-11).

### Fixed

- **The suite could execute a real user binary when a stub name was missed, and PATH is now sealed.** Sandboxing `HOME` and `TMPDIR` seals nothing by itself: a child escapes through `PATH`, and a driver test hung because `spawn` resolved the Cursor driver's declared tool name through the standalone host — which hands a name back without searching — so `run('cursor')` found the operator's own `~/.local/bin/cursor` and waited on `cursor mcp enable`. The runner now hands every suite file a `PATH` of ONE directory holding a symlink per binary the suite is allowed to reach — `ast-grep`, `env`, `git`, `node`, `npm`, `pgrep`, `ps`, `sh`, `sleep`, `tar` — and nothing else; no harness binary is on it. A name nobody stubbed fails to resolve instead of launching whatever is installed. The seal is built in one place, the shared hygiene list, whose two callers are the runner and the helper a file run by hand imports, so files that compose their own `${BIN}:${PATH}` compose it from the sealed value and needed no edit. It is watched rather than assumed: every command the package launches through `run` is appended to the run's resolve trace, and the run goes red if any resolved path lies outside its own run directory — a name that resolved to nothing is the seal working and is not counted. One consequence to know: a refusal branch that used to reach a real binary now reports "not found in `PATH`" under the suite, the Cursor driver's `tmux` resolve being the visible one (PB-2).
- **Two suites on one machine counted each other's processes.** The Codex driver file counted holder and app-server processes with `pgrep -f` by program name — `codex-hold.js` and `app-server --stdio` — which reads the whole machine, and a worker run by tracks puts a second `npm test` on that machine as a matter of course. Reproduced deliberately: two runs started 3.2 s apart reddened the check `after a lift refusal there are no holder processes` in BOTH at once, each counting the other's pids. Both patterns are now qualified by a path this run alone owns — the holder carries its session file under this stand's state home, the stub app-server its bin directory inside this file's sandbox — with a sentinel beside them that requires the sandbox path to stay in each. The tmux member of the same family is checked from the other end: the Cursor wake file now verifies that the `tmux` its run resolved is the stand's stub and that its session state sits in this run's own stand home, so the machine-wide `cursor-agent` server the mechanism shares with a person's own sessions is never reached from a run. The register of every machine-wide read in the suite, and what scopes it, is in the header of `test/run.mjs` (PB-14.4).
- **The sweep sentinel saw only one spelling of the temp directory, and eight prefixes were never demanded of the list.** The check that keeps `SUITE_PREFIXES` complete grepped `mkdtempSync(path.join(os.tmpdir(), '…'))` and required the `os.` qualifier, so a file that did `import { tmpdir } from 'node:os'` and wrote `join(tmpdir(), '…')` was invisible to it: its sandbox prefix was never demanded of the list and never swept, and the check stayed green on an incomplete list. The pattern now takes both spellings of the directory and both of `join`. Measured on this tree: the old pattern found 44 literals and reported nothing uncovered, the widened one finds 61 and reported eight uncovered prefixes — `promptobus-routing-` (four files, including two the routing series added), `promptobus-legacy-`, `pb-hooks-`, `pb-hooks-home-`, `pb-home-`, `pb-install-` and the `promptobus-routing-a-`/`-b-` pair a family entry covers. All of them are on the list now, so their sandboxes are swept after a cut-off run instead of piling up in system `$TMPDIR` (PB-14.5).

## [0.2.1] — 2026-09-05

### Changed

- **`spawn` keeps the brief as a task artifact.** The assignment file the orchestrator passes was read into the participant prompt and forgotten, so orchestrators invented a home for brief files outside the bus. After a successful lift the brief is copied into the task files folder as `brief-<worker>.md` — next to the review diffs — and the lift output names the path. Every lift stores the brief it was given: a repeat at the same address takes the next number instead of overwriting the previous assignment, and a refused spawn keeps nothing (PB-10).

## [0.2.0] — 2026-09-05

### Changed

- **Host contract: `cloneOf(abs)` replaces `reposRoot()`.** The host names the clone a directory belongs to and its namespace path; the package no longer walks a single "repos root" or requires a two-segment namespace — `need-pair` and `cwd-need-pair` are gone from `reviewLayoutError`. A host with several zones (`repos/<group>/<repo>` beside `external/<repo>`) could not be expressed before (PB-5).

## [0.1.0] — 2026-09-04

### Added

- **Public repository skeleton:** package manifest, MIT license, backslop tracker layout, and a GitHub Actions matrix for Node 20.
- **The bus itself:** TypeScript core with tasks, mailboxes, artifacts and the driver contract; a JavaScript runtime; drivers for Claude Code, Cursor and Codex; and the `promptobus` command.
- **A host contract instead of an ambient workspace:** `PromptobusHost` is passed explicitly on every call, with a standalone implementation that reads `cwd`, Git and `promptobus.json`. A consumer with no previous store declares no legacy layout, and that is a normal state rather than a failure.
- **Documentation for a first-time reader:** README in English and Russian, an architecture decision on the standalone boundary, and guides for installation, hooks and trust, and contributing.
