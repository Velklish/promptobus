## [Unreleased]

### Added

- **A per-harness ceiling on live participants bounds the harness choice under `balance`.** The overlay key `caps.liveParticipants.<harness>` is a count of participants of ONE task, merged harness by harness: under `--strategy balance` a harness that already carries that many leaves the pace comparison, so the next worker goes to another subscription. It bounds a run and not an account — the count is the task's own participant list — and it is counted in participants, where the similarly named `penalties.liveParticipantCap` is a ceiling on the live-participant penalty in score points. A ceiling and not a steeper penalty — `penalties.liveParticipantPerHarness` only orders candidates inside a harness, and the pick is made by pace, so an account ahead of the others attracted the third and the fourth worker whatever the penalty cost. A harness no layer names is unbounded and behaves exactly as before; `0` means never that harness, and is reached with nothing live on it. A capped harness keeps its candidates, their scores, its pace rows and its representative — the cap is a choice rule like the quality floor, not a filter — and its rows carry `pace.atCap`. When the ceiling moves the pick, the decision carries a `live-participant-cap` warning naming the harness the cap actually held out — read off the removed rows, never off the pick the comparison would otherwise have made, because removing a capped representative lowers the leader and can widen the band onto a harness no cap touched — its count against the ceiling, both tuples, any further harnesses at their ceiling, and the overlay key, and `spawn` and `review` print that code on their routing line; a ceiling that held out a harness the comparison would not have taken is silent. Every paced harness at its ceiling is a soft fallback with the same code, not a refusal. `models validate` refuses a fractional or negative count and a ceiling on a harness this CLI does not drive. (PB-162)
- **A pin gate — `npm run pins`, `scripts/check-pins.mjs` — fails when a tracked file names a backslop release that disagrees with `cli` in `backslop.json`.** `upgrade` rewrites the pin in `backslop.json`, in `docs/**` and in the root `*.md`, and `lint` warns over that same set; neither reaches `package.json` or `.github/workflows/ci.yml`, where the pin is a live command rather than prose. PB-167 moved both by hand and left the next raise with nothing but a paragraph in the contributing guide between it and the same silence. The gate reads the expected version out of `backslop.json` and carries no literal pin of its own — a gate with one would be one more place for a raise to miss. It skips exactly what `upgrade` skips, restated rather than imported because the CLI arrives by npx and is not a dependency: `CHANGELOG.md`, `docs/adr/**`, `docs/archive/<PREFIX>-N…` and task cards by basename, all of which cite a version as evidence of a moment. Green is not silent — it prints what the walk saw, today `43 live pin(s) in 10 file(s), 148 historical pin(s) in 134 record(s) left alone, 41 of them outside backslop.json` — and a live set holding nothing but `backslop.json` is a failure rather than a pass, because a gate that matches nothing is green for the wrong reason. The config is discounted from that floor on a measurement and not on reasoning: the first version of this gate counted it, and pointed at a spec no file in the tree carried it reported `1 live pin(s) in 1 file(s)` and exited 0 — the config matches itself whatever the walk does. It joins `gates` in `backslop.json` and CI, where it stands ahead of `backslop init`: that step runs backslop at the pin the workflow names and would regenerate the old `AGENTS.md` block over a raise it was not told about. (PB-167.1)

### Changed

- **Codex reads a project's `.codex/skills` from a directory that is not a git repository — measured, so the reviewer sandbox keeps no `git init`.** The reference and [ADR-008](docs/adr/adr-008-codex-reviewer-working-directory.md) said the point was unverified and refused to invent the precondition; it does not exist. The stand: a standalone-host workspace inside no repository at all, one stub skill in its canon carrying a marker string, and one live reviewer turn on a four-line diff. Codex put the sandbox first in its own skill-roots table, listed the stub by name and description, and the model read `SKILL.md` at the path that table gave it and opened its report with the marker — the path reached it only through the harness, since the review prompt names no skill and no such directory. The planned second run after `git init` was not needed. **The same turn also showed that the reviewer could not deliver that report**: all four of its bus calls failed with `user rejected MCP tool call`, each after the holder declined an `mcpServer/elicitation/request`, so the marker was read from the session rollout rather than from the `result` message it was meant to arrive in. The bus server is not the source — started as the participant starts it and driven by a client that declares the elicitation capability, it issues no server→client request and its `promptobus_send` succeeds. Both facts are recorded together in the reference and the ADR on purpose: the first without the second reads as a working reviewer. (PB-161.3, and PB-161.4 for what is still open)
- **The register rule is stated to cover a worker's own scaffolding, not only the suite's checks.** `contributing.md` § Suite isolation says machine-wide reads must be scoped by a path, a pid or a mark the run owns, and a program name is not one. It now says so about the throwaway tooling a worker builds around the suite as well, with the case that taught it: two `until ! pgrep -f "test/run.mjs"` wait loops matched the consumer's `cli/test/run.mjs` by substring, watched a neighbouring repository's runner, and outlived their own run until the system killed them. (PB-166)
- **A suite file that outlives its work is now caught, and a take-down reaches its children.** Two changes to the test suite, from one measurement. The shared helper every suite file imports, `test/home.mjs`, arms an unref'd watchdog at 240 s: a file that has FINISHED empties its event loop and exits, and the timer never fires, so a finished file pays nothing, while a file still alive at the deadline reports what `getActiveResourcesInfo()` names as holding its loop and exits non-zero. It is a second ceiling on a file's whole work and not a free one — `unref` saves the file that finished, not the file still working, and a file that legitimately runs past the deadline is taken down too, so the message names both readings instead of accusing it. That covers the single-file run — `node test/<file>.test.mjs`, the form the mutation-probe rule prescribes — which had no deadline, no child bookkeeping and no parent to notice, and whose process became an orphan at `PPID 1` the moment its session died. The number sits below the runner's 300 s so that under `npm test` a file names what holds it before the runner kills it blind; the runner's deadline stays as the backstop for the one shape a timer cannot reach, a file spinning inside synchronous work, which never returns to its event loop at all. Separately, `test/run.mjs` now spawns each file `detached` and takes a late one down by the negative pid: `child.kill` signals one process, and a suite file spawns them by the dozen, so its children used to be reparented to `init` and stay — reproduced on a fixture that spawns a marked child and hangs, which survived the deadline before the change and does not after it. What the first bullet of the card asked for is closed by a negative measurement instead: all 55 suite files, run one by one by hand on 2026-09-12, exit on their own — `lingered=0 failed=0` — so no file holds its loop open today, and the orphan source in evidence was a hand-built measurement stand rather than a suite file. (PB-166)
- **A Codex participant now runs in a `CODEX_HOME` of its own.** The driver builds one directory per participant under `$TMPDIR` at mode 0700 before the lift and removes it with the session — on `stop`, on `done` through it, and on a failed lift. It holds a copy of the owner's `auth.json` at mode 0600, the mechanism's MCP entries as `[mcp_servers]` of a `config.toml` written at 0600, and, for a worker, `[projects."<realpath of the worktree>"] trust_level = "trusted"`. The owner's `~/.codex` is read once for that credentials file, and the participant path never writes to it: no `[projects]` record and no session rollout land there. The availability probe still starts app-server in the owner's home to read the account limit before any participant exists, so the marketplace snapshot refresh is not something this isolation stops. Consequences: the owner's personal MCP set no longer reaches any participant, so the reviewer's mechanical write deny now covers every server the participant has; `thread/start` no longer carries a `config.mcp_servers` override, and the session record no longer copies the MCP set; the session rollout an operator may want lives in that home, and `phrases.logs` names it. `~/.agents/skills` is the one channel the home does not isolate — that root follows `HOME` — and the lift says so. ([ADR-007](docs/adr/adr-007-codex-participant-isolated-home.md), PB-161)
- **Workspace skills reach a Codex participant as files.** `<workspace root>/.codex/skills` is copied into the working directory's `.codex/skills` with a self-ignoring `.gitignore` beside it, the way the Cursor driver copies `.cursor/skills`; the lift line reports the count and source, or says why there is none. Both roles get it — a worker's copy lands in its worktree, a reviewer's in the directory of its own. (PB-161, PB-161.2)
- **The lift asks Git what it is about to overwrite, for every harness and not only for `.cursor`.** A driver now names the directories its launch files claim inside the participant's working directory — `options.launchDirs`, `.cursor` for Cursor and `.codex` for Codex — and `spawn` and `review` run `git ls-files` for each of them before the first write, naming the tracked paths in a warning. It matters most for a directory copied whole, which wipes its destination first: a repository that lawfully tracks `.codex/skills` of its own used to lose it in silence and have its branch dirty from the first second. Git is asked about the paths the lift will WRITE and not about the claimed directory whole, so a project that keeps its own `.codex/config.toml` or `.cursor/rules` — which a worker is meant to read — is not told on every lift that they are about to be overwritten; the copy destination is among those paths, so it is noticed without a sibling file beside it. Claude Code claims none: its mcp-config and settings file go to the task store. (PB-161.1)
- **A Codex reviewer works in a directory of its own, and that directory is trusted.** `<participant settings stem>.codex-sandbox` in the task store, the Cursor sandbox's shape: the skills canon is copied there instead of nowhere, the tree under review is attached as a read through `runtimeWorkspaceRoots`, and approval containment follows the session record's `cwd` and `addDirs` without a second decision. The trust record now names the participant's own working directory for both roles — a worker's worktree, a reviewer's directory — and goes, as before, into that participant's disposable `CODEX_HOME` and never into the owner's `~/.codex/config.toml`; the tree under review is never trusted, which was the whole reason the record used to be withheld. The reviewed tree gains no file from the lift and loses none. `review` now prints `reviewer home: <path>` on a real lift as well as in `--dry-run`, because the `reviewer … started in <repo>` line names the repository and not the working directory; `spawn` and `review` also print the `workspace skills:` line on a real lift, where it had been visible only in `--dry-run` — the canon travels as files, so whether it arrived is a fact about that lift. ([ADR-008](docs/adr/adr-008-codex-reviewer-working-directory.md), PB-161.2)
- **A Codex command approval that asks to leave the network sandbox is refused, for a worker as for a reviewer.** `networkApprovalContext` and a non-empty `proposedNetworkPolicyAmendments` were read by nothing, so a network escalation whose `cwd` was inside the roots was answered `accept` like any in-root command. The check now runs before containment and before the role split, and the reply is the plain `decline` — the holder never sends the `acceptWithExecpolicyAmendment` or `applyNetworkPolicyAmendment` arms. (PB-88.3)
- **The Codex reviewer's MCP deny is no longer a hedge.** On codex-cli 0.146.0 a tool named in a server's `disabled_tools` is absent from the thread's tool inventory: two threads differing only in that key, the MCP server asked `tools/list` and answering with both of its tools in each, and `mcpServerStatus/list` reporting one tool where the key was set and two where it was not. The filtering is app-server's, above the server. The reviewer prompt phrase and 03-cli § Review now state that instead of "enforcement was not observed", and both name the ceiling: no client-visible method returns the tool payload of the model request, so the inventory is what was measured. The two paid turns the owner authorised answered nothing — the second, captured from the rollout, shows an empty assistant message and `last_agent_message: null` — and the fixture records them rather than hiding them. (PB-87.3)
- **The backslop pin is `v0.6.0`, and the gates runner the Definition of Done names now exists.** `v0.4.0` carried no `gates` command — `backslop gates` answered `unknown command “gates”` and exited 1 — so the `gates` key in `backslop.json` named three commands that nothing executed, the required `gates N, green N` summary was unproducible, and two runs on consecutive days spent a turn diagnosing it and ran the three commands by hand instead. `upgrade` moved the pin in `backslop.json`, in the one `gates` command that names it, and in the prose of seven files — including a line in `docs/archive/README.md` that had been two versions behind at `v0.3.0`; `migrate` reported no format change between v0.4.0 and v0.6.0 and only advanced the version stamp, so no task card was rewritten. The same pin in `package.json` and `.github/workflows/ci.yml` is moved by hand: `upgrade` does not reach those two files and `lint` does not report the divergence. A workflow left on the old pin would be expected to regenerate the old `AGENTS.md` block on every push and undo the raise — inferred from what `init` does locally, where it rewrote fourteen lines of that block, and not from a CI run. The contributing guide now records that instead of promising the opposite, and the missing guard is filed as PB-167.1. (PB-167)
- **The hand-written backslop list in `.gitignore` is gone; the managed `backslop:start` block is the single source.** From v0.5.0 `init` writes that block itself, so the raise in PB-167 left thirteen hand-written adapter paths restating what the block already said and `/CLAUDE.md` listed twice. Nothing was broken by the duplication — git takes the last matching rule, and `git check-ignore -v` already named the managed block for all four adapter paths before the cleanup as well as after it — so this is dead weight removed, not a defect fixed. `.claude/worktrees/` moved up into the general section instead of going with its neighbours: it is where this repository's worktrees live, not an adapter output, and the managed block does not cover it; `git check-ignore -v .claude/worktrees/x` still names a rule. `init` at the same pin now reports `.gitignore: unchanged` where the run that found this reported `appended`. (PB-167.2)

### Fixed

- **A participant lifted with `bypassPermissions` no longer holds the warden's postcard, and a held message is no longer reported as a permission prompt.** The participant settings file the Claude driver writes carries `"crossSessionInbound": "accept"` under a prompt-bypassing permission mode and under no other — the key the harness's own held-message dialog names. Measured 2026-09-11 on claude 2.1.263, one background session per mode with the postcard knocked into its messaging socket: `bypassPermissions` held the message and its record went to `waitingFor: "permission prompt"` while the session's turn ran on and finished; the same lift with the key took the postcard with no dialog at all; `dontAsk`, `acceptEdits` and `auto` each took it without the key, so `dontAsk` is not in the list however its name reads. The stall predicate now separates the two dialogs that arrive through that one field: a prompt suspends a turn, so a participant that BOTH ended its turn and reported after its last activation was not stopped by the dialog standing on it, and no person is called to it. Neither mark lifts the stall alone — an end-of-turn mark alone would silence a dialog that ended a turn in silence, a message alone would silence a prompt hit later in a turn that had already spoken. A participant with no turn mark, or one that ended its turn before the activation, keeps its stall — the second is genuinely deaf and is something a person has to fix. The route printed for a dialog names both possibilities and the key that ends the second. `spawn` does not refuse the mode. (PB-165)
- **03-cli § Review now records why the reviewer gets no second immovable artefact, instead of leaving the absence to read as an oversight.** A reviewer that meets "the working copy contradicts the snapshot" resolves nothing itself: `Bash` is denied to it whole, and the snapshot is the only fixed thing it holds. The candidate fix — the worktree's `HEAD` content of every changed path, taken beside the diff — is refused, and the three reasons are in the reference so it is not re-proposed as new: it closes the discrepancy only on the diff's own paths while the prompt sends the reviewer into the working copy far wider; it costs 13.6× the bytes in the budget that matters (measured 2026-09-12, a seven-file branch: 22 422 bytes of diff against 306 067 bytes of full `HEAD` content), on every review and every re-review; and it guards a report the prompt already forbids, since on a contradiction the reviewer files no finding at all. The read-only guarantee is named as untouchable in the same place — `Bash` stays in `REVIEWER_DENY` and is not relaxed for convenience of resolution — and so is what the orchestrator already holds: the exact `git show <sha> -- <path>` inside the report, and `review --task` to re-snapshot. (PB-169, recorded first in the consumer's own tracker and moved here so the release carries it)
- **03-cli § `done` now names what each of the three drivers does about a stopped session's processes, including the one that does nothing.** Cursor reaps a tree and an orphan marker, Codex kills a process group, and the Claude driver's `stop` runs `claude stop <id>` and waits for the record to leave the registry — it reads no process, walks no tree and signals no group. Whether it has to is written as open rather than closed either way: nothing observed says `claude stop` fails to reap a session's grandchildren, and nothing observed says it does, and inventing a reap on that silence is what PB-161.2 refused for the Codex sandbox. The stand PB-166 asked for was then run (claude 2.1.263, 2026-09-12) and moved the question upstream of `stop` rather than answering it in `stop`'s favour. A participant's turn started a marked long-lived process; `done` closed the session and the process was in `ps` before and after, one occurrence each time — readable as a result only because the "before" reading exists, since "nothing is left" is equally green on a stand that started nothing. The columns are the finding: `ppid=1 pgid=30358` in **both** readings, so the process was an orphan in a group of its own before the stop, `nohup … &` having detached it behind a short-lived tool shell. Neither shape the card proposed would have reached it — a tree walk from the pid `claude agents --json` names finds nothing outside that tree, and a group kill on the session pid finds nothing outside that group; only the stand's own mark did, and the mechanism cannot mark a command a worker writes. So `stop` has nothing to walk by the time it is called, and what is open is upstream of it: how the mechanism delimits "this session's processes" when neither the tree nor the group holds them. One candidate — lifting a session into a process group the mechanism creates and sweeping by it — is a change to the lift and is not made here. The stand's boundary is recorded with it: its process was detached, so a descendant still attached at the moment of the stop is not covered. (PB-166.1)
- **The three non-approval Codex server requests are now derived from the measured schema instead of a typed list.** `item/tool/call`, `account/chatgptAuthTokens/refresh` and `attestation/generate` are still answered with `-32601`, and a re-capture that adds a fourth now fails the suite rather than having it answered by an undecided fallback. 03-cli names them and says what the token-refresh refusal costs: a turn whose ChatGPT token expires mid-way ends with an authentication failure, which is expected rather than a fault of the holder. (PB-88.4)

## [0.5.0] — 2026-09-06

### Added

- **`promptobus models calibrate` reads this machine's own runs back against the shipped catalog and proposes overlay lines.** PB-36 began writing `telemetry.jsonl` at every `done` and nothing read it: a person could see that their serving stack or their subscription behaved unlike the catalog and had no reproducible way to turn that into an overlay correction. The command groups records by `(harness, model, effort)` and never by `tuple` — a lift made with an explicit `--model` carries no routing decision, and 18 of the owner's first 21 records had `tuple: null`, so grouping by tuple would have dropped most of the evidence and then reported a confident median over the rest. A model alias is resolved to a full id through the driver's own dictionary, handed over as `options.modelAliases`, so runs typed `--model opus` land on the row that rates `claude-opus-5`.

  Per key it prints the run count, the medians of `durationSec`, `turns` and `reviewRounds` **per accepted piece** — not dismissed before `done`, and at least one result sent — and the median window movement, which is one number per run: the largest delta among the windows that applied to it, because the resolver scores that tuple on `100 − max(usedPercent)` over the same set and a sum would count one account's session and weekly windows twice for the same tokens. A dismissed run counts as a run and as spend and never as a finished piece; a window that went backwards mid-run is a reset and contributes nothing.

  **The catalog is the anchor, not the local extremes.** Mapping the local minimum and maximum onto 1 and 10 was considered and rejected: with two eligible keys they become opposite extremes however close their measurements, which is exactly the relative-field defect the catalog itself just shed. Instead the eligible key with the most runs is the pivot and keeps its catalog bands, and every other key moves from **its own** band — one band at a 1.5× surprise against the ratio its bands already imply, two at 3×, capped at ±2 and clamped to 1…10. The evidence threshold is 5 runs per key and is a constant of the ADR rather than an overlay key; below it the line reads `insufficient data: N of 5`, and a key no catalog row rates gets its medians and no proposal. `quality` is never proposed from telemetry — review rounds measure how work was received, not how good a model is — and the accepted-piece counts are printed as a note.

  `--json` prints the whole report. `--write` merges only the proposed `ratings` into the layer whose id is `user`, per tuple and per rating, keeping every other key of that file and every rating set by hand; only ratings that MOVED are written, since an override equal to the catalog band would go on overriding after the next catalog update moves the row underneath it. Every band it compares against is the **shipped catalog's**, never the merged stack's: otherwise a person's own override would become the base of the next comparison and the rating would walk a step per run on unchanged data, so running the command twice on one file proposes the same thing twice, and an existing override is printed beside the catalog band rather than standing in for it. It asks on the terminal and takes `y` or `yes`; **without a terminal it refuses unless `--yes`** is given, which is the record that the person already agreed to exactly those lines — `--yes` without `--write` is refused rather than ignored. This is the one exception to the `user` layer being read-only for the tool, and it is that narrow: only this command, only `ratings`, only after agreement. (PB-37)

- **Ratings move to a 1–10 scale with absolute bands, and every overlay that carries `ratings` must be rewritten.** [ADR-005](docs/adr/adr-005-ten-point-scale-absolute-bands-calibrate.md) records the owner's decisions of 2026-09-06 and closes the five defects PB-29.1 found in ADR-004 § Catalog ratings. So a band is now absolute: `clamp(1 + roundHalfUp((x − floor) / (ceiling − floor) × 9), 1, 10)` against a **dated anchor pair** per benchmark, version and agent harness, fixed in the ADR and revisited at every catalog update.   **Migration, in one line: rewrite `ratings` on the 1–10 scale and set `schemaVersion: 2`.** An overlay on version 1 that carries any value on the rating scale is refused by the load and by `models validate` with that sentence, which names the keys it found.   **What moved with the scale.** Every strategy's rating components become `(r − 1) / 9 × 100`, `quotaCost` inverted as `(10 − r) / 9 × 100`, and `balance`'s `spendPenalty` becomes `balance.spendUnit × (quotaCost − 1) / 9`; the weights are untouched and the components still sum to the score. The role floors are restated as `qualityFloor: { worker: 5, reviewer: 9 }`, with `reviewerQualityFloor` still read as an alias. Every catalog row with a published figure is **re-banded from the figure** already in its `evidence`, not translated from its old band; the nine base rows without one are assessed anew on 1–10 against measured neighbours, with the reasoning in `evidence.text` and the rating named in `evidence.hypothesis`. Each base row's `evidence.text` names the anchor pair it was banded with. `fieldSize` is gone from the citation shape: absolute bands read no field.

  **`speed` no longer moves along an effort ladder.** Throughput is a property of the model and its serving stack, not of how hard it is thinking, so every rung of one model carries the base row's `speed`; the extra output tokens of a deeper effort are represented in `quotaCost` alone, and `quality` and `quotaCost` each move one band per step. One band and not two: two preserved ADR-004's relative step but spans eight bands over a five-rung ladder, so both ends of a long ladder ran into the clamp and `claude-opus-medium` came out sharing band 1 with `gpt-5.4-mini` at $2.63 blended — a top-tier model at medium effort reading as cheap as the cheapest row in the catalog. Every rung stays in the catalog even when the clamp makes two of them identical — the effort is still a launchable choice — and `models validate` says so with the new `ladder-indistinguishable` warning instead of collapsing them.

  **Upward interpolation no longer confers the reviewer role.** An interpolated rung could cross the reviewer floor on arithmetic alone, an unmeasured rung claiming a role its measured base never earned; a tuple is now offered as `reviewer` only when its own rating **and** its base row's assessed rating reach the floor, and `models validate` refuses a catalog that says otherwise. `codex-gpt55-xhigh` is the live case and is a worker row. In the other direction the wider scale opens the role up: `cursor-kimi-max` bands 9 from SWE-bench Verified 93.4, so all three harnesses offer a reviewer for the first time and ADR-003's diversity bonus has three harnesses to move between.

  **A hypothesis is a row that says so, not a row that is missing.** ADR-005 supersedes the wording ADR-004 left behind, which the catalog schema still carried: a row is omitted only when maintainers made **no assessment**: an assessed rating with no published figure stays in the catalog, named in `evidence.hypothesis`, so a model a person can actually launch is not silently removed from routing because a leaderboard has not got round to it. (PB-37, closing PB-29.1)

- **The reviewer is told its diff file is a snapshot, and the journal says how far behind it is.** `promptobus review` writes `files/review-<worker>.diff` once, at the call, while the worker goes on committing — on 2026-09-06 two reviewers of the same run read an older state and reported findings the author had already closed. Nothing locks the worker's tree, so the file is not made to follow it; its age is named instead. The reviewer's prompt now calls the file a snapshot, gives the moment it was taken and the worktree HEAD it was taken from, and sends the reviewer to the working copy for the current state before it reports a finding. The command prints the same pair beside the `diff base` line, and the reviewer's participant record carries it (`metadata.diffAt`, `metadata.diffHead`), so `promptobus status` and `promptobus_task` answer "how far behind" without opening the file. A repeat of the command with `--task` re-snapshots — a new numbered diff file and its path to the live reviewer — and both the record and the line move with it, which is why there is no `--fresh` flag.

  **`--strategy balance`, the fifth strategy.** The four ADR-003 strategies answer how to weigh the qualities of a tuple and are untouched; `balance` answers a different question — which account to spend from. For each candidate the **binding window** is the applicable one with the highest `usedPercent`, where applicable means the account-wide windows plus the scope covering that tuple; `underspend = (elapsedShare − usedShare) × 100` is how far behind its own pace that window is, in **percentage points of that window**; and `effective = underspend − balance.spendUnit × (quotaCost − 1) / 4` discounts a heavy tuple in the same unit before harnesses are compared. Each harness is represented by the tuple that would actually be picked on it, the largest `effective` leads, harnesses within `balance.band` (5 points, as is `spendUnit`) are tied and their `balanced` scores decide. It is a **choice layer, not a filter**: every candidate keeps its score and its place and gains a pace block, and when no harness can be paced the pick is the best `balanced` score with a `balance-fallback` warning rather than a refusal. `models` prints the pace table under the candidates and `--json` carries the same numbers. **Nothing in this package pins the reviewer to a harness** — it is routed by pace like a worker, with the reviewer quality floor above it and ADR-003's diversity bonus unchanged on top.

  **`near-limit`, and the switch a person agrees to holds for the next spawn.** A `near-limit` warning names a harness whose binding window is at or past `nearLimit.usedPercent` (80) or whose underspend is below `nearLimit.underspend` (−15 percentage points), with the window, its reset, **which of the two tests tripped** — a level and a rate are different facts about one window — and the strategy it would switch to: `economy` when every paced harness is past the threshold, `balance` when at least one still has room. No line when the strategy it would name is already the one running, and an exhausted harness is not repeated as near-limit.   **Precedence, everywhere: flag → overlay default → none.** `--strategy` on the command line always wins, which is the rule ADR-003 fixed for every named value. Below it, `defaults.strategy` from the merged overlays; below that, nothing — and nothing is the legacy path, so ADR-003's "a call with no `--strategy` routes nothing" still holds word for word where no layer sets one. `models` without `--strategy` takes the same default and falls back to `balanced` where none is set, so it and the next `spawn` cannot disagree about what is in force. ### Changed

- **For a host implementer: one new field on a routing layer, a snapshot at `schemaVersion` 2, and one file that lives beside the cache without a method of its own.** Everything a consumer host has to do for this release is in this entry, and it is one field.

The refusal is at the **declaration** and not at the write, for the reason `harnessStateHome` refuses instead of guessing: a person who learns their host names no writable layer from `models strategy --set` learns it after making the edit it refuses to keep, and two writable layers would make the file the tool writes depend on iteration order. A host that declares no overlay at all declares nothing to write, which stays lawful. **`tsc` does not say so** — the field is optional, so a host that omits it compiles — and the place it is learnt is the first routing command, which refuses with a `GateError` naming every layer the host declared; `models validate` reports the same thing as a finding rather than a refusal, and prints which layer is writable beside its path. A host should mark the **highest-precedence** layer, or the tool would write a value a layer above it overrides; `models strategy --set` warns when that happens. **The writable layer is state, not configuration, so it must not be a file anybody commits** — a consumer keeps it wherever its own state lives, under that one condition.

The cache and the `user` overlay are untouched and stay account-scoped.

  **The availability snapshot moves to `schemaVersion` 2.** A window now states its `kind` — `session`, `weekly` or `monthly` — its `lengthSec`, and an explicit `scope` that is `null` for the whole account, `{ model, models? }` for one model family, or `{ pool: "auto", models }` / `{ pool: "api" }` for a harness with two pools in one cycle; a harness carries `tier: { name, source } | null` and, where it has them, informational `credits` and `resetCredits`; and a model row the harness lists and declines to offer is carried with `hidden: true`. **A scope that covers models names them by id**, so nothing infers a model family from a display name the harness printed. **A cache written by an older version is discarded, not migrated**, and every harness then reports `unknown` / `stale_cache` — the shortest fact in that file lives sixty seconds and the longest an hour, so a reader for the old shape would buy one hour of not asking and be kept forever; the message says a discard happened rather than "no cache entry", so an upgrade does not read as a bug. Three rules keep the new fields honest at the disk boundary: a tier name is shaped like a code — no spaces, no `@` — because it is the second adapter-authored string that reaches disk and `message` is meant to be the only free-text one; the credit **amount** is deliberately not carried, a count being a fact about the account rather than about the plan; and the model-flag list is closed to the one mark that exists, `no-zdr`, because an overlay may deny by a flag and a name checked against nothing would let a typo ban silently nothing. A window with no length, an unknown kind or an unreadable scope is dropped rather than repaired — a garbled scope would otherwise widen into `null`, which is the claim "this binds the whole account".

  **The decision document and the participant record carry the new facts.** `harnesses` in the decision is the `availability:` block, assembled by the command from the snapshot after the resolver has answered, so `--json` carries exactly what the text form shows and `render` still reads the document and nothing else. A routed lift records `windows` on its participant — the applicable windows of the tuple it chose with the `usedPercent` they had at that moment — which is the starting value the spend of a run is later read as a delta from, and `promptobus status` prints it beside the routing line. `strategySource` says whether the strategy came from a flag or from a layer.

  **`telemetry.jsonl` lives beside `cacheFile` and the host does not name it.** It is deliberately not a method: it is one leaf inside a directory the host already owns, and a second path to declare would let a consumer put the telemetry of one account beside the availability of another. **The consequence for a consumer is that moving the cache moves the telemetry with it** — the two are read together by the calibration pass, and a `cacheFile` that changes between releases leaves the old records behind rather than migrating them. Like the cache it is the ACCOUNT's, not one workspace's: `promptobusHome()` is not used for it at all.

  **Token handling in the three adapters, since a consumer inherits it.** Claude Code's access token is read from the credential record, used as one header, and never written or refreshed — `refreshToken` is not parsed out of the record at all, the refresh endpoint is never called, and the suite greps both the verdict and the written snapshot for the token. Cursor's bearer comes from the macOS keychain item `cursor-access-token` first and from `CURSOR_API_KEY` only as a fallback; `cursor-refresh-token` is never asked for, and the backend URL read off `~/.cursor/cli-config.json` is accepted **only** as `https:`, because a bearer is about to be sent to it. Codex's tier comes off the call the probe already makes, and `account/read` — the method that answers the account e-mail — is still not called at all. Every keychain read and every HTTP call arrives as a parameter with a live default, so no test reaches the network or a keychain.

The decision the whole surface implements is [ADR-003](docs/adr/adr-003-model-routing.md), fixed with its schemas and golden fixtures before any of the code (PB-11, PB-12, PB-18, PB-21). The text form prints at most eight unrated rows per harness and counts the rest; `--json` keeps every row.

- **`--strategy`, `--allow-payg` and `--refresh` on `spawn` and `review`.** The resolver picks the harness, the model and the effort, and an explicit `--harness`, `--model` or `--effort` becomes a **constraint** on that choice rather than a value — a named value is never replaced by a neighbouring one, and a named combination that is unavailable or exhausted ends the command with diagnostics instead of a substitution. `auto` is not a CLI value: the orchestrating agent turns a task into one concrete strategy before the call. Routing joins the gate order those commands already state — everything before the first disk write — so a strategy with no candidate ends with the rendered decision and leaves no task, no worktree and no participant behind; explicit constraints are checked against the merged catalog and the workspace tool manifest before the resolver is asked, because the resolver cannot tell a harness this workspace never declared from nothing surviving. `--dry-run` reads the cache and writes neither a cache entry nor task state, and `--refresh --dry-run` probes and still writes nothing. Without `--strategy` the command takes its previous path down to the driver's own defaults (PB-21).

- **A rated model catalog ships with the package, and overlay layers sit above it.** `models/catalog.json` holds the first rated matrix — nineteen tuples across the three harnesses, each rating carrying a source and evidence a later maintainer can check; a model the harness exposes and nobody could rate from a named source gets no row and appears as a runtime `unrated` line that nothing picks. Above it, `host.routingPaths()` names the overlay layers, lowest precedence first — under the standalone host `~/.promptobus/model-routing.json` and `<workspaceRoot>/model-routing.local.json`, with room for a consumer's own policy layer between them. A weight set is replaced whole, an allow or deny list whole per selector kind, everything else field by field, and a missing overlay file is normal. **A ban is final from below**: the overlay schema refuses `deny: {}` and `deny: { models: [] }` alike and every denied name must exist, so "deny nothing" cannot be written and a consumer's ban holds whatever a person writes in their workspace file. Two hazards are written down where a person meets them: Cursor carries the effort level inside the model id, so a Cursor row names the full id and no effort; and a Claude row names `claude-opus-5` or `claude-sonnet-5` rather than the `opus` / `sonnet` aliases, because an alias re-points under a rating and nothing goes red. The overlay file to copy is in [guides/model-routing.md](docs/guides/model-routing.md) (PB-13, PB-13.1, PB-13.3).

- **The three accounts can be asked what they can run, before a session exists.** Each driver declares an availability adapter — Claude Code reads `claude auth status --json` and its own model dictionary (the binary publishes no listing); Cursor reads `status` and `models`; Codex opens `codex app-server --stdio`, asks `account/rateLimits/read` and `model/list` and kills it again, with no `thread/start` and no turn, so asking costs neither a session nor a run. The preflight runs all of them at once under one 15 s budget and resolves each binary once before the race, so a harness that never answers is `probe_timeout` rather than a command that hangs, and a host that spends the budget inside its own synchronous `resolveToolBin` stops the run instead of extending it. The result is the availability snapshot, kept at the file the host names with mode `0600` and a TTL per entry — an hour for auth and inventory, a minute for limit windows, five minutes for a failed probe, a confirmed exhaustion until its reset, and one with no reset until `promptobus models --clear-exhausted <harness>` lifts it. **The file holds no prompt, no token, no e-mail and no open account id**: a verdict is projected field by field onto the closed snapshot shape before it is written, so anything an adapter attached beside the contract never travels, and a writer holds a lock across the read, the merge and the rename so two commands probing at once do not lose each other's entries. A limit hit between the preflight and the launch marks the harness exhausted and refuses with `limit-hit-at-start`, naming the file the mark went into and the two ways out of it. `available` means auth, model **and** limit confirmed: only Codex reaches it, and Claude Code and Cursor stay `unknown` / `quota_unknown` because neither exposes a stable source for the remaining limit — which the resolver penalises rather than blocks (PB-14, PB-15, PB-16, PB-17, PB-21.1).

- **A routed run is auditable while it runs, not only at its start.** The decision is kept in the participant's `metadata.routing` — strategy, role, tuple, score, the snapshot it was made on and the warnings — and `promptobus status` prints that line per routed participant. The protocol version does not move for it: `metadata` is declared open in `schemas/v1/participant.schema.json`, so a record carrying a decision is readable by a mechanism of any version, and a reader that does not know the field ignores it (PB-21).

- **The orchestrating agent has the rubric that turns a task into one strategy, and the package now ships it.** `skills/orchestrate` carries the `auto` rubric — contracts, architecture, security, migrations, incidents and any still-ambiguous statement are `quality`; ordinary development is `balanced`; reconnaissance and a small precise change are `speed`; bulk low-risk routine is `economy`; and the price of a mistake moves a track up one row — together with the strategy envelope agreed before the first spawn (strategy per track, allowed harnesses, PAYG policy), where a fallback inside the envelope needs no second approval and leaving it does. A `--harness`, `--model` or `--effort` the person named travels to the CLI unweakened; two review rounds without progress step the track up once. `skills/solo-review` gets the reviewer's default `quality` and the diversity rule — a reviewer off the worker's harness or model scores higher, and a second reading with the same blind spot is not a review. Both files are in `package.json` `files` now, so a consumer references the rubric out of the installed package rather than out of a URL it has to keep in step (PB-19, PB-20).

- **A repository can declare how to restore the process skills it does not keep in git.** A worker repository's own `promptobus.json` may carry an optional `generate` field — the argv of a command, never a shell line — and `spawn` runs it in the fresh worktree: after the participant record reaches the task journal, so an interrupted generator cannot leave a directory the next spawn refuses to reuse; before the launch files, so a generator writing into the harness config directories is not the last writer; and before the dependency install, which is the trade the field makes — an `npx …` generator works in a worktree with no `node_modules`, an `npm run …` one does not. It is read from the WORKTREE at run time, because that is the file the participant will see. A refusal does not refuse the lift: the operator gets a warning with the exit code and a log beside the worktree, and the participant preamble names the outcome in **every** case, including "no generator declared" — a participant that is never told cannot notice that its repository's rules are missing. Skills committed to git stay the default and cost this step nothing (PB-8).

### Changed

- **Host contract: `PromptobusHost` gains two required methods and one declared field, and a consumer meets all three at one release.** `routingPaths()` names the availability cache and the ordered overlay layers — account-scoped, so they do not hang off `promptobusHome()`, which stays the per-workspace task store, and an ordered list rather than a getter per layer so a consumer can insert its own policy layer without another change to the interface. `harnessStateHome(harness)` names where the package keeps its session registry for one harness and may answer `null`; precedence at the call site is `PROMPTOBUS_<HARNESS>_HOME`, then the host, then a refusal naming both, with no default any more — the default is what went wrong, a consumer that had named its own variables had two harness registries writing into the operator's real home while `inspect` read the sandbox, with no error anywhere. And `HostToolBin` now declares the `version` field three drivers and three availability adapters were already reading: optional, and its absence means UNREAD rather than "old". The standalone host answers the same paths it used to guess and returns no version deliberately — it does not search for the binary, and `resolveToolBin` is synchronous, so reading a version would mean `spawnSync` inside the preflight budget. `tsc` refuses an existing host implementation until the two methods are added (PB-11, PB-2, PB-15.1).

- **The Cursor driver declares its binary as `cursor-agent`, not `cursor`.** `options.tool` is the name the package hands to `host.resolveToolBin` and from there straight to `run`, so it must be the name of the binary that actually starts; it said `cursor`, which is the harness name, and a host that hands a name back without searching sent that through `PATH` into an operator's own `~/.local/bin/cursor`. A host that switches on that name meets `cursor-agent`; the harness id, `--harness cursor` and the `tools` list are unchanged (PB-2).

- **The Codex MCP key prefix is the consumer's name, not a constant in the package.** The `config.mcp_servers` override merges with the operator's personal file by field, so the package moves its records into a namespace that file does not use — and the word is the consumer's identity, which the host already declares. The prefix is `${host.commandName}-`: standing alone it is `promptobus-` exactly as before, and inside a larger CLI a participant reads `mcp__<commandName>-promptobus__promptobus_send` and sees the tool it is running under. The config key and the tool name in the prompt still come from one function called twice; the prefix reaches the detached holder through the session record, because that process is handed a record file and has no host to ask. A key built with no prefix refuses instead of falling back to the canonical name, which would be the collision itself (PB-3).

- **Everything the package ships describes itself in English.** `description` and `title` in `schemas/v1/*.json` are translated, with every structural keyword, `$id`, pattern and required list untouched byte for byte, so the two schema directories in one tarball agree on language; the suite's own check titles and comments were translated with them, one to one, leaving fixture literals that stand in for a person's words alone (PB-12.1, PB-9).

### Fixed

- **A Codex holder dies with its session, and a run that leaves one behind now says so.** The holder is detached on purpose — `spawn` returns after the first turn and someone has to hold the app-server stdio — but it was reaped only from cleanup hooks, and the take-down that leaks reaches none of them: a suite file taken down with SIGKILL left its holder and app-server alive, and one 2026-09-04 run left twelve such processes alive into the next day, each holding a session file under a directory that had since been removed. The holder now watches for its own record every five seconds and, when it is gone, kills its app-server and exits without writing to its log — a log write would recreate the tree that was just removed. `stop` and `done` are unchanged: they reap first and remove the record after, so the watch usually has nothing to do (PB-2.1).

- **`done` left the worktree of a squash-merged branch behind and blamed a conflict.** Cleanup decided by a re-merge, and that question stops having an answer the moment the base moves over the same lines — after a squash and a second worker on the same file, `git merge-tree` conflicted on a branch whose work was already in. A second measurement now answers where the merge cannot: the branch's own patch id (`git patch-id --stable` over `git diff <fork> <branch>`) looked for among the commits the base gained since the fork. The report names the state instead of the obstacle — `merged as a squash`, `is entirely in <base>`, `is not merged` — and recognition stays deliberately narrow: a squash whose content was edited while merging, and work taken as several cherry-picks, keep the directory, because a directory is cheap to delete and impossible to return (PB-6).

- **The Cursor stall report fired on a session that was editing files.** Liveness had two signals — the chat transcript growing and an instrumental process under the session's tmux pane — and both are blind to the same phase: the agent edits files itself, inside one long call, and spawns nothing. Twice on live runs a participant was announced stalled while the owner's panel showed sixteen files edited. A third signal now covers it: how long ago the participant last wrote in its own working tree, the newest mtime among `git ls-files -mo --exclude-standard` plus its HEAD commit time. It is positive only — a recent write lifts the verdict, no write raises none — and the verdict names every measurement and its span, because an orchestrator has to tell a silent transcript from a dead session (PB-7).

- **The one message an operator sees at an undeclared harness sent them to a command that does not exist.** `--harness <name>` outside the workspace tool manifest was refused with `Declare it: promptobus tools add <name>`, and there is no `tools` subcommand. The refusal now names the file and the field instead — declaring a harness is a hand edit — and the only command left in the message is the host's own sync, which exists. A gate reads the dispatcher's own `case` labels and fails on any command string under `lib/` that is not among them, so the next inherited command cannot arrive quietly (PB-1).

- **`HostClone` now leaves the package.** `PromptobusHost.cloneOf(abs)` returns it and neither entry point re-exported it, so a consumer implementing the host could not name that method's return type without copying the interface — and `tsc` said nothing, because the interface compiles and the package builds; only the consumer's own build failed. It is in the `export type` list of `promptobus` and `promptobus/host` now, and the check that keeps those lists honest reads every `export interface` / `export type` out of `src/host.ts` instead of naming two by hand (PB-11.2).

- **The suite could reach a real user binary, count a neighbouring run's processes, and read a file from inside an unterminated string.** Six defects of one family, none of them shipped and all of them able to make a green run mean nothing: `PATH` is now sealed to one directory holding a symlink per binary the suite may reach, so a name nobody stubbed fails to resolve instead of launching whatever is installed; machine-wide `pgrep` patterns are qualified by a path the run alone owns, after two runs 3.2 s apart reddened the same check in both by counting each other's pids; the temp-directory sweep sentinel reads both spellings of `tmpdir()` and gained the eight prefixes it had never demanded; the package import scanner is a tokenizer that knows strings and comments, after a message fragment `' from '` was read as a module specifier and everything past it parsed from inside a string that never closes; nine checks that asserted the absence of text nothing writes are gone or made real; and the home diversion every suite file needs now lives in a module every file imports first, rather than in a helper 22 of the 46 files never load (PB-2, PB-2.2, PB-4, PB-9.1, PB-14.4, PB-14.5).

- **The publicity audit reads no link out of a code span or a fenced block.** A markdown sentence that quoted the link pattern was reported as a link to its example, so the gate refused documentation about its own rules (PB-22).

## [0.2.1] — 2026-09-05

### Changed

- **`spawn` keeps the brief as a task artifact.** The assignment file the orchestrator passes was read into the participant prompt and forgotten, so orchestrators invented a home for brief files outside the bus. After a successful lift the brief is copied into the task files folder as `brief-<worker>.md` — next to the review diffs — and the lift output names the path. Every lift stores the brief it was given: a repeat at the same address takes the next number instead of overwriting the previous assignment, and a refused spawn keeps nothing (PB-10).

## [0.2.0] — 2026-09-05

### Changed

- **Host contract: `cloneOf(abs)` replaces `reposRoot()`.** The host names the clone a directory belongs to and its namespace path; the package no longer walks a single "repos root" or requires a two-segment namespace — `need-pair` and `cwd-need-pair` are gone from `reviewLayoutError`. A host with several zones (`repos/<group>/<repo>` beside `external/<repo>`) could not be expressed before (PB-5).

## [0.1.0] — 2026-09-04

- **Public repository skeleton:** package manifest, MIT license, backslop tracker layout, and a GitHub Actions matrix for Node 20.
