# PB-226 · Result

**Closed 2026-09-17, completed.** A `type=artifact` message can no longer be written without a file, and a key the tool does not declare is refused by name instead of dropped. Three refusals carry it. **At the adapter:** `sendMessage` in `lib/store.js` throws a `GateError` on `type: "artifact"` with no `artifactPath`, naming that parameter. It stands there rather than at the tool because that function is where both doors meet — the `promptobus_send` tool and the `send` command, built and covered but not registered ([03-cli](../../reference/03-cli.md) § Send — built, not published) — so both are refused in the same words and a later registration of `send` inherits the refusal instead of needing its own. **At the MCP boundary:** all three tool declarations in `src/mcp/tools.ts` carry `additionalProperties: false`, and `requireDeclaredArgs` in `src/mcp/server.ts` checks the call against that same declaration at the top of `callTool`, before the task is resolved — MCP clients do not validate a tool's input schema, so the declaration alone would have changed nothing. The allowed keys are read from `MCP_TOOLS` rather than repeated in the handler: two lists drift, and the drift shows itself only when a key goes missing in silence. The rule is all three tools and not `promptobus_send` alone because the defect is the class: `promptobus_mailbox` given `claimed: true` used to drop the key and perform an ordinary take, a typo that reads as success. **At the engine's write path:** `prepare()` in `src/v1/engine.ts` refuses `type: "artifact"` that carries neither `artifact` nor `linkArtifact`, so a message built past the adapter — through `sendSync`, which is public API — cannot claim an attachment it does not carry; a `linkArtifact` that names no record of the task is refused as `artifact-not-found`.

**Reading was left exactly as it was, and that is a decision rather than an omission.** The invariant is held at the write and nowhere else: `src/v1/validate.ts` and the published `schemas/v1/message.schema.json` carry no such rule. Held at the read it would be retroactive — `readRecord` isolates a schema-invalid record into `broken/inbox`, so records of the old shape sitting in live journals would stop being delivered, and two of them were measured in this run's own store. `test/fixtures/v1/valid/message/artifact-missing-old-shape.json` pins that shape as valid, and two verdicts hold the mailbox itself: `peek reads the old shape as written and does not set it aside` and `read delivers it too — the mailbox is not stopped by a record of the old shape`.

**Presence, not a read, for a linked record — the trade-off taken in the last review round.** `prepare()` asks `existsSync(artifactFile(home, task, linkArtifact))` and does not open the record. Reading it through `readArtifact` would have been stricter and was the shape of the previous round, but `readArtifact` moves a corrupt record into the attic before it throws, and prevalidation must leave the task untouched — a refusal that has already changed the store is not a prevalidation. The price is stated out loud in [04-protocol](../../reference/04-protocol.md) § Artifacts: a `type=artifact` message may be written linking a record that is on disk but corrupt. Who classifies a broken record is the reader, not the sender, and the verdict `a link to a record that is on disk but corrupt is not set aside by prevalidation` holds it.
