# PB-209 · Result

**Closed 2026-09-13.** The pipeline was red on **every** push to main — eight consecutive runs, all four matrix cells, the `v0.7.0` tag among them — and the cause was not the subject under test but the guard standing beside it. One file of 65 failed at the `Test` step, so `audit`, `pins`, `init` and `lint` never ran on any push at all: the project had no working CI and did not know it.

The failing line was a **validity precondition**, and it failed in the direction nobody expects: `assert.ok(took > 150, 'the two stub calls answered in ${took} ms — too fast to prove anything')`, with the runner answering in **114 ms**. Not "the machine is slow" — the machine is fast, and the check refuses to draw a conclusion. The real evidence in that test is counted (`ticks >= 5`), and the comment directly above it argues why counting beats timing: "a threshold in milliseconds would measure the machine's neighbours." The precondition written one line below contradicted that argument.

**Closure:** a test-only mode in which the stubs answer deterministically — two sequential waits of 100 ms. The precondition then holds **by construction** on any machine, and the tick count stays the evidence. No other fixture is touched.

**Verification.** Gates on the merged tree; on the worker's tree `6c45acc`: `backslop gates` exit 0 — gates 4, green 4, `npm test` exit 0 with 65/65 test files. Baseline before the change: the file is green locally, 46/46 — which is itself part of the evidence, because it shows the defect lives only where the machine is fast enough, exactly as diagnosed. Mutation probe: restoring the blocking call in place of the non-blocking one reddens the check, which is the probe the test's own comment prescribes; two earlier patch attempts were refused before any mutation applied and were recorded as **not** measurements rather than dropped. The isolated reviewer confirmed the two things asked of it: the mode is genuinely test-only and does not leak into the ordinary path, and the two sequential waits preserve the counted probe rather than replacing one wall-clock threshold with another.

**Documentation in the same pass.** `docs/reference/03-cli.md`, `README.md`, `CHANGELOG.md`.

**Left open, and it is not small.** The fix cannot be verified where the defect lives: **nobody ran the CI matrix**, because the only way to run it is to push — the very action this card unblocks. The first push after this merge is the measurement, and if it stays red the diagnosis was wrong, not the environment.

Second: this card has a **root twin**, `PB-159.1`, and it is recorded as a dependency rather than a note. That card names this same file — "the probe and status budgets" — and prescribes the same remedy, counted evidence in place of a millisecond threshold. The two differ only in which end they fail from: there a budget is missed under the load of neighbouring suites, here a precondition is missed on a machine that is too fast. The neighbouring absolute thresholds in this file (`elapsed < 2750`, the status budgets) were deliberately left untouched — they belong to that card, and whoever opens this file next is expected to close both, or the work lands twice.
