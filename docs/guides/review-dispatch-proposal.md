# Starting an approved review while the orchestrator is busy

**Proposal for owner decision; no runtime change.** The retained canonical worker status at 13:24:30 UTC on 2026-10-26 reported focused checks on a frozen revision, no running operation, no technical blocker and full gates not started. That timestamp dates the report, not a command start or a measured idle interval. It does not establish that a reviewer was ready then, compare models or measure savings.

## Where the handoff belongs

Start with the BB route only. Let the existing BB plugin runtime reconcile a narrowly preauthorized transition when a canonical worker result commits, and on reconnect. It should call the same review admission and launch path as an explicit owner request. The trigger is *evidence becoming eligible*, independent of whether the owner is in a turn. This requires new code in that runtime, not a new session. Without explicit delegation the owner continues to dispatch manually.

Native review remains owner-invoked.

### Who makes evidence ready

Before work, the owner specifies each review prerequisite (required pass, permitted skip with an exact condition, or integration-only), producer, owned paths, reviewer assignment template and resource limits. The executor runs only authorized checks and retains original terminal receipts and streams. An unaccounted gate, required failure, pending outer call or unauthorized skip blocks review.

Use one pre-launch evidence route. The [current uploader](../../integrations/bb/engine-host.ts) reads bounded files under the ready orchestrator's `ownedRoots`, sends from that orchestrator, and needs an existing canonical recipient. For this proposal the recipient is the already registered producing worker in the same task, **not** the future reviewer. Its artifact mail is not a new assignment. Before work, bind the executor's exact command outputs to a per-assignment directory already authorized for that worker to write and for the owner to read under its declared `ownedRoots`; fix the owner-only staging paths there or in a separate owner-owned directory. Validate real paths, ownership, source environment and terminal receipt identities. If the roots do not permit this handoff, or the worker cannot receive artifacts, the route is ineligible. Do not copy from undeclared paths or enlarge roots at dispatch.

**Proposed scoped owner action, not a current CLI facility:** the task runtime may act on the verified owner delegation only for that file inventory, recipient and assignment. It runs the [preparation sequence](../../integrations/bb/README.md#compact-current-review-evidence) on finalized originals, then calls the owner-bound upload operation for each missing upload-plan entry. Parts land as canonical task artifacts from the orchestrator to the worker; record the worker as original producer and the orchestrator as relayer. Feed the actual ordered upload receipts (IDs, sender, sizes and hashes) to `evidence-prepare`. This constructor prints the typed manifest; it neither uploads nor publishes it. The scoped action publishes the exact manifest bytes and digest in a proposed durable, owner-bound task record keyed by assignment and intended reviewer ID. Generate the explicit `participant add` input from that record. Admission uses the existing bound owner as reader to resolve every landed part, then checks source, producer/relay identity, bytes, hashes and required coverage. The reviewer's first assignment references those task artifact IDs through the bounded manifest; no pre-launch reviewer mailbox or acknowledgement is needed. Unreadable parts block launch.

Reconcile on **either** canonical result commit **or** durable manifest publication after the last required part lands, and rescan both on reconnect. Neither event alone is sufficient. Do not wake the owner to copy evidence, synthesize missing receipts or rerun an unchanged check merely to repair packaging.

### Authorization and single launch

The [current control schema](../../integrations/bb/control-schema.ts) has neither a review delegation nor its expiry. Propose a versioned opt-in owner publication: authenticate the publishing session against the current task's actual owner thread, project, host and environment under the task lock; record the human approval reference, control revision, expiry, producer binding/assignment, permitted source/base, evidence operations, destination actor, exact provider/model/effort/permissions and actor/command/round ceilings. Require separate current executor and reviewer grants. Child-authored fields, a self-asserted `ownerConfirmed`, or an attention event cannot create this record. Missing verifiable provenance, ambiguous clock/expiry, unsupported versions or routes fail closed.

**Uniqueness and capacity.** One obligation per `(task, producer binding ID, causal assignment boundary, destination step, phase)`. Use the latest canonical result in journal order after that boundary when the complete evidence first validates. In one proposed durable transaction shared by manual dispatch of that obligation, automatic dispatch and reconnect, compare the obligation's absence and available capacity, then persist the unique reservation, slot claim, immutable payload and launch intent together. The payload fixes result ID, source environment/base/head, manifest digest, grant/delegation revision and reviewer route. On conflict read the winner; do not enqueue a second start. A new result ID, manifest or token cannot replace that payload. If it ceases to be current, fence it; only a fresh authorized assignment can create a successor obligation, subject to capacity.

**One start route, including corrections.** Use `participant add` with `--environment` naming the already prepared, verified source environment and the constrained reviewer provider. No `--environment-path`, `--new-environment`, bootstrap prompt or `participant resume`. Refuse before SDK spawn if the route would require provisioning or a preparation turn. Each round requires a separately authorized fresh reviewer participant ID, grant, thread and launch intent; the same approved model and restrictions review the new head with the prior report and closure evidence. If fresh participants are outside the approved ceiling, park the round. Do not reuse an earlier thread or attempt ID. Change the spawn path to use the transaction's persisted intent rather than minting another ID inside spawn.

**Final check.** Before submitting the initial prompt verify the reservation, prepared environment, authority and frozen evidence. Hold prompt dispatch until the actual thread binding is ready; the first possible model turn is the review assignment, never the current provisioning-hook bootstrap exception. Immediately before allowing it, extend the final hook to reread authoritative control and journal, revalidate the actual producer and reviewer bindings, exact causal assignment and latest result, clean source environment/path and full head/base, landed manifest digest and contents, exact reviewer route/permissions, unexpired delegation revision, current grant tokens, STOP/noNewStages and reservation ownership. Compare to the frozen payload. Today the hook checks current control but does not establish this evidence freshness. A mismatch before admission refuses the turn; retire the claim only on proof no operation remains. If revocation or source change crosses the hook/provider-start gap, retain the observed start, quarantine its output, request authorized Stop and refuse workflow advancement on a fresh authority check. Keep the slot until matching termination and confirmed drain of outstanding calls; a Stop request or idle flag is insufficient.

**Lost response.** Bind the reservation to the persisted `launchAttemptId` before submission. Reconcile against the BB launch intent and exact thread metadata, parent/lifecycle owner, provider and environment. One matching candidate can restore correlation, not prove a turn started or drained. Empty or ambiguous lookup after possible submission stays unknown, occupies the slot and requires recovery; do not retry. Duplicate deliveries and manual requests return the same attempt and receipts.

## What counts as progress

| Phase shown | Minimum observation | What happens next |
|---|---|---|
| Waiting | Assignment or preceding terminal receipt; no matching start | Show dependency, capacity, explicit blocker with responsible actor, or next eligible action. |
| Reserved / submitted | Admission bound to operation ID | Await actual start. Preflight, queued work and an accepted call do not count as execution. |
| Running | Correlated command spawn or provider turn-start with session/turn identity and time | Retain until matching terminal receipt. A live session alone does not prove a gate is running. |
| Finished / failed / unknown | For commands, original exit or signal and outer call completion; for review, turn end **and** matching canonical result to advance | Missing or inconsistent proof stays pending/unknown. A finished turn alone is not a handover. |
| Ready for owner | Current independent result and evidence for that exact revision | Owner decides findings, exceptions and acceptance. Publication is a separate operation. |

**Observation contract (proposed).** For each event persist its source, operation/attempt ID, source event ID and occurrence time if supplied, host observation time (UTC), and journal cursor. Correlate an actual child-process `spawn` event with command ID/process identity and its exit/signal plus outer completion; the current direct-command receipt timestamp precedes spawn. For model execution require a public provider turn-start and terminal event with the same thread/turn and bound launch attempt. If the route lacks these observations, show unknown rather than reconstructing running time from an admission, terminal file or thread display state.

**120 seconds is an idle-alert threshold, not a start deadline.** Count verified idle time since assignment or the last verified phase end, using host monotonic elapsed time. Persist accumulated time, observation checkpoint/clock epoch, capacity/blocker state and alert-emitted marker per assignment and idle episode. Pause while waiting for capacity or a named blocker; show that wait separately. Persist/deduplicate events by source and event ID and the alert by obligation/episode. After reconnect, replay from the checkpoint; count a gap only if continuous visibility and clock continuity are provable, otherwise mark unknown and resume timing from fresh observations. A duplicate, status chatter or reconnect cannot emit the same alert twice. Alert at the first observed scan at or after threshold. BB delivery sleeps after a serial scan: it guarantees neither a five-second scan interval nor a launch time.

**Evidence through correction.** Retain task, subject and actual environment/path, producer, immutable binding branch/base, review diff base/full head, assignment/result IDs, artifact IDs and hashes, runtime/build identity and all command IDs, raw outputs and terminal receipts. Use BB's existing evidence manifest and explicit required prior findings/failures; native gate/handover JSON is a different contract. A read-only reviewer gets the full current diff and evidence, not executor reasoning. A concrete finding names location, observed failure and closure check. Only findings the owner has authorized for correction return to the original worker by canonical `review`; disputed or scope-changing findings wait. Link correction assignment, superseded head/result, finding IDs and replacement head/checks. Recheck the changed source with the independent reviewer; prior PASS cannot certify the replacement. Acceptance names the latest reviewed assignment/result and exact source; changed integration content needs current gates and review of the change.

**Summary delivery.** Offer the owner at most eight changed obligations and 2 KiB per digest, ordered by decisions, failures, stalls, then ready work. Each row names task/source, actor, elapsed phase, next action and original message/receipt reference; include overflow count and a cursor into the retained history. Coalesce duplicates by obligation. Track display/delivery separately from the owner's explicit mailbox read and decision. Generate on read or existing permitted attention path; do not send a model prompt for each row. Preserve originals even when delivery fails.

**Three separate human decisions.** No blanket correction approval. After a finding, record authenticated human consent naming the exact report/result, finding IDs, source and bounded correction scope before the owner issues the canonical worker assignment. For logical acceptance require separate consent to the exact independent result and the existing owner-only `bb promptobus task accept --task TASK --reviewer REVIEWER --result RESULT_ID` after reading all report parts. For publication require a separate human decision naming repository, expected main and accepted candidate head; retain it with the integrator's grant. A reviewer PASS, logical acceptance or possession of a lease supplies none of the other decisions. Drift invalidates approval for the old tuple.

**Resources.** Assign each concurrent executor its own worktree, output, temp and writable cache. Explicitly grant live-demo operator, host/environment, server/port, writable profile, expiry and teardown evidence. Serialize collisions on the actual shared resource; leave unrelated gates free within approved limits. A stopped grant prevents new starts but does not prove an in-flight writer drained. Hold its lease until confirmed release. Only the designated integrator may publish, one writer per repository main under the clone-root key: compare current main to tested base, fast-forward only, record old/new heads and terminal exit. On base drift prepare and verify again before publishing.

## Verification budget for a future implementation

1. **Deterministic replay first** (fake clock, scheduled observations, no actors). Owner busy through second 180; one reviewer slot, one command slot. A result at 0, last evidence at 2: no start before publication, one start at simulated scan 5 despite duplicate delivery, manual request and reconnect. B becomes eligible at 6; A reports findings and drains at 10, B starts at scan 15 and drains at 20. Verify A's eligible-to-start delay is 3 seconds; B's is 9, including 4 waiting for capacity. These are fixture expectations. At 181 record human consent to A's exact findings; issue a fresh correction assignment, one worker turn and command start/end at 182/185, corrected result and evidence at 186, independent re-review at 190. Expect three reviewer starts, one correction turn, zero dispatch-only owner turns, peak one reviewer and one command. Without consent A stays parked. Race two distinct result IDs for the same assignment: latest before selection wins; one arriving after selection fences stale payload without a second launch. Republish evidence and race manual/auto reservation with one free slot; assert one claim and immutable payload.
2. Replay an idle assignment at 0: no alert at scan 119; one at scan 125 and none on reconnect at 126. Insert a capacity wait from 30 to 80: threshold moves to 170; lose visibility across restart and assert no inferred idle during the gap. Stop before reservation or before final hook: zero starts. Stop after hook but before provider start: one observed start, zero advances, occupied slot through confirmed drain. Lose the launch response; empty and ambiguous attempt lookups must both hold capacity. Inject stale assignment, changed head, delayed old PASS and duplicate receipt; none authorizes acceptance. Compare original message IDs, bodies, artifact bytes and receipt sequence before/after summary delivery; unread set changes only on explicit read. Without publication consent expect no merge; with two approved publication requests assert non-overlapping leases and revalidation of main. A late receipt releases only its own drained operation.
3. **Bounded paired live check, separately authorized.** One manual baseline and one candidate, one disposable local repository per arm seeded from the same full commit, same two small changes, one deliberate correction, same reviewer policy and limits. Record before either arm: full package SHA, installed generation/build digest, actual selected host, BB/SDK/provider versions, task/actor/session, worktree/base/head and effective route. Obtain actual start/end receipts, not planned UUIDs. Hold the owner busy for 60 seconds with an isolated demo resource; compare ready→eligible→start times, gate and review terminal receipts, model starts by role, peak concurrency, original mail and two serial publication records. Limit each arm to 15 minutes and one correction. Stop on identity mismatch, uncertain writer, missing receipt or budget exhaustion; preserve partial evidence. A single paired run tests the handoff, not model capacity or per-role token savings.

Two required cases within that replay:

- Start A with a registered worker and owner, no reviewer and no manifest. Stage a multipart original; inspect each simulated canonical upload from owner to worker, including the ordered IDs returned by the artifact store. Withhold the final part: no manifest publication or launch. Deliver it at second 2, assemble from those receipts, publish, then resolve the IDs from the owner's admission path and the reviewer's bounded assignment. Compare reconstructed bytes, sender, producer and digest to the original. Substitute a missing recipient, out-of-root file, reordered parts or wrong sender: none may produce an eligible handoff.
- Record reservation, attempt ID, SDK spawn, hook decision and actual provider start/end as separate observations. A provisioning request or bootstrap input produces zero turns. For A's corrected head lose the spawn response: lookup by the **new** attempt ID must recover only the second thread. Presenting the first thread's metadata cannot satisfy recovery. Verify no second SDK submission, no bootstrap starts, one assignment start per admitted round and no release from thread discovery alone. Without supported first-turn observations the live check cannot qualify this route.

The 60-second live window tests handoff latency while the owner is busy. Only the replay exercises the 120-second idle alert in this budget. Neither verification has been run.

**Public limits and decision.** BB system input lacks a typed child-outcome subject; `threads.update` cannot atomically cancel a notification already admitted. Final hook validation and later provider start are distinct: a Stop crossing that gap cannot be advertised as an atomic fence. If actual starts or drain cannot be observed for the chosen route, report the live check inconclusive and leave automatic launches disabled there. Do not use private BB APIs, provider transcripts as authority, or global settings. Suppressing routine child-completion wakes is a separate, existing mechanism.

Approve or revise the BB-only transition, idle and latency targets, resource limits and verification budget before implementation. Suggested order: read-only phase projection and replay; owner-scoped reservation and guarded launch; isolated live comparison. Default off, with manual review retained. Independent review of this proposal and the owner's acceptance of scope are still pending.
