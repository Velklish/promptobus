# Contributing

This repository is run entirely through [backslop](https://github.com/Velklish/backslop). There is no issue tracker beside it. Install dependencies with `npm ci`, then run the project copy with `npx --no-install backslop`. The GitHub tag is pinned in `package.json` under `devDependencies.backslop`, and `package-lock.json` records the resolved commit. The `cli` field in `backslop.json` names the local invocation.

The backslop skills and rules for Claude Code, Cursor and Codex (`.claude/skills/backslop-*`, `.cursor/rules/backslop-*`, `.agents/skills/backslop-*`) and `CLAUDE.md` are generated and ignored, so a fresh clone or worktree has none of them. Restore them with `npm ci` and then `npx --no-install backslop init`: `init` keeps `tools` and `hooks` from `backslop.json`. It also writes two tracked outputs, the `AGENTS.md` backslop block and the hook records in `.claude/settings.json`, and leaves both unchanged only while the installed backslop is the pin in `package.json` and `backslop.json` that wrote the committed block — measured at v0.20.0. At another pin it rewrites them ([measured size of that rewrite](#init-rewrite-at-another-pin)). A worker or approver worktree that Promptobus creates needs no manual step, because this checkout's `promptobus.json` declares the same command in `generate` and the lift runs it after `npm ci` ([03-cli § Spawn](../reference/03-cli.md#spawn)).

To update backslop, raise the GitHub tag in `devDependencies.backslop`, run `npm install` to update the lockfile and installed binary, then run `npx --no-install backslop upgrade` and `npm run pins`. Use `upgrade --to X.Y.Z` when the chosen tag is older than the latest release. The local CLI must report the target version before `upgrade` writes files; running it before `npm install` still invokes the old binary and refuses the update.

```bash
npx --no-install backslop status
npx --no-install backslop lint
```

A fresh checkout has no generated adapter output, and `backslop lint` is red without it: run `npx --no-install backslop init --hooks claude` after `npm ci`. The output is untracked, so `git status` does not change, and CI runs the same `init` before its lint step.

The package dependency, lockfile and CI must resolve the same backslop release. `npm run pins` checks those pins and refuses a live command that calls the old `npx github:…/backslop` form instead of the installed binary. It exempts historical references in `CHANGELOG.md`, `docs/adr/**`, task cards, archive task records and journal rows. The tool-owned `docs/archive/README.md` and `docs/archive/LOG.md` header are current instructions and use the local command. The gate reads other tracked files, including those `upgrade` never opens, and runs by hand and in CI before `backslop init`. The order gives a legible failure: CI commits nothing, so an `AGENTS.md` rewritten by `init` at a stale pin disappears with the runner. No CI run has been made to confirm that ordering.

The previous GitHub-form setup had the same blind spot across files. Since v0.8.0, `backslop upgrade` rewrote live Markdown, `package.json` and CI files but not tests. Measured at v0.9.0 → v0.10.0, it changed `backslop.json`, `package.json`, `.github/workflows/ci.yml`, `docs/**` and root `*.md`, and left `test/gate-record.test.mjs` on the old tag. That test pin was raised by hand in the same pass. The historical measurement explains why the separate pin gate remains.

**The gate says what it looked at, and the source pin cannot satisfy its own floor.** Green prints the counts because a pin gate that matched nothing would pass in silence. The old gate printed `43 live pin(s) in 10 file(s), 148 historical pin(s) in 134 record(s) left alone, 41 of them outside backslop.json` at the time of that measurement. It discounted `backslop.json` from the floor: an earlier version counted the config's own `cli` and, when pointed at a ref no other file carried, reported `1 live pin(s) in 1 file(s)` and exited 0. The expected ref now comes from `package.json` and the lockfile; their agreement alone cannot show that the scan reached another live command or pin.

**The gate reads any ref, not only a version.** `#main`, a truncated `#v0.6` and a commit sha are divergences exactly as a wrong version is; an earlier gate that matched only semver passed all three. That mattered because the package test beside it (`test/promptobus-package.test.mjs`) compared the package and CI refs with each other: moving both to `#main` passed that comparison. Measured after widening the old gate, `#main` in `package.json` produced `✖ package.json:27: names github:…/backslop#main, expected #v0.6.0 from backslop.json “cli”`, exit 1. The old gate and package test were complementary. The current pin gate also refuses the obsolete GitHub-form invocation in live instructions.

**A tracked file the gate cannot open is a finding, not a skip.** It cannot vouch for a file it did not read, and a silent skip is the exact shape of the divergence it exists to catch. The summary line therefore counts what was read rather than what `git ls-files` listed: `777 of 777 tracked file(s) read` on a clean tree, `776 of 777` with one file unreadable, and the unreadable path is named above the verdict.

**Write a literal GitHub spec in backticks when documenting a historical run.** The old gate read the ref through whitespace, a quote, a backtick, `)`, `]`, `,` or `;`; a period and a colon were not terminators. A sentence ending `… npx github:…/backslop#v0.6.0.` outside backticks was read as `v0.6.0.` and failed (measured: `✖ docs/ROADMAP.md:18: names github:…/backslop#v0.6.0., expected #v0.6.0`). The closing backtick kept the version boundary unambiguous. A generic `#<version>` or `#<sha>` was not exempted either: the one such definition left the tree when it was folded into the archive journal. The examples here abbreviate the owner segment so they cannot be mistaken for a current project command.

**An example of a wrong ref cannot be written as a live one.** The historical pin gate did not distinguish examples from facts. At the recorded merge it passed 47 then-current live refs and rejected three written-out examples of wrong refs (`#main`, `v0.6.0.`), so the examples above abbreviate the owner segment. The same technique in `scripts/audit-public.mjs` names a forbidden shape without assembling the string.

**Green says what it looked at.** The summary prints `N of M tracked file(s) read`, the count of local calls outside the config and dependency files, and the number of exempt historical GitHub refs left alone. A scan that found no local call must not pass silently. A tracked file it cannot open is a finding, not a skip. The gate reads the expected release from the package dependency rather than carrying a second literal pin, and it preserves the historical records' original commands.

**`npm run probe` keeps four outcomes apart, and three of them are ones a person cannot be trusted to notice by hand.** Red with the mutation and green without it is the only pass. A mutation that changed nothing is a refusal — the probe proved nothing, and that is not green. A check that stays GREEN with the mutation in place is reported as not seeing the file, which is the shape this repository kept finding by eye. A dirty tree is refused before anything is touched, and what is dirty is named. When the mutated run is red but no line of its output names a failing check, the tool warns before the verdict: no failing check was named, and a run that stops before the suite — a build step, a module that fails to load — reads as red. A mutated run that was cut off before its verdicts is refused with exit 2 and is not counted as the red: one killed by a signal, one that exits above 128 — how a shell reports a signal, and how this suite's files and runner exit on one — and one whose output carries, at the start of a line, the suite's abort line (`✖ abort: process exited …`) or the runner's line for a file it took down by a signal or at its timeout or could not start. An indented or mid-line copy is a quote — a report that prints another probe's output — and does not count. Such a run stopped; it did not redden a verdict. The restore comes from a snapshot taken before the mutation, never from git — a git restore is exactly what lost the work the script exists to protect. It runs in a `finally`, so a refusal or a failed spawn with the mutation in place still puts the file back. A SIGINT or SIGTERM sent to the probe while the mutation is in place is held, not obeyed — dying there would skip the `finally` — and the run is then refused as cut off once the file is back; the run is a blocking spawn, so a signal sent to the probe alone takes effect when the run ends, while a terminal's Ctrl-C reaches the run as well. The snapshot holds the content of one file, so `--stdin-patch` asks git how it would apply the patch — `git apply --check --numstat --summary` — and refuses it before applying unless all it does is change the content of the probed file: a patch that touches another file, or deletes, creates, renames, copies or changes the mode of any file, the probed one included, leaves a change the restore cannot undo. Reading only the `---` and `+++` lines misses most of these: a delete names the probed file beside `/dev/null`, a pure rename or copy has neither line, and a mode change sits on headers of its own. `--run` is why it is not a test-only tool: the loss that forced the script into existence happened while probing a GATE, where a refusal inside a test-shaped probe would never have been called. `--run` is shell text, the command a person writes; without it the probed file runs as `node <file>` with its name passed as an argument, never through a shell, where a `$(…)` or a backtick in a file name would run. And `--mutate` takes a JavaScript regexp rather than a `sed` expression, applied in node — `sed -i` differs between BSD and GNU and the suite's own PATH has no `sed` at all, so the first version died `spawnSync sed ENOENT` on three of four cases the moment a check ran it. The separator is arbitrary (`s|…|…|`). A replacement containing the `\n` escape is refused by name and the message names `--stdin-patch`, because `String.replace` writes that escape as a backslash and an `n`, while a replacement that already holds a real newline passes; `$&`, `$1`, `` $` `` and `$'` are warned about and not refused — a person may mean them. The regexp error names only the pattern half, never the separator: `s/x(/a/b/` parses the pattern as `x(/a` and the error blames `( ) | { }`.

<a id="init-rewrite-at-another-pin"></a>Why it matters is an inference, not a measurement. Measured: `init` at a given pin rewrites the `AGENTS.md` backslop block and the adapter output to that version — at v0.6.0 it changed fourteen lines of `AGENTS.md`. Inferred from that: the workflow runs `init` at the pin it names before `npx --no-install backslop lint`, so one left on the old pin would be expected to regenerate the old block on every push and undo the raise. No CI run has been made to confirm it.

**Everything the repository tracks and ships is written in English.** Strings, comments, commit messages, checks, scripts, tests, fixtures, docs, skills, tracker records and the changelog are English, and there is no translated README. `npm run audit` reads every tracked text file and every packed entry for Cyrillic. Cyrillic stays only where it is data rather than prose, and each place says why. The snapshots are named in `AUTHORING_SNAPSHOTS` in [scripts/audit-public.mjs](../../scripts/audit-public.mjs): the transliteration table in `src/protocol.ts`, the journal of closed tasks, a run trace quoted in a card, and the frozen `v0.61` store snapshot. Outside the runtime paths `bin/`, `lib/`, `src/`, `schemas/`, `templates/` and `dist/` — in practice, in tests — a file marks its region with a comment line `english-authoring: input — <reason>` and closes it with `english-authoring: end`; a region in a runtime path is a finding of its own, and the Cyrillic inside it stays one. A region is for a deliberate input whose behaviour depends on its script — a multibyte body that proves a size counts characters, a non-ASCII file name, a pattern for a frozen log line. Ordinary scenario narration, titles, prompts and message bodies are translated, not marked. A region without a reason, a region never closed, and a region or snapshot that no longer excuses any Cyrillic are findings, so the exceptions shrink with what they excuse.

## Roles

| Role | Steps | Must not |
|---|---|---|
| Worker | 1–4: change, document, run gates | Declare the work accepted; move files in `docs/backlog/` or `docs/archive/` |
| Approver | 5–7: review, archive and fold, triage, commit to the main line | Write the worker's code |

One agent may play both roles in order. Under orchestration they are different sessions. The worker commits on the assigned branch and stops.

Procedure text lives in `AGENTS.md` (backslop block) and in the `backslop-task` / `backslop-batch` skills that `backslop init` laid out for the selected adapters.

## Worker path

1. **Take the first queued task** from `status`, or create one:
   - `npx --no-install backslop new <slug> --title "…"` → triage
   - add `--queue` to put it in the queue
   - A tiny change that does not alter a contract may skip a tracker file if one pass finishes it.
2. **Change the code.** Reverse a prior decision by deleting it. Do not strike through. Use [glossary](../GLOSSARY.md) names. If a name is missing, propose a row.
3. **Document in the same pass.** Update the matching [reference](../reference/README.md) section, this guide if the workflow changed, and `CHANGELOG.md`. An architectural choice needs `npx --no-install backslop adr <slug>` and a row in [docs/README.md](../README.md). A changed decision rewrites its existing ADR. A documentation fix carries a check that fails on the old text.
4. **Gates on an unchanged tree.** Commands in `backslop.json` `gates` must exit 0: `npm test`, `npx --no-install backslop lint`, `npm run audit`, `npm run pins` and `npm run codex-schema`. For a committed task branch, run `npx --no-install backslop gates --require-clean --base <base>`, where `<base>` precedes the task take commit. Also run `npm test` when you touch runtime code. The runner puts `promptobus-e2e.test.mjs`, `promptobus-mixed.test.mjs`, `promptobus-cursor-wake.test.mjs`, `promptobus-warden.test.mjs`, `model-routing-preflight.test.mjs`, and `runner.test.mjs` in the serial group because their wall-clock checks or nested pool measure machine neighbours. The serial group does not help when the neighbours are OTHER suites, so the run prints the machine's load average with its own numbers: cores and the load before the pool, the load before the serial group, and for every failed file the load when it started and when it finished. The runner does not judge which assertion is a budget — it cannot see one from the outside, and a hand list of "files with budgets" would rot with no sentinel able to catch it — so the reading is yours, and what the numbers give you is a candidate explanation rather than a verdict. A red whose assertion is a wall-clock budget, beside a load average several times the core count, MAY be a measurement of the machine; the load does not establish that, and the reader owes the evidence. What discharges it is the pair the rules ask for and both halves of it: that file standalone, twice, and the same file on the base commit, with the exit code of each. A green standalone run is a pointer and not an acquittal — the last time this class was followed to its end the pointer held and the cause was not load at all, it was a thirty-second registration window the file had outrun (2026-09-13), and two more reds of the same shape that load explains neither of. A red at a load the machine could carry is yours from the start. A test change needs a mutation probe, and `npm run probe` performs it: `npm run probe -- <file> (--mutate s<sep><js-regexp><sep><replacement><sep>[gi] | --stdin-patch) [--run <command>]` commits-first by refusing on a dirty tree, snapshots the file, applies the mutation, runs the check, restores, and runs it again. Choosing a mutation that is meaningful stays yours, and so does the decision that a gate with an early cutoff needs a second probe feeding it a false positive. What is no longer yours to remember is the order: "commit first" was held by nothing but memory, and a probe over uncommitted work loses it — `git checkout --` takes the edit along with the mutation, which happened three times in two days, twice caught by the author and once reported as done and found by a reviewer.

Before sending the records, run `npm run schema-skew` (`--resolve-from` the directory of the running bus when the copy Node finds from this checkout is not the hoisted one); what it reports, and why it is not a project gate, is in [the gate record](../reference/04-protocol.md#the-gate-record).

Report: what changed, how you verified it (numbers and exit codes), what you left open, findings outside the task. Open a `major` finding outside the task with `npx --no-install backslop new <slug> --parent N --cost major`, then fill its `Evidence:` line. A `minor` finding uses `--minor --evidence "…"`; a `major` or `critical` hypothesis also needs `--cost <level> --hypothesis`. Evidence is required for every minor entry and hypothesis. Do not push. Do not edit the repository's main tree from a worktree.

Commit subject: `PB-N: <what was done>` when the change has a task number.

## Approver path

Review the diff in an approver worktree created from local main. Squash the worker's changes there, run the gates there, then archive, fold and triage in one pass:

```bash
npx --no-install backslop archive N
npx --no-install backslop fold N
```

Between the two, fill `docs/archive/<id>-<slug>/result.md` (outcome, what was done, verification). `[TODO]` in that file fails lint. Do not commit between the two unless the task directory has attachments: squash them into `HEAD` after `archive N`, before `fold N`. `fold N` removes the directory, appends a line to `docs/archive/LOG.md` and prints the definition and the result on stdout as the commit message draft. That message is the body's only storage once the directory leaves the tree, and `npx --no-install backslop show N` finds it by the `PB-N:` subject. Review every `triage/` entry: merge, clarify, `mv N queue`, or `mv N deferred` with a return condition. Ask the owner only before rejecting.

A task without attachments reaches the default branch as one commit; one with attachments reaches it as the attachment squash and the fold-draft commit. For a task without attachments, intermediate worker and review commits are squashed in the approver worktree, and the squashed commit carries the `fold` draft as its message and the acceptance trailer: `git reset --soft <base>`, then `git commit --cleanup=verbatim -F <draft> --trailer "Squash-of: <sha>"`, where `<sha>` is the full sha of the worker head that was squashed — the subject may become `PB-N: closed — …`, the body stays, and `--trailer` appends to the draft rather than replacing it. The trailer is the proof `done` and `sweep` take for a squash whose content was edited while merging — a conflict resolved by hand, a card archived and folded — where neither `merge-tree` nor `patch-id` sees the branch any more ([03-cli § namedBySquash](../reference/03-cli.md#namedbysquash--did-an-acceptance-commit-name-the-branch-head)). It must name the head exactly: a worker commit after the named one keeps the worktree and branch, and an acceptance without the trailer leaves both for the owner to remove by hand. Naming a head discards whatever of it the squash left out — `merge-tree` finding the base without it no longer keeps the branch — so leave out only what the fold draft says was left out. A `fixup` onto the worker's `PB-N:` commit drops the draft and with it the only copy of `result.md`. In the ordinary path, an extra commit between `archive N` and `fold N` would put a revision into the journal line that the final squash discards. Run lint on the final commit, verify the clone root is on main, then publish only with `promptobus lease --as approver:<slug> --task <id> --key <clone root> -- git -C <clone root> merge --ff-only <approver branch>`. If main moved, redo the squash on current main in the approver worktree and rerun gates before retrying. Once the session is stopped and the branch is taken, `sweep` or `done` removes that worktree and branch.

### Local writer rules

The `writer.style` glob selects `lib/cli.js`, but the style pass applies only to its human-facing `helpText` block. Refusal strings and comments elsewhere in that file are outside the style pass. Check their behaviour against code when a changed command makes them relevant.

For a release, the currency ledger also has one row for the CLI help and one row for **every** shipped skill under `skills/`. Each row names the behaviour change it was checked against or says `no change touches it`. Keep the upstream rows for behaviour-changing commits and the style ledger. Releases have no writer task: put both ledgers in the message body of the commit carrying the writer fixes.

For a parenthetical break, use a spaced em dash. Preserve existing em dashes; do not strip them or replace them with hyphens or en dashes.

A release follows [releasing](releasing.md).

## Suite isolation

The suite runs on a machine that is not its own: a person's binaries and sessions are there, and a second `npm test` — a worker run by tracks puts one per worktree — may be going at the same moment. The rules below keep a run from reading or touching anything but itself. Each is enforced by a check, because each was broken in silence first.

**Every sandbox and socket prefix is on the sweep list.** A run that is cut off — Ctrl-C, a file taken down at the file timeout, a crash — never reaches its own cleanup, and the leftovers are removed by the sweep at the start of the next run ([test/tmpdir-sweep.mjs](../../test/tmpdir-sweep.mjs)). Suite sandboxes use the hand-built `SUITE_PREFIXES` list in `$TMPDIR`; a two-way sentinel in `tmpdir-sweep.test.mjs` greps `test/` for every `makeSandbox('…')` and every `mkdtemp` of a temp directory, requires every literal to be covered, and rejects every list entry that covers no literal. The grep takes both spellings of the directory — `os.tmpdir()` and an imported `tmpdir()`, `path.join` and a bare `join` — because while it demanded the qualified one, a file that imported `tmpdir` was invisible to it and its prefix leaked past the sweep with the check green. The same walk also refuses a `mkdtemp` whose first argument is a BARE prefix, by name and file: that is not a temp path at all — Node resolves it against `process.cwd()`, so the directory is made in the checked-out tree, and a bus participant, whose shell cannot write its own worktree, gets `EPERM` and no verdicts from that file. A literal beginning with `/` is an absolute path and passes. The check exists because the fixtures of `tmpdir-sweep.test.mjs` itself did this while the file asserted the opposite of production code four lines above; being absent today is not being impossible. **That sentinel is built in three parts on purpose, and each part is a place it went blind.** The pattern is lifted out of the walk into a named constant, because the walk's own floor comes from the two neighbouring greps: a drift in this one alone would leave the verdict green having examined nothing. The rule that decides a literal IS a defect is lifted out beside it for the same reason — left inline in the loop, no sample can arrive at it, and inverting the predicate emptied the list with the check still green (measured on the shape before that change). And the samples that exercise both are assembled from fragments rather than written out, because this file is itself inside the walk and a sample written whole would be caught by the very sentinel it exists to prove — the technique [scripts/audit-public.mjs](../../scripts/audit-public.mjs) uses on itself. Its verdict carries no floor of its own by design: zero calls examined is the lawful answer today, and the floor is the sample check. Test harness sockets have short paths, so their directories live directly under shared `/tmp`; the runner sweeps their `SOCK_PREFIXES` after the same one-hour cutoff. It writes an owner marker with the run pid as a second line of defence, then probes each aged socket; a live listener or any unknown probe result holds the directory instead of deleting it. Adding a sandbox or socket with a new prefix means adding the prefix; the sentinels say so on the next run.

**Every suite file diverts home at module load.** The runner gives each file of a run its own home, so a run started with `npm test` never touches the operator's. A file run BY HAND has no runner, and that is the case the diversion is for: it applies the shared hygiene list — home, the warden switch, the closed list of inherited names, the `PATH` seal — from [test/home.mjs](../../test/home.mjs), and every `test/*.test.mjs` imports it **before any module that is not a Node built-in**, because one that resolved a home path at load would see the real one. The same boundary removes all four known harness identities before a fixture installs the one it is testing; otherwise a suite run from a participant of another harness presents two identities and turns a foreign-session check into an owner action. A built-in captures nothing, so `node:fs` above the line is not the hazard. The verdict helper [test/check.mjs](../../test/check.mjs) imports it first in turn, so a file that names the helper is covered and needs nothing else. `home.mjs` borrows nothing itself — the sandbox is written out in it rather than taken from `sandbox.mjs`, which statically imports three package modules — and the sentinel checks that too. The apply used to live in the helper, which meant it reached only the files that wanted a verdict printer: the 22 written against `node:test` had nothing, and the two of them that actually wrote under home carried a copy of the diversion each. A sentinel in `tmpdir-sweep.test.mjs` reads the directory and refuses a suite file that imports neither, and checks that the helper really does import the apply point — otherwise "naming the helper is enough" would be a claim rather than a fact.

**A machine-wide read is scoped by something the run owns.** A second `npm test` on the same machine is the normal state — a worker run by tracks starts one per worktree — and per-file sandboxes do not separate two runs in the process table, on a tmux server, or in `/tmp`. Every such read must be qualified by a path, a pid or a mark that belongs to this run alone; a program name is not one. The register of the reads the suite makes today, and what each is scoped by, is in the header of [test/run.mjs](../../test/run.mjs), beside the serial group.

**A check must not depend on how fast the machine is, and the commonest way it comes to depend on that is a single read of a file another process writes.** `promptobus-driver-codex` reddened twice at `load ≈ 40` with **different counters** — `126/140` and `136/139` — and was green twice at `load ≈ 10` and on the base, `186/186` each. The cause was not a timeout budget: seven places read a stand thread file once, `try { JSON.parse(readFileSync(…)) } catch { null }`, while the stand's holder writes it from another process. Under load the reader wins the race, the value is `null`, and the check reports the product wrong; the counters differ between failures because a different read is won each time, which is the signature to recognise. **Two failures with different counters are one defect, not two.** So: a read of anything another process produces goes through `waitFor` with a bounded timeout, the way the rest of the file already did in one place. And when a wait does run out, the failure has to say so — the detail carries `TIMEOUT after <ms> waiting for <file> — the stand had not written the thread; this says nothing about the product`. A red that blames the product for a slow machine is what sends a run off to re-run instead of to read, and re-running until green is how a real regression gets filed as "probably the load". **The same rule applies to a precondition another live process can hold, and there the answer is to wait for it and say so on its own line.** Step 5 of `promptobus-cursor-wake.test.mjs` delivers into a turn in progress; the wake one step above holds the inject lock through its own pauses, and under load it was still holding it when the delivery ran — the refusal then said "already writing into this session" about a neighbour's clock rather than about queueing. So the file waits until no live process holds the lock (the rule `takeLock` itself uses), asserts that on a line of its own, and takes the lock path from production (`lockFile`) instead of spelling it, since a suffix that drifted would make every poll read nothing and the precondition pass on the first one. What such a wait cannot do is close the window: the warden is alive beside the test and may take the lock again between the last poll and the call, so the title claims only what a poll proves — the previous writer let it go before this delivery, not that there is no race. The measured limit of that rule, stated so it is not mistaken for a full answer: the marker reaches the checks whose detail was written to carry it — four of the eighteen that fail when no thread file appears at all. The other fourteen fail downstream of the same absence without naming it. And the reddening itself was **not reproduced**: shortening the wait to zero leaves the file green, because `waitFor` reads once before it checks the deadline and on an idle machine the file is already there. Load was not manufactured — a heavy run on a machine shared with other workers is what this run forbids — so the mechanism rests on reading the code and on an end-to-end probe of the timeout path, not on reproduction.

**The sweep sentinel catches its own authors, which is the argument for having it rather than a convention.** In one night `tmpdir-sweep` reddened on three separate passes: twice on the worker who was editing the suite at the time — once for a sandbox prefix absent from the list, once for a `node:test` file that had not diverted home — and once on another worker. A gate whose usual catch is the next person is worth less than one that catches the person writing it, because that is the person who believes they do not need it.

**The rule covers the scaffolding a worker builds around the suite, not only the suite's own checks — and it was learned that way.** A worker fixing the runner's take-down spent the same day enforcing this rule on `run.mjs` and then broke it in their own tooling: two wait loops of the form `until ! pgrep -f "test/run.mjs"; do sleep 10; done`, started to sleep until their `npm test` finished. `pgrep -f` matches a substring, and the consumer's suite lives at `cli/test/run.mjs`, which contains that substring — so the loops were watching a neighbouring repository's runner and outlived their own run by hours, until the operating system killed them under memory pressure. The mechanism is established; that specific match is the likely cause rather than a measured one. What supports it is which loops died and which did not: every waiter keyed on **a file the worker had created** exited on its own, and exactly the two keyed on **a fragment of a program path** survived. A throwaway one-liner is a machine-wide read like any other, and the person most likely to forget that is the one who has just finished writing the rule down.

**PATH is sealed; an unstubbed binary name resolves to nothing.** Sandboxing `HOME` and `TMPDIR` seals nothing by itself — a child process escapes through `PATH`. The runner hands every suite file a `PATH` of one directory, holding a symlink per binary in `REACHABLE_BINARIES` ([test/hygiene.mjs](../../test/hygiene.mjs)): `ast-grep`, `env`, `git`, `node`, `npm`, `pgrep`, `ps`, `sh`, `sleep`, `tar`. Nothing else is reachable, and in particular no harness binary is — `claude`, `cursor`, `cursor-agent`, `agent`, `codex` and `tmux` are absent on purpose. A file that needs one stubs it (`stubCommand` + `withStubPath` in [test/sandbox.mjs](../../test/sandbox.mjs), which prepend to the sealed value rather than replacing it); a file that forgot gets ENOENT naming the command, which is the outcome the seal exists for. Adding a name to the list means saying in the comment beside it which check needs it.

One consequence to know rather than rediscover: refusal paths that used to reach a real binary now report "not found in `PATH`" under the suite. The Cursor driver's `tmux` resolve is the visible one — it refuses instead of talking to the machine's tmux, which is the intended reading of that branch.

**The environment is closed the same way: a suite file inherits a list of names, not everything minus a list.** The runner builds each file's environment from `INHERITED_VARS` in [test/hygiene.mjs](../../test/hygiene.mjs) — locale, terminal, time zone, the OS user, the temp directory, the Windows system names and `PROMPTOBUS_DOCS_REV` — and `RUN_VARS`, the names the run issues itself: home, the sealed `PATH`, the Claude config directory, the warden switch and the run's three traces, the lease directory, the Cursor install list and the seal marker `PROMPTOBUS_TEST_PATH_SEAL`, which lets a nested apply keep the built seal instead of building a second. Every other ambient name is dropped, and [test/home.mjs](../../test/home.mjs) applies the same filter at module load, so a file run by hand is covered too. The session that starts `npm test` carries whatever its host and its harness put there, and a list of names to drop covers only the names someone has already found. Measured on this repository's suite, run from a bus worker session on 2026-10-04: the environment `npm test` inherited carried `PROMPTOBUS_CURSOR_USER_HOME` pointing at the operator's Cursor home, `findTranscript` in [lib/cursor-persist.js](../../lib/cursor-persist.js) reads under it, and the list of names to drop let it through to every suite file. A tool's location — `GIT_DIR`, `npm_config_userconfig` — and a credential get past such a list the same way. [test/runner.test.mjs](../../test/runner.test.mjs) starts a runner copy with names no list knows — a fictional service's lever and home, a product location override, two tools' locations — and requires that a suite file sees none of them, sees no name off the two lists, and still sees the inherited `TZ`; without that last check an emptied environment would pass as a closed one. macOS writes `__CF_USER_TEXT_ENCODING` into every process it starts, whatever the parent passed, so that name is on the list. A name is added with the reason its value cannot point at a person's state, written beside it. A consumer whose own suite calls its own hooks or services asserts there which of its variables those must not inherit: this suite drops such a variable because no list names it, not because it knows the variable.

**A suite file exits on its own, and a single-file run is protected too.** `node test/<file>.test.mjs` is the form the mutation-probe rule prescribes, and it has no runner above it: no deadline, no child bookkeeping, and no parent to notice. When the session that started it dies, such a file is reparented to `init` and nothing will ever collect it — measured at the end of run 0911e, five orphans at `PPID 1`, all older than the sessions that could have started them, one of them holding a core for two days. The protection is a **watchdog in [test/home.mjs](../../test/home.mjs)**, the helper every suite file already imports, so no file needed an edit: an unref'd timer at 240 s. Unref'd is the mechanism — a file that has FINISHED empties its event loop and exits, and the timer never fires, so a finished file pays nothing for it, while a file still alive at the deadline has by definition a live handle, which `getActiveResourcesInfo()` then names. The number sits below the runner's own 300 s on purpose, so that under `npm test` a file reports what holds it before the runner kills it blind; the runner's deadline is the backstop.

**It is a second ceiling on a file's whole work, and it is not free.** `unref` saves the file that finished and only that one: a file still honestly working at 240 s has a live loop like any other and is taken down too, because the timer cannot tell unfinished work from a leaked handle. The message therefore names both readings rather than accusing the file. The cost differs by form — under `npm test` the ceiling moves from 300 s to 240 s, four fifths, and a file in that band was already failing as "hung", so what changes is 60 s of headroom and a diagnosis in place of a blind kill; run BY HAND there was no ceiling at all and now there is one, which is the honest price of closing the hole. The margin is narrower than the fast case suggests: the slowest file measured alone is 44.5 s, but the header of [test/run.mjs](../../test/run.mjs) records `promptobus-package.test.mjs` at 186.5 s under the pool at load average 8 — 0.78 of this ceiling. A file that legitimately needs longer is split, moved to the serial group, or given a larger `WATCHDOG_MS`. **The limit, stated rather than discovered:** a file spinning inside synchronous work never returns to its event loop and runs no timer of its own, so the watchdog does not catch that shape at all — that is the 100 %-CPU orphan of the measurement, and the same reason `SIGTERM` did not touch it. Only the runner's `SIGKILL` reaches it, and only under a run. What the suite files leave in `$TMPDIR` on a hand run is a different question and is answered by the sweep above, not here.

**A run leaves no process behind.** A file taken down at the deadline goes **with its children**: files are spawned `detached`, so each is its own process-group leader, and the take-down signals the negative pid. A plain `child.kill` reaches one process, and a suite file spawns them by the dozen — the real CLI, git, stub binaries, a nested runner — so whatever it had started was reparented to `init` and stayed; two pairs in the 0911e measurement have exactly that shape, a file and its child runner, both at `PPID 1`. Reproduced and then closed on a fixture in [test/runner.test.mjs](../../test/runner.test.mjs): a file that spawns a marked child and hangs, under a runner copy with a 2 s deadline, left the child alive before the change and leaves nothing after it. The child is found by a mark in its own command line, never by program name — the register rule above.

**Two boundaries of that take-down, named because this section's own rule is to name limits.** A child that started itself `detached` becomes its own process-group leader and is therefore NOT in the file's group: it survives. That is how the warden, the Codex holder and the suite's own long-lived stands start, and it is why the holder gate at the tail of the runner still has something to find. And once files are `detached` they no longer receive a terminal `SIGINT`/`SIGHUP` directly — the take-down now depends entirely on the runner living long enough to relay it, so a runner that is itself hard-killed leaves its files behind. What collects them then is the watchdog above, except in the one shape it admits it cannot catch.

Two further run-level gates at the tail of [test/run.mjs](../../test/run.mjs) watch what a run may LIFT, and they are mirror images. A warden may not be auto-lifted at all, so that gate judges the ACT: the lift point appends a line to the run's warden trace, and any line is a failure. A Codex holder is started on purpose — the Codex file lifts real participants — so its gate judges the MOMENT: the driver appends the pid and the session file at every holder start, and the tail refuses a holder still alive when the run ends, matching the pid against the session file in its live argv because the system reuses process numbers. A holder reaps itself once its session record goes, and the record goes with the run directory, so a red gate means a holder was still holding a live session. Neither gate kills anything; both name what is left.

**The warden gate's boundary is the environment, not the process tree.** Both halves of it are variable names — `PROMPTOBUS_WARDEN=off` is what prevents a lift, `PROMPTOBUS_WARDEN_TRACE` is what records one — so the gate reaches exactly as far as those two names travel. A child that INHERITS its environment is inside the gate for free. A child that COMPOSES one is inside it only because the code composing it names the two, and the participant's MCP server is that second kind: `mcpConfig` in [lib/driver-codex.js](../../lib/driver-codex.js) writes the bus entry's `env` rather than inheriting it. Before the driver forwarded the two names, a warden auto-lifted from a participant's MCP server was neither stopped by the switch nor written to the trace — measured on a live tree, the warden's parent was the MCP server and its environment carried no warden name at all. The gate was green about that process class because the suite lifts no real participant on a real binary (the Codex stand starts no MCP server of its own), not because it covered it. A silent gate is not a slightly weaker gate: it says something false about its own subject, which is why this was fixed rather than noted. The driver now forwards both names when `mcpConfig` finds them set, verbatim and only then — a real run names neither, so nothing there moves, and a live participant still gets the warden it wants. Cursor was measured afterwards and carries the same two names for the same reason: its MCP child's environment is REPLACED, proved by a sentinel that reached the harness process and not that child. Claude MERGES instead — 99 names in that child, workspace credentials among them — so nothing there needs carrying, which is a different answer rather than an open question.

The seal is watched, not assumed. Every command the package launches through `run` is appended to the run's resolve trace ([lib/exec.js](../../lib/exec.js), variable `PROMPTOBUS_EXEC_TRACE`), and the runner refuses a run in which any of those paths lies outside its own run directory. A name that resolved to nothing is not counted — that is the seal working. The boundary is `run` itself: a test file that calls `spawnSync` on its own does not pass through it and is not traced; those calls are `process.execPath` and stub binaries inside the file's own sandbox, and the route the gate exists for is the one through the bus boundary.

## What the stands prove, and what they cannot

**A live measurement without its executing copy recorded is not attributable.** The lift line
and holder journal header record the resolved CLI entry path, the executing Promptobus package
path and version from `import.meta.url`, and the host version separately; the participant binary
version is recorded when the host already read it. A precheck for this class has three parts: the
state under test, the participant home state, and the version and path of the copy that raised the
process. A stand shape or a changed output line cannot substitute for that provenance. A version
without the package path is insufficient when tree and installed copies share a version. These
fields identify a location and reported release, not exact code identity: different revisions at
the same path and version remain indistinguishable. Two consequences for whoever writes the check.
A verdict that runs from the tree and asserts the tree's own path proves nothing about the
discriminator — it is true for any resolution, including a wrong one taken from `cwd`; the copy has
to be run from a second path and name itself. And a header rebuilt from a record that carries no
package field says `unresolved`, never the reading copy's path: a record written by another copy
signed by its reader is the same false attribution in a quieter form.

A harness stand is a stub binary, not the tool. It answers the protocol the driver speaks
and does nothing else, so a check written against one proves the mechanism's half of an
exchange and never the harness's. Where the two are confused, a probe comes back green on
a broken mechanism.

The measured case, because it cost a regression: **the Codex stand records the `cwd` it is
handed on `thread/start` and never enters it.** A working directory that does not exist is
therefore invisible to every check built on that stand — only the real binary would refuse
it. So a property like "the participant's working directory is on disk before the lift"
cannot be asserted through a lifted thread at all; it has to be asserted where the
mechanism creates the directory, which for launch files is the plan. A reviewer's
directory creation lives in that plan; a mutation probe that stayed silent while the
directory was created elsewhere went red once the creation moved there.

The general rule that follows: when a mutation probe leaves the suite green, ask what the
stand observes before concluding the code is unnecessary. Two outcomes are legitimate — the
code is genuinely dead and goes, or the property is real and must be re-expressed where the
suite can see it. "The probe was silent" is not a third one.

**A stand lifts no MCP server at all, so one whole class of difference is invisible to every stand there is.** Whether a name standing on the lift command reaches the process a participant's MCP server runs as is decided by the harness, not by the mechanism, and the three disagree. Measured 2026-09-12, one participant per harness, by `ps eww` on the child scoped by `PROMPTOBUS_ROLE` rather than by program name — every participant runs the same binary: Claude MERGES, and its MCP child carried 99 names including `GITLAB_TOKEN`, which is defined on that machine only in `workspace/.env` and in none of the three zsh rc files, so it can only have come down the lift chain; Codex REPLACES, 11 names; Cursor REPLACES, 9. Cursor is the one that proves the mechanism rather than the count: a sentinel put on the lift command was present on the harness process (103 names) and absent from its MCP child, so the environment is not lost on the way to the harness — it is replaced at the MCP layer. No stand could have shown any of this, and the card that asked for it said so before the measurement rather than after.

The consequence is stated no wider than it was measured. The driver writes fourteen MCP servers into a participant's config and exactly one of them, `promptobus`, carries an `env` block. So a server the driver declares **without** an explicit `env` receives nothing from the workspace on Codex and Cursor and everything on Claude. Whether the mechanism ever relies on that is a second question this measurement does not answer: at the moment of measurement all three harnesses were running exactly one local MCP child each, and none of the other thirteen had started — several are remote or lazily started. The conditional sentence is the finding; "thirteen servers are broken" is not.

**A green check is not evidence until you know what it looked at, and five ways it can look past its subject were measured here.** A check whose expected value is the value the run already carries passes on code that hardcodes it — assert a sentinel the run could not have supplied, not the run's own `PROMPTOBUS_WARDEN_TRACE`. A positive half alone leaves the conditional untested: an unconditional forward writes `undefined`, which a value comparison accepts and only an `in` test rejects, so the negative control belongs in the same check. A comparison across cases can pass on the very code the change replaces — three `self-wake` states already printed three different reasons, so "the three lines differ" was green before the prognosis existed, and only the comparison with `(reason: …)` stripped out measured the conflation. And a fixture every row of which carries the new field never reaches the fallback that reads the state without it: the file looks covered, the branch is unmeasured, and it takes a row built to lack the field to find out. The fifth is the selection itself: a check that picks a participant's line out of `status` and falls back to the whole output on a miss asserts nothing — the regexps find their text on somebody else's line and the check passes having picked nothing, while a negative regexp goes red about a neighbour. Pick the line by the WHOLE address and the `·` separator that follows it, because one address can contain another (`worker:cdx-second` contains `worker:cdx`) and the journal order is not the test's to rely on — `upsertParticipant` moves a touched record to the tail. Fall back to `''` so a miss reddens, and give the miss its own evidence: an empty string in the third argument of `check` says nothing about what the output did hold.

## Inline comments, and moving one into the documentation

An inline comment runs at most two lines. The rule is the owner's, and the reason is measurable: an agent pays for every line of a file header on each read of that file, and again in each new session. `test/comment-length.test.mjs` holds it, as a ratchet — a long run in a file outside its pending list is red, and a file on the list that no longer has one is red too, so the list can only shrink.

### The sweep

**A comment run is the consecutive lines that begin with `//` or `/*`; inside an open `/* … */` it is the lines of the block; strings and template literals are not comments; a comment after code on the same line does not start a run; a line of code or a blank line breaks it.** The threshold is two lines. That definition is shared with the consumer that keeps a length gate of its own, and each repository implements it separately — no code travels between them, because this package does not publish its hygiene (`files` in `package.json`). The one place the two readings part is the interior of an open block: here the bare lines of `/*\n a\n b\n */` are IN the run even when they carry no `*`, because the length gate identifies a run by its own text and a run missing its bare lines is the identity of a different comment; the consumer's line-based lint counts only the lines that carry a marker.

`test/comment-scan.mjs` is a lexer, not a per-line regexp, and it carries its state ACROSS lines: an open block, a string, a template literal with a stack for the `${…}` nested inside it, a regular-expression literal, and the continuation after a `*/` that is followed by more comment on the same line. Each of the five is a place the per-line version went blind, and two are measured rather than imagined: on 2026-09-16 the consumer's copy of this gate, made stateful without regex state, took the backtick inside `/…/` for the start of a template that never closed and stopped seeing 66 blocks — 413 lines — in 10 files; the naive repair, deciding by the previous character alone, then lost 5 more blocks to nested `${…}`.

**What the length gate catches.** A comment run longer than two lines in a file the pending list does not name. A run in a listed file whose text the list does not name — debt swapped rather than paid. A listed run that no longer exists, so the list cannot drift into an allowlist of names nobody checks. The list is a **multiset**: a run listed once and written twice spends one entry and is refused for the other, which is how a copy of an already-allowed block is caught. A tree named in `TREES` that holds no tracked code file is refused too, because a walk that reads nothing reports the same green as a walk that read everything.

**And it says how much it read, for the reason the pin gate and the tmpdir sentinel say it.** A walk that examined nothing fills the same empty lists as a walk that examined everything, and every verdict here is an assertion that a list is EMPTY — so without a floor the two are indistinguishable. Measured on this gate before the floor existed: emptying its walk outright left **11 of 11 verdicts green**. The floor is the count of files judged against the count tracked, and the count of long runs seen against the number the tree is known to carry; the second is a literal and comes down with the ceilings as debt is paid. **A floor is only half of it:** it catches a walk that read nothing and not one that reads every file and judges none, because those counts fill either way. So the walk is a function the checks can call themselves — with a file the list does not name, a listed file the list owes nothing for, a listed file with nothing left, and a name the walk never sees — and each refusal is compared with a count the check computes from the same file rather than with a literal, which catches a branch that collects one entry of seventy-six as well as one that collects none.

**What it does not catch.** It judges `lib/`, `src/` and `bin/`; the rule is repository-wide, and a long comment under `test/` or `scripts/` rests on the author. It says nothing about whether a comment is TRUE, useful, or in the right place — only how long it is. It does not shrink the debt: the pending list is regenerated from the tree when the gate is enabled, and from then on it may only lose entries — **and "only" is held by two literal ceilings in the gate, on the number of listed files and the number of listed runs, because every other check here is satisfied by a list that grew alongside the tree.** Paying debt down means lowering those numbers by hand; raising either one is an edit a reviewer sees in the diff, which is the point of writing them out. **What the ceilings still do not separate is a swap at an unchanged count:** one entry removed and another added leaves both numbers where they were, and the gate reads that as the tree it was handed. Only the diff of the fixture tells sweeping from trading, so a change to that file is read rather than counted. And a division misread as a regular expression — `if (x) /re/.test(s)` — leaves the lexer in code where a regex was meant; that costs nothing unless the regex itself carries a quote or a comment marker. The tokens after which a `/` is read as division are exactly `)`, `]`, `}`, `++` and `--`, plus any identifier, number or literal; `!` is NOT among them, because `!/\s/.test(v)` is prefix negation and `lib/exec.js` writes it, while the postfix TypeScript `x!` appears nowhere in these trees.

**What the link gate catches.** A markdown link inside a comment whose file does not resolve, or whose `#anchor` names no heading. A pointer that a section binds to a symbol, where the comment stands above no declaration and sits inside no symbol, or above a different one — `if (…)`, a bare call and a property are not declarations, and each of the three was accepted by the withdrawn version. A `Source:` line the gate cannot read is a refusal and not a silent skip. Every pointer lands in exactly one counted class and the classes are held against a baseline, so an unchecked pointer cannot arrive quietly. Per-file pointer targets are a **multiset**: removing one of two identical targets in one file is a loss.

**Its own checks are written through the walk, not beside it.** A predicate whose input is built by a walk — what binds a pointer, what declares a symbol, what class a row takes — is exercised through `pointersIn` or `runsOf`, because the shape of that input is decided there and nowhere else. A fixture calling the predicate directly tests the predicate; it does not test the gate, and three review rounds running found the same defect in the seam between the two while every direct fixture stayed green. **That includes every refusal class.** On a green tree each of them is empty by construction, so nothing there would notice the walk giving up on a shape the tree happens not to contain — and refusing is the only thing a gate exists to do.

**What it does not catch, and the two classes it counts without checking.** It checks the BINDING, never the prose: the withdrawn gate's second bad binding was a module contract published as the documentation of `seq` while the comment did stand above `let seq = 0;`, and the rebuilt gate is green on that shape too — a person reading the section is the only check there is. **`fileLevel`, 55 pointers today:** the section's heading is prose rather than a backticked name, so the file is compared and the symbol is not, even where the `Source:` line names one — `docs/guides/install.md` § What the installer knows and never writes is such a section. **`crossFile`, 6 pointers today:** the section describes a different file, and nothing beyond that is compared; the mirror image — the right file under the wrong symbol — would be caught, but the right symbol under the wrong file would not. Both counts are held against the baseline, so neither class can grow in silence, and that is the whole of the guarantee there. A link whose text carries `§` is read as a citation — it sends a reader to a section rather than claiming the section documents the code below — and its symbol is not checked; that is the tree's own convention, and a pointer written in the binding form gets the full check. A pointer added since the baseline is reported as a count and allowed, because the sweep adds pointers by design.

A long block splits three ways: what serves a reader of the documentation moves there, what retells the lines below it or the history of the change goes, and a constraint invisible from the code is cut to two lines. **Losing a fact is not tidying.** A paragraph that was the only carrier of a measurement moves or stays; it does not disappear.

**The Codex protocol fixtures are a citation, and `npm run codex-schema` is what keeps its version tag honest**. The schemas under `test/fixtures/codex-app-server/<version>/` were generated from one binary; the harness now names that directory off `PROVEN_CODEX_VERSION` in `lib/driver-codex.js`, so the constant and the fixtures cannot disagree silently, and `test/codex-fixtures.test.mjs` fails when the constant names a directory that is not there. The remaining gap is the machine: a locally installed `codex` newer than the fixtures leaves the suite green about a protocol nobody speaks any more. `scripts/check-codex-schema.mjs` compares the two and prints the regeneration command; with no `codex` on the machine it says so and exits 0, which is why it sits in `gates` and not in CI — the runner installs no such binary.

**Moving a block changes the base of every relative link in it, and that is the likeliest way to lose content in this work.** A comment in `lib/model-routing/cache.js` writes `](catalog.js)` and `](../store.js)`; the same text in `docs/guides/` must say `](../../lib/model-routing/catalog.js)` and `](../../lib/store.js)`. Resolve each link against the source file's directory and re-relativize against the destination's — pattern matching on the prefix misses the bare forms. Measured 2026-09-12: six links of the shape `](model-routing/cache.js)` survived a prefix-based rewrite and turned both `backslop lint` and `npm run audit` red. Both gates check links, so the failure is loud — but only after the fact, and only because those gates exist.

**The same break happens to the block's pointing words, and there no gate can help.** "read below", "the list below", "the constants above" are deixis: they name a position rather than a thing, and the position is gone the moment the block is. A relative path can be resolved and checked; a word cannot, and `below` is perfectly legitimate in document prose — a gate on it would cry wolf. So the mover WARNS on `below|above|following|earlier` inside a block it is about to move, and the warning goes to the person already looking at that block. Rewrite them to name the thing: "the one field the adapter reads" rather than "what is read below". Measured the same day: two relocated paragraphs had carried theirs across, found by grep after the fact rather than by anything automatic.

**And the loss no gate catches at all: prose that was there and is not.** Length, links, anchors, the build and the whole suite were green through a commit that destroyed six sentences — none of them looks at whether the text that stood in a file still stands somewhere. The damage came from the smallest script of the pass, one written as cosmetic and applied to `lines[i - 1]` without checking what was on that line; care is distributed by how important a step feels, and destructiveness is not. A gate cannot hold this, because it would need each batch's own base commit to compare against. So the script that removes the lines is the one that reports them: after every move it lists any comment line that left the file and cannot be found in the destination, which is the difference between moved and deleted. Proving a batch lost nothing is a set difference — every removed comment line minus every line the pass itself added — never a reading of the diff, because nobody rereads two thousand relocated lines and notices the one that changed mid-sentence.

## Public surface

Do not add internal product names, private package scopes, or links into another repository's `docs/`. Examples in tests and docs use a fictional workspace. `npm run audit` runs `scripts/audit-public.mjs`, which scans tracked files and the packed tarball for forbidden strings and checks tracked links for repository leaks.

**The development tracker stays in this checkout.** The README, the two process skills and the package manifest reach every consumer, and none of them is a place for backslop: its commands, `backslop.json`, its task ids and this guide stay in the source checkout. `npm run audit` builds the real tarball and refuses the word `backslop` and a task id (`PB-` followed by a number, or `PB-N`) in every packed entry. In a packed skill it also refuses any reference to `docs/guides/contributing.md`, `docs/backlog/`, `docs/archive/` or `docs/ROLES.md`. In every other packed entry, including a comment in `lib/`, `src/` or `bin/`, the compiled `dist/` and the README, it refuses those paths unless they follow the release prefix `https://github.com/Velklish/promptobus/blob/v<version>/`. A relative `../docs/guides/contributing.md` from a shipped comment resolves to nothing in the tarball. The rules are in the `Tracker boundary` part of [scripts/audit-public.mjs](../../scripts/audit-public.mjs). They do not read tracked files, because this guide, the cards and `AGENTS.md` are where the tracker belongs. Comments in `lib/`, `src/` and `bin/` and the schema descriptions ship too, so a task id cannot stay in them ([Comments](../../AGENTS.md#comments) already forbids provenance in comments). The README may point a contributor to this guide through that release link. An installed skill may not: the agent that reads it works in the consumer's repository. A packed `package.json` that does not parse is a finding of its own, not a crash of the audit.

**One tracker field ships, and the check names it.** `devDependencies.backslop` stays in the package manifest. `npm ci` installs the tracker from it, `npm run pins` reads it, and consumers install a GitHub release tag, for which npm packs the committed `package.json` unchanged. A git dependency runs only `prepare` and never `prepack` or `postpack` (npm 11.6.2, `pacote/lib/dir.js`). A pack-time rewrite would therefore clean `npm pack` output, which nobody installs, and leave the installed manifest unchanged. Measured with `npm install git+file://<checkout>#<sha>` into an empty project: the installed `package.json` was byte-identical to the committed one, and a committed `prepack` that deleted the field never ran. `MANIFEST_REMAINDER` in the audit exempts that one field path. The same name under `dependencies`, a script that calls the tracker, and any other field that names it are findings. Removing the field needs a release that is not the source tree, either a tagged side commit with its own manifest or a packed tarball as the release asset. That is a change to the release procedure, not to this check.

**The organization's identity is refused everywhere, not only in what ships.** The `ORGANIZATION` list in [scripts/audit-public.mjs](../../scripts/audit-public.mjs) holds the brand — as a word, a camelCase prefix or a snake_case prefix — the organization's team namespace, its service name, its forge group, its tracker ids and its tracker and wiki products. The audit reads it in every tracked text file and every packed entry: tests, scripts, docs, the changelog and tracker records alike, and no directory is exempt. A fixture that needs a repository uses the fictional `demo_team/orders-api`. A detector test that must hold one of these strings builds it from fragments, and no fragment is the brand word alone, because the audit reads that test too. The provenance of an organization integration — its names, reproductions and measurements — stays with the consumer that owns it; evidence here is a neutral scenario.

**A finding that moved here from a consumer's tracker arrives carrying that tracker's names, and they must come off.** Its task identifiers and the name of its internal CLI are exactly what the audit refuses (`origin tracker ids` and `organization brand` in [scripts/audit-public.mjs](../../scripts/audit-public.mjs)), and this repository is public. Keep the provenance in words — whose tracker, what date, that the copy there is archived — rather than as an identifier nobody here can open anyway. The trap is quiet: `backslop lint` says nothing about it, only `audit` goes red, and a pass that skipped the heavy gate learns about it after reporting. Measured on 2026-09-12, twice in one evening from a single import: two cards carried the identifiers and the CLI name into the queue, and a CHANGELOG entry written from one of those cards carried an identifier on to the release notes.

## Documentation links

`test/docs-links.test.mjs` checks every tracked Markdown file. It runs inside `npm test`, so it is not a separate gate. It reads inline links, reference-style links and HTML `href`s, and it ignores that shape inside a fence, an inline code span or an HTML comment. A fence closes only on a line of the same character at least as long as the opening line. A heading anchor is GitHub's slug: punctuation is removed, letters are kept, each space becomes a hyphen, and a repeated heading takes `-1`, then `-2`. The check prints how many files and how many links it read. An empty inventory fails. This section's own [heading][docs-link-section] is one of those anchors.

Each local link is resolved in the source checkout. The same link is also resolved in two delivery layouts: the files `npm pack` ships, launched through the shared process runner so a hung npm stops at 60 seconds, `package.json` included and a file a nested ignore drops left out, and the skill files `promptobus install` copies into `.claude/skills`, `.cursor/skills` and `.codex/skills`. A link that resolves in the checkout and not in a delivery layout is a delivery miss. A repeated reference definition keeps the first destination. A heading inside an HTML comment is not an anchor, and it does not take a duplicate suffix. A badge's image and its outer destination are both links.

Links from a consumer document into `docs/backlog/` or `docs/archive/`, and links from one onto a file that exists but is not tracked, are task dependencies. Consumer documents are `README.md`, `skills/`, `docs/` other than the backlog and the archive, and the `[Unreleased]` section of `CHANGELOG.md`. The backlog, the archive and released changelog sections are not consumer documents. Today's task dependencies and delivery misses are the list in [test/fixtures/docs-links-baseline.json](../../test/fixtures/docs-links-baseline.json). A violation that is not listed fails, and a listed violation that no longer occurs fails, so the baseline can only shrink.

`npm run docs-links:external` requests each `http` and `https` URL outside CI. A response of 401, 403 or 429, a 5xx response, and a transport failure are `unverified`. They are not dead links and they are not a pass. A 404 or 410 is dead. The command exits 0 only when every URL is confirmed.
