# PB-419.19 · Reject Cursor delivery on unreadable pane

- **Scope:** [Drivers reference](../../reference/05-drivers.md)
- **Created:** 2026-11-05
- **Dependencies:** none
- **Cost:** major

<!-- quality-audit-import:2026-11-05:PB/PQA-109 -->

## Context

Evidence: `lib/cursor-persist.ts:389-414` maps a failed tmux capture to null and then to an empty input string. `clearInput` and `waitInput` at `:551-567` treat that as an empty field; `injectText` can return `ok: true` if subsequent commands succeed. `lib/driver-cursor.ts:490-495` publishes activity on that result. An audit probe using extracted functions and fake tmux/filesystem returned `ok:true` with both capture calls failing and other commands succeeding (exit 0). It did not exercise a real Cursor session or demonstrate delivery loss.

## Work to do

Carry the distinction between an empty field and an unreadable pane through clear and wait operations. Refuse delivery or confirmation on failed capture without changing the independent missing-session behavior.

## Acceptance criteria

- Regressions for failure of the initial capture and a later capture after Enter return `ok:false`.
- Existing successful and stuck-input cases continue to pass, and failed capture cannot publish a successful activity.

## Verification

After implementation run `npm run build` and `node test/promptobus-driver-cursor.test.mjs` from the repository root; **notRun**.

Additional audit-proposed checks, **notRun**: `node --test test/promptobus-driver-cursor.test.mjs`.

## Dependencies and limits

None. Actual tmux failure frequency and live delivery impact were not measured; live Cursor testing is outside this evidence.
