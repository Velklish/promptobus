# PB-161.4 · A Codex participant cannot use the bus at all: every MCP tool call dies on a declined elicitation

- **Scope:** `lib/codex-session.js` (`decideApproval`, `SERVER_REQUESTS`), `test/codex-elicitation.test.mjs`, [03-cli](../../reference/03-cli.md) § The Codex holder
- **Created:** 2026-09-12
- **Dependencies:** none

## Context

Found while running the PB-161.3 measurement, on a live Codex reviewer — not by reading. The
reviewer did its job correctly and **could not deliver the result**. It said so itself, in its
final message:

> Delivery to the orchestrator was attempted twice, but the Promptobus MCP calls were rejected
> by the environment.

**Every** bus call of that turn failed. Four calls, four identical failures, from the holder
log (`codex-cli 0.146.0`, 2026-09-12):

```
21:57:56.429 event item/started mcp promptobus-promptobus/promptobus_mailbox inProgress
21:57:56.433 approval deny mcpServer/elicitation/request the participant has no person to
             answer an elicitation server=promptobus-promptobus mode=form id=0
21:57:56.436 event item/completed mcp promptobus-promptobus/promptobus_mailbox failed
             {"message":"user rejected MCP tool call"}
```

and the same at `id=1`, `id=2` (mailbox) and `id=3` — the `promptobus_send` carrying the
report. From the session rollout, the body that was lost:

```json
{"type":"mcp_tool_call_end","invocation":{"server":"promptobus-promptobus",
 "tool":"promptobus_send","arguments":{"to":"orchestrator","type":"result",
 "body":"PB1613-MARKER-7F3A9C2E\nNo findings.\nChecked the full snapshot, …"}},
 "result":{"Err":"user rejected MCP tool call"}}
```

The mechanism is one line. `decideApproval` (`lib/codex-session.js:785`) answers
`mcpServer/elicitation/request` with `{ allow: false, why: 'the participant has no person to
answer an elicitation' }`, unconditionally, for both roles. The decline is correct as a
judgement — there really is no person — but its consequence is not what the code assumes.
`test/codex-elicitation.test.mjs` opens with "the holder declines
`mcpServer/elicitation/request` **so the turn continues**". The turn does continue; the TOOL
CALL does not. The participant's only channel to the bus is dead, in silence, on every call.

**This is a regression with a known author, not a new defect: PB-41 removed a hang and put a
lost report in its place.** That line was written to close PB-41, where on 2026-09-06 two
Codex reviewers in a row HUNG after `approval allow mcpServer/elicitation/request` — the
permission was being asked of a person, and a background session has none. The trade was a
hang for a silent loss, and the loss is quieter than the hang was: a hung reviewer is visible,
a reviewer that finishes a turn having delivered nothing looks like a reviewer with nothing to
say. The orchestration skill still forbids lifting a Codex reviewer because of PB-41, and the
condition for lifting that ban was "PB-41 closed, verified live". **This run is that live
verification, and it failed.**

**Why the suite is green about it.** Every check on this path is written against the Codex
stand, which is a stub app-server: it never issues an elicitation, so the decline never has a
consequence to observe. `codex-elicitation.test.mjs` asserts the decision function returns
`allow: false` and nothing about what happens to the call afterwards. This is the same shape
the contributing guide already warns about under "What the stands prove, and what they cannot":
the stand proves the mechanism's half of the exchange and never the harness's.

**The sender IS established, and it is not this package.** Measured 2026-09-12, free — no
model, no paid turn. The bus MCP server was started exactly as the participant's
`config.toml` starts it (same command, same four environment variables), driven by a scripted
JSON-RPC client that **declares the elicitation capability**, so a server wanting one is free
to ask. Through `initialize`, `tools/list` and a real `tools/call` of `promptobus_send`:

```
initialize ok · server: {"name":"promptobus","version":"0.6.0"}
tools: promptobus_send, promptobus_mailbox, promptobus_task
tools/call reply isError= false
tools/call text: "sent result → orchestrator · … address=reviewer:subject"

=== server→client requests during initialize + tools/list + tools/call: 0 ===
  the promptobus MCP server issued NO elicitation and NO other server→client request
```

The call succeeded and the message landed in the task journal. So the server neither elicits
nor needs to, and the `mcpServer/elicitation/request` that killed four calls — logged with
`server=promptobus-promptobus` — **originates in codex-cli**, which attributes it to that
server while asking something of its own. That matches the shape of a per-call approval for an
MCP tool, and it agrees with PB-41's own history: what hung there was `approval allow` on the
same method, which is what an approval question does when nobody answers it.

**What remains NOT established:** what codex-cli is asking. The elicitation's fields are
deliberately unlogged — the log carries only allowlisted fields, which is right and stays — so
the message itself was never written down. "Per-call MCP approval" is the reading the evidence
fits, not a measured fact, and nothing should be built on it until the next item settles it.

## Work to do

- Settle what codex-cli asks. Log the elicitation's allowlisted shape fields at the decline
  point — `mode`, `serverName`, whether a `requestedSchema` is present — which is a line of
  code and one live turn, or read it out of codex-cli 0.146.0's own app-server protocol, which
  costs nothing.
- If it is a per-call approval: the decline must become an ACCEPT for the mechanism's own
  servers, which are pre-approved by construction — a participant's MCP set comes from its own
  disposable `CODEX_HOME` and nothing else is in it (ADR-007). A blanket decline of a channel
  that also carries approvals is what turns "no person to ask" into "no bus". The decline must
  stay for anything that is genuinely a question to a person, which is what PB-41 was about,
  so the split has to be by what is being asked and not by the method name.
- Whatever the decision, the check must move to where the consequence is visible: today's
  check asserts the return value of `decideApproval`, and the defect lives one step later, in
  what the call does after the decline.
- Re-measure with a live participant afterwards, and treat it as the live verification PB-41's
  closure was owed. This one cannot be proven on the stand, and saying so is part of the fix.
- Phase 3.5 of the parity run — lifting the orchestration skill's ban on a Codex reviewer —
  stays blocked until that re-measurement is green.

## Out of scope

- The elicitation redaction itself. Not logging a server's prompt text is right and stays;
  what this card wants is the shape, not the message.
- PB-161.3's own question, which this run answered separately and positively.

## Verification

- A live Codex participant sends a `result` through `promptobus_send` and it arrives in the
  task journal — shown by the journal, not by the absence of an error.
- A check that fails when the bus call dies, rather than one that passes because the decision
  function returned `false`.

## Weight

If this reproduces beyond this stand, a Codex worker cannot report either: `promptobus_send`
is the same tool on the same server. The parity effort's premise is that a Codex participant
is a participant; a participant that cannot reach the bus is not one. Worth confirming before
anything else in the Codex track is measured.
