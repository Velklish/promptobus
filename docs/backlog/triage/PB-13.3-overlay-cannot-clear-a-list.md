# PB-13.3 · An overlay can replace a deny list but never clear one

- **Scope:** [03-cli](../../reference/03-cli.md)
- **Created:** 2026-09-05
- **Dependencies:** PB-12, PB-13

## Context

Finding from the PB-13 review. Allow and deny lists merge by replacing the named selector kind whole, so a higher layer states what the rule is instead of adding to a list it cannot see. What no layer can do is remove a rule: there is no way to write "deny nothing".

Three things close that door together, and each is verified:

- `schemas/model-routing/overlay.schema.json` gives `selectors` `"minProperties": 1` and `nameList` `"minItems": 1`, so `deny: {}` and `deny: { models: [] }` are both refused. The schema says so in its own words: "An empty list is a shape error, not 'allow nothing'";
- `validate` refuses the same two documents — `test/model-routing-catalog.test.mjs`, the cases `empty rule` and `empty name list`;
- the reference check requires every denied name to exist in the merged catalog, so `deny: { models: ["nothing-real"] }` is not a way round it either.

The consequence: a ban written by a lower layer survives every file above it that does not name that same selector kind. **For a consumer policy layer that is the behaviour the first consumer wants** — a product ships a ban and it holds whatever a person writes in their workspace file. For a person who wants to try one model their consumer forbids in one repository, it is a wall with no key, and ADR-003 argues the workspace layer sits above the consumer layer precisely so that a person can override the product. Both readings are defensible; today only the first is implemented, and nothing in the contract says which was intended.

This is the trade-off, not a bug: nothing is broken and no run misbehaves. What is missing is the decision.

## Work to do

- Decide whether an overlay should be able to reset a list. If yes, the shape is a schema change to `overlay.schema.json` — a sentinel such as `deny: { models: null }`, or an explicit `reset: ["deny.models"]` — and that file is PB-12's, with the supersede cost that carries.
- Whichever way it goes, ADR-003's sentence about the workspace layer overriding the consumer layer needs to agree with the code: today it can override a ban only by replacing it with another ban.
- [guides/model-routing.md](../../guides/model-routing.md) already states the current behaviour and points here; it changes with the decision.

## Out of scope

- Making deny lists accumulate across layers. That is the other direction and it makes the wall higher, not lower.
- Anything about allow/deny that the resolver does — PB-18 reads the merged lists and does not care how they got there.

## Verification

- If a reset is added: an overlay above a layer that denied a model lifts that ban, `validate` accepts the document, and the decision output attributes the lift to the right layer id.
- If not: the reference says plainly that a ban is final from below, so nobody reads ADR-003's ordering sentence as a promise it does not keep.
