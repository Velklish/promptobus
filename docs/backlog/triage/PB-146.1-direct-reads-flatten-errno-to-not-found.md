# PB-146.1 · Direct task and artifact metadata reads flatten every filesystem read failure into not-found, so EACCES or EIO reads as absence

- **Scope:** `src/v1/store.ts` (`readTask`), `src/v1/artifacts.ts` (`readArtifact`), `src/v1/errors.ts`, [04-protocol](../../reference/04-protocol.md) § Artifacts
- **Created:** 2026-09-09
- **Dependencies:** PB-146

## Context

Finding of `worker:s-store` while implementing PB-146 (run `pb-run-0909-t20260909-132344`), from the source, not measured. `src/v1/store.ts:126-130` wraps the task metadata read in a `catch` that inspects no errno and always raises `task-not-found`; `src/v1/artifacts.ts:202-205` does the same for `artifact-not-found`. A read that fails with `EACCES`, `EIO` or any errno other than `ENOENT` is therefore answered as "the record does not exist", the same flattening PB-66 removed from the mailbox and intent reads. PB-146's "Out of scope" states that direct callers already receive the right code; they do not for a non-`ENOENT` read.

Hypothesis, to verify with a fixture: `chmod 000` on `task.json`, then `readTask` → `task-not-found` instead of a refusal naming the errno.

## Work to do

- Reserve `task-not-found` / `artifact-not-found` for `ENOENT`; classify or propagate any other read errno with the errno named (the PB-66 seam pattern: separate the read from the parse).
- Deterministic fault-injection tests for both readers, one `ENOENT` and one non-`ENOENT` case each.
- State the rule beside the PB-146 taxonomy in 04-protocol.

## Out of scope

- The bulk `listTasks` taxonomy and unparseable artifact metadata — PB-146.
