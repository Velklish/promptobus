# PB-234.2 · A field added to a record schema cannot be sent until the package is released, so the run that adds it cannot exercise it

- **Scope:** [04-protocol § The handover record](../../reference/04-protocol.md#the-handover-record)
- **Created:** 2026-09-17
- **Dependencies:** none

## Context

The `send` check reads the schema from the **installed** promptobus package, while the worker
edits the schema in its **checkout**. The two are different files, and `additionalProperties:
false` makes the gap a refusal rather than a warning.

Measured on 2026-09-17 while closing PB-234, which adds `mutationProbe.expected` to
`schemas/v1/handover-record.schema.json`. The worker's own handover record carried the new
field — the natural first user of it — and the bus refused the send:

> `«handover-pb234.json» does not match schemas/v1/handover-record.schema.json, so it is not
> the evidence its name claims: /checks/mutationProbe: matches 0 of 2 allowed shapes, expected
> exactly one; /checks/mutationProbe/expected: field the schema does not define.`

Both sides, read the same minute:

| schema read by | `mutationProbe.expected` defined | `additionalProperties` |
| --- | --- | --- |
| the branch, `schemas/v1/handover-record.schema.json` | yes | `false` |
| the running bus, `node_modules/promptobus@0.12.1/schemas/v1/…` | no | `false` |

The same document validates clean against the branch schema through `schemaErrors` and is
refused by the bus. Neither reader is wrong; they are reading different files.

This is the mirror of the compatibility direction PB-234 was told to protect. That one — an
OLD record reaching a NEW reader — is handled: the field is optional and two suites send a
record without it. This one is a NEW record reaching an OLD reader, and `additionalProperties:
false` is what turns it into a refusal. The strictness is deliberate and earns its keep
elsewhere (the record has no free-text seam, and that is asserted), so the finding is not
"relax it" — it is that the seam has a consequence nobody has written down.

The practical cost, in the order it bites:

1. The run that adds a field cannot use it. Its own hand-off must be written in the previous
   shape, so the first record to exercise a new field is one written after a release.
2. The gap is silent until the send. Nothing in the gates notices: the branch's own suite
   validates against the branch's schema and is green.
3. What is refused is the evidence, at the moment of handing it over — the most expensive
   place to discover a version skew, because the work is already done.

## Work to do

- Decide what a new field in a published record schema means here, and write the answer where
  a person adding one will read it — `04-protocol.md` for the two records, or the contributing
  guide if the rule is general. The options are not equal and the owner should pick: accept the
  skew and say so ("a field lands in the release after the one that adds it"); bump
  `schemaVersion` on any field addition, which an older reader already refuses by `const`, so
  it trades a confusing refusal for a clear one; or let an unknown field under `mutationProbe`
  pass while every other node stays closed, which buys forward compatibility at the price of
  the guarantee that nothing free-text rides along.
- Whichever is chosen, a gate would catch the skew before the send: compare the schema files
  the checkout ships against the ones the installed package ships, and say which records the
  running bus would refuse. That is cheap — both are JSON files on disk.

## Out of scope

- The `mutationProbe.expected` change of PB-234 itself. It is complete, its gates are green,
  and its handover record was sent in the shape the running bus accepts.
- Changing `additionalProperties: false` on its own. That guarantee is asserted by
  `test/handover-record.test.mjs` and is not the defect here; how a field is ADDED is.

## Verification

- A person adding a field to a published record schema finds, in the document they are editing
  or the guide they follow, what release their field can first be sent in.
- If the gate is built: it is red on a checkout whose record schemas differ from the installed
  package's in a way the bus would refuse, and green when they agree.
