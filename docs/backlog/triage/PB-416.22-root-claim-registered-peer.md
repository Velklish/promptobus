## Context

During the approved recovery, the actual BB session already held `peer:bb-controller-kwv32` in root task `tdm-20261109-installed-r4`. One shipping public `promptobus_mailbox` call with `claim: true` and that explicit task returned `claim is for the orchestrator address: this call reads peer:bb-controller-kwv32`. The helper exited 1 on its owner postcondition. The result carried neither a JSON-RPC error nor an `isError` flag. Root owner, all four unread refs, 294 canonical message hashes, child owners and native fields remained unchanged; no Stop or update followed.

Evidence: controller artifacts `/private/tmp/tdm-20261109/successor-thr_kwv32nzn42/root-takeover-refusal.json`, `root-takeover-before.json`, `root-takeover-after.json`; `src/mcp/server.ts` resolves the held mailbox before dispatching claim, and `lib/store.ts` `mailboxAddress` selects the single held peer over the declared orchestrator role. This is separate from the telemetry repair and access-snapshot guard recorded in PB-416.20.

The actual owner explicitly approved root takeover in a completed question, forwarded by the relinquished parent. The exact answer is retained in the controller's private `actual-owner-root-takeover-grant.json`. The grant permits ONLY-root old owner to actual BB owner takeover despite live processes, root unread-to-history with preserved bodies/IDs, caller binding, and normal join/warden effects including a possible model turn and an exception to the documented ended-owner precondition. It does not permit child claims, identity/role edits, peer unlink, internal claim calls or direct driver Stop. The source repair is separately authorized for preparation only: no merge, publish, install or live use.

- Preserve existing identity, recorded-owner, child, alias and other-held-address refusals; keep the existing owner mutation, history, binding and join implementation.
- Document the exception in Claim, the CLI owner route, ADR-028 and the unreleased changelog.
