# PB-66.1 · An unreadable mailbox ref keeps unread at one forever, so the warden knocks until the filesystem condition clears and nothing bounds the retries

- **Scope:** `src/v1/messages.ts` (`readInbox`, `countInbox`, `glanceInbox`), `src/supervisor.ts` (the re-knock on `stale && !busy`), [04-protocol](../../reference/04-protocol.md) § Message types
- **Created:** 2026-09-09
- **Dependencies:** PB-66

## Context

Finding of the PB-66 review (isolated reviewer, run `pb-run-0909-t20260909-132344`), stated from the source, not measured. After PB-66 a non-`ENOENT` read or rename refusal on one mailbox ref is reported in `broken` and the ref stays in the inbox for a later read. Nothing bounds how many later reads: `countInbox` counts file names without reading them (`src/v1/messages.ts`, the `readdirSync` count), so an unreadable ref keeps `unread ≥ 1`; the warden re-knocks on `stale && !busy` every `KNOCK_RETRY_SEC` (`src/supervisor.ts`, the retry branch); `glanceInbox` skips the unreadable record silently (its `catch { continue; }`), so the postcard says "unread 1" with an empty preview; the participant fetches the mailbox, takes nothing, and the cycle repeats until the filesystem condition is lifted. Before PB-66 `readInbox` threw on the same refusal, so the loop existed and was worse; PB-66 documents that a knock repeats until the condition clears but does not bound it.

Hypothesis, to verify with a fixture: a permanent non-`ENOENT` refusal (a ref whose mode stays 000, or a directory where a file is expected) produces one knock per `KNOCK_RETRY_SEC` for the life of the task, with an empty preview each time.

## Work to do

- Decide the policy (owner): after N consecutive refusals of one ref name, treat it as corruption and isolate it into `broken/<participant>` with the errno as `code`, or keep the retry unbounded and make the postcard say why the count does not drain (the errno and the name). The first is a data-affecting decision — an isolated ref is no longer delivered — and belongs to the owner, not to a worker.
- Implement the chosen policy with a test that drives the refusal past the bound and asserts the terminal state (isolated with the errno, or the postcard text).
- State the rule in 04-protocol beside the PB-66 sentence.

## Out of scope

- The PB-66 repair itself (report and continue) — landed.
- `peekInbox` / `glanceInbox` swallowing read errors without a note — a separate entry if wanted.

## Verification

- Test: a ref that refuses N+1 reads ends in the terminal state the policy names; a ref that refuses N reads and then succeeds is delivered normally.
