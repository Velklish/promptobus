# PB-139.1 · lib/ has no type net: @ts-check on the dist boundary needs its own tsconfig and a gate

- **Scope:** `lib/*.js`, `lib/model-routing/*.js`, `tsconfig.json` (or a new `tsconfig.lib.json`), the gate command list
- **Created:** 2026-09-17
- **Dependencies:** none

## Context

PB-139's first pass marked 19 `lib/*.js` files that import from `../dist` with a `// @ts-check` first line, meant as a lightweight boundary-safety net against a silent break from a `src/` export rename. Reviewed against the actual tree: the marker is checked by no gate — `tsconfig.json`'s `include` stays `["src"]`, and nothing in `scripts/` or `package.json`'s `test`/`build` scripts runs `tsc` over `lib/`. `// @ts-check` only does anything inside an editor's TypeScript language service or an explicit `checkJs` compiler run; neither happens in CI or in `npm test`.

Measured: `npx tsc --ignoreConfig --noEmit --allowJs --target es2022 --module nodenext --moduleResolution nodenext --skipLibCheck lib/*.js lib/model-routing/*.js` → exit 1, 1605 diagnostics across the marked files. Top counts: `store.js` 258, `review.js` 235, `spawn.js` 132, `models.js` 129, `resolver.js` 117, `telemetry.js` 114, `guard.js` 107. So the marker was never actually clean on any of these files — it advertised a guarantee nobody had verified.

Separately, the file list itself had drifted: `grep -rl '\.\./dist' lib` today also names `driver-claude.js`, `driver-codex.js`, `cli.js`, `contract.js`, `approver.js`, `sweep.js`, `stop.js`, `harness-registry.js`, and `lib/model-routing/cache.js`, none of which carried the marker — the boundary PB-139 drew no longer matches which files actually cross it.

PB-139's second pass (2026-09-17) removed `// @ts-check` from all 19 files rather than leave a false guarantee in place; this finding is the follow-up on whether and how to build a REAL gate.

## Work to do

- Decide the shape of a real check, one of:
  - a separate `tsconfig.lib.json` with `allowJs: true`, `checkJs: true`, `noEmit: true`, explicit `include` naming the boundary files (kept in sync with `grep -rl '\.\./dist' lib`), wired into a `package.json` script and into `scripts/`'s gate list; first-pass error count against the current tree is unknown and must be measured before committing to zero-error as the bar — likely in the same 1000+ range as the unscoped measurement above, disproportionate to fix in one pass;
  - or per-file JSDoc typing tight enough that `@ts-check` is actually meaningful for that one file, taken up file by file rather than as a 19-file sweep.
- Whichever shape is picked, re-derive the file list from `grep -rl '\.\./dist' lib` at the time of the fix, not from PB-139's original enumeration.

## Out of scope

- Reintroducing `// @ts-check` without a gate that runs it — that is exactly the defect this finding documents.
- A full `checkJs` pass with a zero-error bar in one step — the diagnostic count is unbounded until measured against the actual chosen `tsconfig.lib.json` shape.

## Verification

- Whichever gate is built: a documented command, in the gate list, exit 0 on the tree it ships with.
