# PB-15.7 · The Claude adapter's event-loop check measures the machine, not the probe

- **Scope:** `test/model-routing-adapter-claude.test.mjs`
- **Created:** 2026-09-05
- **Dependencies:** none

## Context

Found by the routing track while adding the same check to the two neighbouring adapters (PB-16.2).

`the probe does not block the event loop, so the preflight budget can still fire` asserts a fixed wall-clock threshold: a timer set for 20 ms beside a ~400 ms probe must have fired by 250 ms (`assert.ok(tickedAt !== null && tickedAt < 250, …)`). The property under test is that other work runs while the probe is in flight; the threshold measures how loaded the machine is.

Measured on 2026-09-05: the same shape, added to `test/model-routing-adapter-codex.test.mjs`, went red in a full `npm test` run — `a timer set for 20 ms fired at 760 ms while a 1457 ms probe ran` — while passing every time the file was run alone. The file is in the runner's pool, which is where the load comes from. The two new checks were rewritten to count ticks of a 20 ms interval instead (`ticks >= 5`): a blocked loop fires an interval once however long the block, because node coalesces the periods it missed, so the count separates the two cases without a stopwatch. The Claude check kept its original form — it is PB-15's, it was green in that run, and rewriting it was outside the task.

It is a latent flake, not a wrong check: on an idle machine the timer fires at ~20 ms and the threshold is a twelvefold margin. On a loaded one it can exceed 250 ms with the adapter behaving perfectly.

## Work to do

- Bring the Claude check to the same tick-counting shape as the Cursor and Codex ones, so all three measure the same property the same way.

## Out of scope

- The adapter itself. Nothing about the probe is in question — the check is green on the behaviour it is about.

## Verification

- The rewritten check green under a full `npm test` (where the file runs in the pool) and red on the file's own documented mutation probe: put `run()` from `lib/exec.js` back in place of the spawn.
