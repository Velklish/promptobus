# PB-33.1 · `models --clear-exhausted` says the next run probes, and the next run reads the cache

- **Scope:** `lib/models.js` (the `--clear-exhausted` success message), [03-cli](../../reference/03-cli.md) § Model routing
- **Created:** 2026-09-06
- **Dependencies:** none

## Context

`promptobus models --clear-exhausted <harness>` removes the harness's whole cache entry and reports:

```text
✔ codex: the exhaustion mark is cleared — the next run probes it again (<cacheFile>)
```

The next run does not probe. `models` reads the cache and asks no harness anything — that is the command's own documented rule, and `--refresh` is the only flag that probes — and `spawn` and `review` take the cache too unless `--refresh` is passed. With the entry gone, the harness comes back `unknown` / `stale_cache`, its candidates lose the ten `unknown-availability` points, and under `balance` they are not paced at all. So the clear does not put the harness back in contention until somebody probes; the message says it already has.

Measured on 2026-09-06 in a throwaway workspace with a diverted `HOME`, the shipped catalog and the suite's `balance-snapshot.json` fixture with its stamps moved onto the run clock, codex staged `exhausted` / `manual_exhaustion` with no reset:

```text
$ promptobus models --clear-exhausted codex
✔ codex: the exhaustion mark is cleared — the next run probes it again (…/model-routing/cache.json)

$ promptobus models --strategy balance --role worker      # no --refresh
  codex   unknown    tier unknown
chosen: claude-opus-medium · claude / claude-opus-5 medium · score 74.25
  ! snapshot-stale: codex was answered from a cache entry past its TTL and no probe ran
```

The harness entry left in the cache after the clear is `null`, confirmed by reading `cacheFile` directly.

The behaviour is right — a clear should not start a probe of its own, for the same reason `models` does not. It is the sentence that is wrong: it describes a run that probes as though it were the next run of any kind.

## Work to do

- Reword the success message so it names the probe rather than promising it — for example, "the mark is cleared; `promptobus models --refresh` re-reads the harness, and until then it counts as unknown".
- Check the neighbouring exhaustion messages for the same shape while the file is open: `manual_exhaustion` in the reason-code table already says only `--clear-exhausted` may clear it, and says nothing about what happens after.
- If the wording changes, the [03-cli](../../reference/03-cli.md) sentence "`models --clear-exhausted <harness>` drops an exhaustion the cache is holding with no known reset" gains the same clause, so the command page and the command agree.

## Out of scope

- Making the clear probe. That would put the preflight budget on a command whose whole point is that it costs nothing, and it is the opposite of the rule `models` keeps.
- The epoch stamp the `snapshot-stale` line prints for a cleared entry — that is PB-33.2.

## Verification

- The message names `--refresh` (or another probing command) rather than "the next run".
- A suite check pins the new string, as the neighbouring messages are pinned.
