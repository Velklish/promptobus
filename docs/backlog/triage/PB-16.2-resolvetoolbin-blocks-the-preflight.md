# PB-16.2 · A synchronous `resolveToolBin` blocks the preflight budget timer and every neighbouring adapter

- **Scope:** [03-cli](../../reference/03-cli.md)
- **Created:** 2026-09-05
- **Dependencies:** PB-14

## Context

Found in review of PB-16, and it belongs to the host contract rather than to any one adapter.

`PromptobusHost.resolveToolBin(name)` ([src/host.ts](../../../src/host.ts), `HostToolBin`) is **synchronous**, and a host is free to start a process inside it. This package says its own does: [lib/driver-cursor.js](../../../lib/driver-cursor.js) lines 936–938 —

```js
// Search WITHOUT a version probe: `resolveToolBin` asks `--version` with a 15 s
// ceiling, and version fitness was confirmed at lift — there is no reason to ask
// again at stop.
```

The preflight ([lib/model-routing/preflight.js](../../../lib/model-routing/preflight.js) lines 164–175) starts every adapter at once and races them against a single `setTimeout` budget:

```js
const started = harnesses.map((harness) => Promise.resolve()
  .then(() => adapterFor(harness).probe({ host, timeoutMs: budgetMs, refresh }))
  …
let timer = null;
const budget = new Promise((resolve) => { timer = setTimeout(resolve, budgetMs); });
await Promise.race([Promise.all(started), budget]);
```

Both halves live on one event loop. A `resolveToolBin` that blocks it — `spawnSync` with a 15 s ceiling is the shape this repository already describes — stops the budget timer from firing, stops the two neighbouring adapters from making progress, and stops each adapter's own kill timer. The 15 s ceiling the person was promised then becomes 15 s per blocking resolve, in series, and the mechanism that was supposed to cap it cannot run while it is blocked.

**This is not one adapter's bug.** PB-16 moved its deadline to the first line of `probe`, before the resolve, so the budget at least *covers* the resolve; it cannot make a synchronous call yield. PB-15 (Claude) and PB-17 (Codex) call `resolveToolBin` the same way and have the same exposure — no adapter can fix it from its own side.

What is verified: the synchronous signature, the comment naming a 15 s `--version` ceiling, the single-event-loop race in `runProbes`, and that all three adapters call resolve from inside `probe`. What is not: that any shipped host actually blocks for a measurable time — this package's standalone host answers `{ ok: true, bin: name }` with no process at all ([src/standalone.ts](../../../src/standalone.ts) line 262), so the suite would not see it.

## Work to do

- Measure it before changing anything: a stand-in host whose `resolveToolBin` blocks for two seconds, three adapters under one budget, and the wall clock of the whole preflight against the budget. If the numbers show the budget holding, close this — the concern is then only theoretical.
- If they do not, choose where the fix belongs, and it is one of two places, not both:
  - the **contract** — an async or promise-returning `resolveToolBin`, which every host implementation must then follow, and which is a breaking change to `PromptobusHost`;
  - the **preflight** — resolve every harness's binary once, before the adapters start, and hand each `probe` the `HostToolBin` it needs in `ProbeRequest`. That keeps the host contract as it is, makes one resolve per harness instead of one per probe, and takes the call out of the race entirely.
- Whichever lands, say in `docs/reference/03-cli.md` § Availability what an adapter may and may not do on the event loop, because today nothing does.

## Out of scope

- The per-adapter deadline. PB-16 already starts it before its resolve, and PB-15 and PB-17 can do the same; that bounds the accounting, not the blocking.
- Making `resolveToolBin` itself cheaper or cached. That is a host's own business and does not remove the hazard from a host that chooses to probe.

## Verification

- The measured preflight wall clock with a deliberately blocking stand-in host, before and after, in the task result.
- A check that the whole preflight finishes within its budget even when one host resolve blocks — the check that reddens if the fix is reverted.
