# PB-16.1 · The Cursor start path names no limit, so a late-start exhaustion cannot be classified

- **Scope:** [03-cli](../../reference/03-cli.md)
- **Created:** 2026-09-05
- **Dependencies:** PB-16
- **Cost:** minor

## Context

Filed while doing PB-16, whose "Work to do" asked for the PB-14 late-start hook: *"Late-start quota errors from the driver's start path update the cache"*. It is not implemented for Cursor, and the reason is not an omission — **there is no signal to hook.**

The whole Cursor start path is `spawn()` in [lib/driver-cursor.js](../../../lib/driver-cursor.js) calling `liftSession()` in [lib/cursor-persist.js](../../../lib/cursor-persist.js). The only text `spawn` gets back on failure is `lifted.error`, and it is one of two strings the package composes itself:

```text
pty provider pane did not lift: <tmux stderr>
persist session did not appear in the tmux list. That is how a binary refuse before start
looks (wrong model id, expired login), and a launch from inside a foreign TMUX — then
persist silently lifts an ordinary non-persistent agent
```

Neither carries harness output. `liftSession` kills the launch pane without a `capture-pane`, so whatever the binary drew is gone by the time the driver can look at it, and the transcript is no help either — `readTranscript` keeps `turn_ended.status` and no reason text, and it is not the start path in any case. The driver already says this in its own words in `stallRoute`: *"A wrong model id and an expired Cursor login look the same"*.

So a `markExhausted` hooked to the generic string would fire on a **typo in `--model`** as readily as on a spent limit, and it would fire the sticky kind — `manual_exhaustion`, which nothing but `--clear-exhausted` lifts. A false permanent exhaustion of the whole Cursor harness is worse than no classification, so PB-16 shipped none and said so in its `### Cursor` subsection of the CLI reference. The orchestrator confirmed that choice on 2026-09-05.

What is verified: the two strings, the missing capture, the transcript shape, and that `cursor-agent` has no limit or usage command at all (`cursor-agent status` and `cursor-agent models` were the only two the PB-16 inventory found, measured on 2026.09.02-c22c1a3). What is not: what a limit-hit Cursor account actually prints, because nobody has had one to look at.

## Work to do

- Measure it first. On an account whose limit is actually spent, capture `cursor-agent -p '<trivial prompt>'` and an `agent persist` launch, and record the exit code and the exact text — including whether a reset time is named, since that is what separates `subscription_exhausted` from the sticky `manual_exhaustion`. Without this measurement there is nothing to write a pattern against, and a pattern guessed from another harness is how a false exhaustion gets shipped.
- Then choose the route. Two exist:
  - a `capture-pane` in `liftSession` before the launch pane is killed, so the failure text reaches `spawn` at all — the pane is the only place a pre-start refusal is drawn;
  - a short `cursor-agent -p` probe on the failure path, which costs a second process on a path that has already failed and needs no pane.
- Hook whichever lands to `markExhausted`, and keep the generic lift failure unhooked: it must stay a plain refusal, because a wrong model id arrives through it.

## Out of scope

- The availability adapter itself (PB-16, closed). A limit is not visible to `status` or `models` either, which is why a healthy Cursor probe is `quota_unknown`.
- Liveness of a running participant — PB-7.
- The two neighbouring drivers' late-start hooks. Claude Code and Codex have limit text of their own and are not blocked by this.

## Verification

- The measured transcript of a limit-hit account in the task result, secrets redacted — this is the evidence the whole entry waits on.
- A test on stubbed start-path output: the measured limit text marks the harness exhausted with the reset when one is named, and the generic "did not appear in the tmux list" string marks nothing.
