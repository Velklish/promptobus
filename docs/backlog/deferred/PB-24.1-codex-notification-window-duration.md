# PB-24.1 · The Codex notification fallback names no window duration, so that path now reports no window

- **Scope:** `lib/model-routing/adapter-codex.js`, `test/harness-codex.mjs`, [03-cli](../../reference/03-cli.md)
- **Created:** 2026-09-06
- **Dependencies:** PB-24

## Context

ADR-004 makes `lengthSec` required on a window: without it there is no pace, and a window with no length is dropped by the cache projection on the way to disk — invisibly. So `rateLimitWindows` (PB-24, N1) leaves out a window whose duration the payload does not state, rather than giving it one the harness never said.

The Codex adapter has two limit sources. `account/rateLimits/read` states `windowDurationMins` on both windows — measured on codex-cli 0.146.0, and that is the ordinary path. The **notification fallback** — `account/rateLimits/updated`, taken when a binary does not have the request ([03-cli](../../reference/03-cli.md) § Codex availability) — carries the snapshot flat, and the shape the suite's stand-in models carries **no duration at all** (`test/harness-codex.mjs`, the `unsupported` and `flat` flags).

So on that path the harness now reports no window. What it costs is bounded and is not a wrong answer: the verdict is unchanged, the account is still `available`, and an exhaustion keeps its reset, because that comes from `reachedResetAt(snap)` and not from the window list — the test beside it says so. What is lost is the pace: `remaining` is unknown for that harness, every one of its candidates takes the `unknown-availability` penalty, and the cache entry ages at the one-hour auth TTL rather than the sixty-second window one.

**The open question is what a real notification payload contains**, and this entry is a hypothesis rather than a claim: the spike of 2026-09-06 recorded the shape of the request's answer and not of the notification's, and the stand-in was written before the duration mattered. Two outcomes:

- the real payload **does** carry `windowDurationMins` (or a field the duration can be read from) — then the adapter reads it, the stand-in is corrected to match, and the window comes back on that path;
- it **does not** — then no window is the honest answer, and 03-cli should say so where it describes the fallback, so the next reader does not take it for a bug.

## Work to do

- Capture a real `account/rateLimits/updated` payload from a binary that lacks `account/rateLimits/read`, or establish from the app-server protocol that the notification carries no duration.
- If a duration is there: read it in `rateLimitWindows`, and give the stand-in the same field so the suite stops modelling a shape the harness does not send.
- If it is not: add a sentence to the Codex subsection of 03-cli — on the notification path the limit is a percentage with no window, so the harness is penalised as `unknown` rather than paced.

## Out of scope

- Deriving the length from the window id. `primary` is the session window by app-server's own naming, and that is why the adapter states its `kind`; the length is a number the harness states, and ADR-004 forbids deriving one from the other.

## Verification

- Either a window with a `lengthSec` comes back on the fallback path, with the captured payload recorded in the result; or 03-cli says the fallback yields no window, and the test that pins it names the reason.

## Deferred

- **Deferred:** 2026-09-06
- **Reason:** the notification path (`account/rateLimits/updated`) was never captured live; the request path carries `windowDurationMins` and is what the adapter reads today, so nothing in 0.4.0 waits on this.
- **Return condition:** a captured `account/rateLimits/updated` payload from a live Codex session (the driver's log can record one) — then either the adapter reads the duration from it or 03-cli says the notification path has no window.
