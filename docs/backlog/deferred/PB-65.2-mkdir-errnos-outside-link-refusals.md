# PB-65.2 · A stray file at a store directory path (EEXIST, ENOTDIR) or a read-only or full volume (EROFS, ENOSPC) on the recipient-directory mkdir still escapes classification, and EEXIST cannot simply join LINK_REFUSALS
- **Scope:** `src/v1/artifacts.ts` (`LINK_REFUSALS`, `linkFailure`), `src/v1/messages.ts` (`linkOnce`), [04-protocol](../../reference/04-protocol.md) § Engine
- **Created:** 2026-09-10
- **Dependencies:** PB-65.1

## Context

Finding of the PB-65.1 review (isolated reviewer, run `pb-run-0910-t20260910-085454`), from the source. PB-65.1 classifies a refusal on creating the recipient inbox directory through `linkFailure`, whose list `LINK_REFUSALS` (`src/v1/artifacts.ts:164`: EXDEV, ENOTSUP, EOPNOTSUPP, EPERM, EACCES, EMLINK) was drawn for a hard link and left unchanged by the card's decision. The refusals most likely on a `mkdir` are not in it: `EROFS` (a read-only volume), `ENOSPC` (a full one), and — measured by the orchestrator on Node 25.2.1 — `EEXIST` when a file sits where the inbox directory must be and `ENOTDIR` when it sits deeper on the path. All four escape `recoverTask` as raw errnos, and `recover()` at `bus()` open still takes every store command down for them — loudly now, where a shared `catch` would have read the mkdir `EEXIST` as "ref already placed" and dropped the intent in silence, but the crash class PB-65.1 was opened for. The same holds for the link itself, where PB-65 left the list narrow on purpose. Hypothesis, not measured: a store on a read-only volume, or with a stray file at `inbox/<participant>`, plus one open intent makes `status`, `history` and `prune` exit 1 after PB-65.1.

**A trap for the repair:** `EEXIST` cannot simply join `LINK_REFUSALS`. The `EEXIST → return false` branch of the link half of `linkOnce` is what makes recovery idempotent, and `materialize` (`src/v1/messages.ts`, around line 259) reads the raw code beside the list — the comment at `src/v1/artifacts.ts:161-165` warns of exactly this for `ENOENT`. The directory half needs its own classification, not a wider shared list. Also in view: a `mkdir` `ENOENT` (a path component removed in a race) would read in `materialize` as "a neighbour materialized first" and answer `intent is gone and there is no canon` for a live intent — retryable, no loss, unmeasured.

## Work to do

- Decide (owner) whether the directory half of `linkOnce` gets its own classification — `EROFS`, `ENOSPC`, `EEXIST`, `ENOTDIR` on the mkdir become `link-refused` (or a code of their own) with the errno named, a retry being the right answer for a volume that comes back writable and a refusal the right answer for a stray file — or whether the taxonomy stays as PB-65 drew it and 04-protocol says which errnos are classified on each half.
- If it does: a regression per errno through a fault seam (a new `mkdir` point beside the `ref` step), the way PB-66's seams inject errnos portably; `LINK_REFUSALS` itself untouched; one sentence in 04-protocol § Engine.
