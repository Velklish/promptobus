# PB-373.19 · Prove the OpenCode external_directory grant on the real binary with the owner's data directory

- **Scope:** [05. Drivers](../../reference/05-drivers.md)
- **Created:** 2026-10-28
- **Dependencies:** none
- **Parent:** PB-373.17
- **Cost:** major

## Context

Finding discovered while working on PB-373.17.

PB-373.17 gives an OpenCode lift a config grant for `external_directory` on its declared roots and answers a covered ask after the first prompt; its verification ran on a no-model stub holder only, by design. Evidence: the PB-373.17 acceptance records no OpenCode launch (worker result and approver result, 2026-10-28). The real OpenCode 2.0.20 binary has not yet run a lift with the new config, so whether the binary honours `permission.external_directory["<root>/*"] = "allow"` is read from its bundled schema, not observed.

A live run needs the owner's OpenCode data directory: an empty data directory has no subscription login, and the binary then falls back to a free model, which the owner does not allow.

## Work to do

- With the owner's consent and their data directory, lift one OpenCode worker on `opencode-go/minimax-m3` whose first prompt reads a file inside a declared root outside the session cwd; record that no `external_directory` ask appears, the turn reaches idle with tokens, and `status` never says `turn running` while an ask is pending.
- Record one ask outside the declared roots and confirm the lift fails naming it.

## Out of scope

- Changing the driver; this card measures it.

## Verification

- The holder journal and `opencode stats` of the live run show a completed model turn with no pending permission ask for the declared root, and the outside-root case fails by name; commands, exit codes and versions are recorded in the result.

## Deferred

- **Reason:** needs the owner's consent to run OpenCode with their own data directory; nobody else can provide the subscription login.
- **Return condition:** the owner allows one live OpenCode run with their data directory.
