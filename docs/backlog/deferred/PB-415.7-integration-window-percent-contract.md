# PB-415.7 · Represent unknown routing-window usage honestly in the public integration declaration

- **Scope:** [Host integration entry point](../../reference/02-host.md), [Routing windows](../../guides/model-routing.md)
- **Created:** 2026-10-30
- **Dependencies:** none
- **Cost:** major
- **Parent:** PB-415.4

## Context

Found while preparing the integration declaration migration. The existing public RoutingWindow promises usedPercent: number, while a cached OpenCode local-estimate window can retain unknown usage. The integration runtime copies that undefined value into its report; JSON serialization omits it. The declaration allows a consumer to call usedPercent.toFixed() without proving a number.

Evidence: static audit at 6af7809cebd785510d93e3347b88708b96f49c5c followed adapter-opencode.ts's missing-allowance branch, cache.ts windowOf, preflight.ts dryRun/retainedReadings and integration.js windowOf/routingDiagnosis to integration.d.ts RoutingWindow. `git diff --numstat 4503555d9b007bf8b78f4f2bef963b15bb2c2563 HEAD -- lib/integration.js lib/integration.d.ts` exited 0 with no output: the runtime and public declaration match the original baseline. model-routing-adapter-opencode.test.mjs already checks an accepted local-estimate window without usedPercent; the existing integration fixture does not cover that cache case. No public runtime reproduction or live account probe was run in this audit.

A valid schemaVersion 2 cached window has id and model scope, kind session, positive lengthSec, estimate local-estimate and resetAt null, with no usedPercent. routingDiagnosis reads the cache with dryRun true and refresh false, and retains its windows even when stale. This is a pre-existing public declaration mismatch. The language-only migration must keep its accurate implementation types distinct from the compatibility declaration rather than silently filling unknown usage with zero or asserting the raw report to a false shape.

## Work to do

- At an explicitly selected public-contract boundary, represent unknown usedPercent honestly and update affected consumer type assumptions. Preserve runtime window values and unknown usage semantics.
- Add a public integration fixture with an accepted cached estimate lacking a percentage, plus a TypeScript consumer check that requires narrowing before number operations.
- Remove the legacy compatibility declaration only with the corresponding consumer handover; keep this baseline finding visible until that change is accepted.

## Out of scope

- Changing quota estimates, model selection, account probing policy or the shared service architecture.

## Verification

- Reproduce the public report on the original contract with an isolated cache and no external model turn. Record command, source identity and result separately from the static audit above.
- The corrected declaration admits both measured and unknown usage; a consumer cannot call number-only methods on an unknown percentage without narrowing. Existing measured-window reports stay compatible in value.
- Required gates and independent review pass; the consumer handover names the declaration change explicitly.
