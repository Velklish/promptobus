# PB-390.2 · Verify child cleanup when abort fixture process discovery fails

- **Scope:** [Live smoke fixtures](../../reference/02-host.md), abort setup and child ownership
- **Created:** 2026-10-20
- **Parent:** PB-390
- **Cost:** major (hypothesis)

## Evidence

Finding discovered while working on PB-390.

Evidence: test/live-run.test.mjs:164-171 spawns a detached child before run.child can throw; restricted failure was observed, surviving child identity was not measured

At `c0184c4b89346ae4a72462229e44f430da51b100`, the generated abort fixture installs its abort hook after `run.child`, which queries the process table. A discovery error can therefore precede the hook. The original restricted run failed at this boundary, but it did not retain a child PID/birth identity; a surviving original process is not established and must not be guessed from a global name or prefix.

Next step: a controlled fake-only fault probe captures its own child identity, injects a discovery failure before registration and checks child death. If it demonstrates a leak, register direct owned-child cleanup before the failing operation and retain the regression case. Preserve the original unknown and never use global process cleanup as the remedy.
