## Context

It is not a demonstrated defect in BB message delivery. Sending a Hold through an asynchronous mailbox does not prove that its recipient read or applied it.

The previous recipient subsequently performed closure and both final lint commands, then reported that it read the Hold messages only after those commands. Its final report explicitly says it did not read the active-slot record immediately before either lint.

Exact lint start/end timestamps were not recorded: actual overlap with the next actor, interference and an effect on gate validity remain unproved.

Authenticated receipts: final result `20261009T000620871-0333-98fca5` and artifact `20261009T000620757-0331-aa0e7f` preserve the recipient's disclosure and command evidence. Proceed, Hold and reassignment messages are retained in the private run packet. That packet preserves actual argv, exits, final source comparison and tracker closure; no raw receipt was rewritten. ## Work to do

- State the release contract in the BB orchestration and participant instructions. A release identifies the completed command scope and confirms that no further mechanical calls from that grant remain. A runner-only release does not authorize a later closure lint.
- Publish the exact command scope, authenticated actor, authorization identity and owner confirmation in one canonical task. Persist the matching active-slot authorization before dispatch can activate the participant. Do not require a later confirmation message or bind authorization only after delivering the runnable task. Record the returned task id for audit without creating a second execution barrier.
- Treat a completed release as terminal for that grant. A delayed confirmation or a resume must not revive it; remaining authorized work receives a fresh complete grant. State this in both orchestrator and approver instructions so acceptance can advance without repeated confirmation turns.
- Require the participant to check current control/STOP and that the active slot belongs to its authenticated identity immediately before every mechanical call. An earlier mailbox grant is insufficient when current ownership has changed.
- Require explicit release acknowledgment before reallocating the slot. If revocation is needed while the actor is active or its command scope is uncertain, use the official task-owned participant stop/pause route and verify the actual state before reassignment, preserving its worktree and receipts.
- Put all required preconditions in the initial exact command grant, including live account routing before each substantial suite invocation. A changed precondition sent during a running batch takes effect only after acknowledged application; use verified stop/pause when continuation under the old conditions is unacceptable. Cached quota must not be reported as a fresh routing receipt.
- Preserve actual commands, exits and receipt limitations. Do not repeat unchanged mandatory suites solely because of delayed Hold delivery when there is no demonstrated interference or incomplete required receipt.

## Verification

- A deterministic coordination fixture delays Hold delivery after Proceed. The old contract permits reassignment without a release; the corrected contract keeps the slot until release or verified stop/pause.
- Reproduce the BS-236 event order with controlled message delivery: preparation task, participant release with zero commands, then delayed owner confirmation. Assert that the released authorization never executes a command. A fresh grant with actor/authorization prebound before dispatch starts its authorized preparation without a second confirmation turn, including when the participant reads the task immediately.
- Check the orchestrator and approver instruction contract against the old separate-confirmation requirement quoted above. The check must fail on that requirement and pass on the complete initial grant; do not accept a regression test that checks only the operator's disposable recovery script.
- A runner-only release cannot implicitly grant closure lint. An actor that reads stale Proceed refuses a new mechanical call when current ownership differs or STOP is present.
- Record actual call start/end and release/stop acknowledgment in the fixture; do not infer overlap from commit timestamps.
- Verify that only task-owned participants are affected, and that source, worktrees and raw evidence are preserved. Run mandatory repository gates on the accepted implementation SHA.
