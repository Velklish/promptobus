# PB-225.1 · The approver is outside the attachment contract on both sides

- **Scope:** `lib/approver.js` (the approver preamble), `lib/review.js` (`worktreeOwner`, the review subject), [03-cli](../../reference/03-cli.md) § Review
- **Created:** 2026-09-17
- **Dependencies:** `PB-225` closed the same gap for the worker
- **Previous order:** 490
- **Cost:** minor

## Context

Round-1 review of `PB-225`, 2026-09-16. `PB-225` made the review subject list every file the
reviewed address attached — name, type and time — and put the same sentence, one shared
constant, into the reviewer subject and the worker preamble. The approver was left out of both
halves of that, and neither half is an oversight the change could have covered in passing.

The preamble side: the approver's hand-off text asks for a gate record and for overflow as an
artifact, and says nothing about what a reviewer will be shown. It does not carry
`ATTACHMENT_CONTRACT`, so an approver attaching evidence has no stated reason to expect it in
anyone's subject.

The subject side: an approver lift sets its session working directory to the clone root, not to a
worktree.

<!-- quote:../../../lib/approver.js -->
    cwd: cloneRoot,
<!-- /quote -->

The reviewed address of a subject is resolved by matching the target directory against the
participants' recorded worktrees, and a participant with no `worktree` owns nothing.

<!-- quote:../../../lib/review.js -->
export function worktreeOwner(taskMeta, repoDir) {
  return (taskMeta.participants ?? [])
    .find((p) => p.metadata.worktree && canonical(p.metadata.worktree) === repoDir) ?? null;
}
<!-- /quote -->

So a review whose subject is an approver's own hand-off resolves no owner, takes the third branch
of the attachment block — "this subject is not a participant worktree" — and lists nothing. That
an approver hand-off is a lawful review subject is already stated in the reviewer's own preamble,
which tells the reviewer that a missing handover record is expected there rather than a gap:

<!-- quote:../../../lib/review.js -->
      + 'absence is expected rather than a gap is an approver\'s hand-off: the record is the WORKER\'s, and an '
<!-- /quote -->

The gap is not hypothetical in shape: the same run's task files folder carries
`gates-approver-*.json` files, so approvers do attach records that a subject would have to name.

> Source: `reviewer:t11`, round-1 report of 2026-09-16 on branch
> `worktree-promptobus-run-0916-t11-t20260916-130945`, minor finding on `lib/approver.js`.

## Work to do

- Decide whether "the reviewed address" extends to an approver at all. The candidate resolution is
  by `metadata.repoAbs` for a participant in the approver role, the way `worktree` resolves one for
  a worker — that is a widening of `worktreeOwner`, or a second resolver beside it, and it touches
  who a subject belongs to, so it is a decision rather than a patch.
- If it does: give the approver preamble the same `ATTACHMENT_CONTRACT` sentence the worker
  preamble carries, from the same constant, so the two sides still cannot drift.
- If it does not: say so where the approver is asked for its gate record, so an approver knows its
  attachments are not shown and does not attach evidence expecting them to be.

## Out of scope

- Changing where an approver session works. The clone root is `ADR-015`'s decision, not this
  finding's.
- Anything about the worker or reviewer sides of the contract: `PB-225` closed those.

## Verification

- A lifted reviewer whose subject is an approver's hand-off either names that approver's attached
  files with name, type and time, or the approver preamble states that they are not shown; the test
  asserts the sentence, and the mutation probe that removes it reddens exactly that assertion.
