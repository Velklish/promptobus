# PB-406.3 · Routing weighs each harness's subscription plan and an owner-declared capacity, and live caps per harness live in the overlay

- **Scope:** [03. CLI § Model routing](../../reference/03-cli.md#model-routing)
- **Created:** 2026-10-28
- **Dependencies:** PB-406.1
- **Parent:** PB-406
- **Cost:** major
- **Taken:** 2026-10-28

## Context

Finding discovered while working on PB-406. Evidence: adapters already read a plan (`rateLimitTier` for Claude, `planType` for Codex, the included amount for Cursor) but the resolver and catalog never use it (03-cli § Availability: "an input to no score"); the overlay's `account.<harness>.plan` is display-only; `caps.liveParticipants` exists but is empty by default. A consumer kept a cap of two Codex participants in its own rules after a measurement on a smaller plan, and the owner had to lift it to six by hand on 2026-10-28.

## Work to do

- An overlay field `account.<harness>.capacity` per window kind: a relative weight the owner sets (for example "Codex weekly is 4× the Claude weekly"); pace and remaining are scaled by it, so 1 % of a large plan counts more than 1 % of a small one. Without it, keep today's behaviour.
- Use the plan the adapter reports to pick a documented default capacity where one is known, and show plan and capacity in `models`.
- Move per-harness live caps to `caps.liveParticipants.<harness>` in the overlay, enforced at lift with a refusal that names the cap and the overlay file; document that consumer rules should set the overlay instead of their own counts.

## Out of scope

- Fetching absolute request quotas from vendors that do not publish them.

## Verification

- Two harnesses at the same `usedPercent` with capacities 1 and 4: `balance` prefers the larger one; a test fails on the current code.
- With `caps.liveParticipants.codex: 6`, a seventh live Codex lift is refused naming the cap; the sixth is not.
