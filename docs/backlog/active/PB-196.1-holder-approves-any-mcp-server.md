# PB-196.1 · The Codex holder accepts a tool-call elicitation from any MCP server, not only the ones the mechanism configured

- **Scope:** [05-drivers](../../reference/05-drivers.md), `lib/codex-session.js`
- **Created:** 2026-09-25
- **Dependencies:** none
- **Cost:** major
- **Previous order:** 260
- **Taken:** 2026-09-25

## Context

Finding discovered while working on PB-196.
Evidence: a no-turn measurement on `codex-cli 0.156.1`, 2026-09-25. A participant home of the shape the driver builds — a copy of `auth.json` and a `config.toml` with the trust entry and the mechanism's MCP entry — starts a built-in MCP server, `codex_apps`: `mcpServerStatus/list` after `thread/start` reports it connected with 52 tools, among them account-writing ones (`sites.delete_site`, `sites.deploy_site_version`, `sites.update_environment_variables`, `sites.create_source_repository_write_credential`, `plugin_management.uninstall_app`). The source is the `apps` feature, stable and on; the same home with `[features] apps = false` lists no server at all. PB-196 turns the feature off in the participant home, which closes this one server.

The holder's rule for an elicitation is still server-blind. A tool-call approval is recognised by its kind, its mode and its schema, and never by the server that asks:

<!-- quote:../../../lib/codex-session.js -->
function isToolCallApproval(params) {
  if (!params || typeof params !== 'object' || Array.isArray(params)) return false;
  if (approvalKind(params) !== MCP_TOOL_CALL_KIND) return false;
  // Upstream applies the schema test inside the Form arm; a URL elicitation is a different
  // variant and carries no schema at all, so the mode is part of the proof, not a detail.
  if (params.mode !== 'form') return false;
  return messageOnlySchema(params);
}
<!-- /quote -->

and a recognised one is allowed for every role:

<!-- quote:../../../lib/codex-session.js -->
    if (isToolCallApproval(params)) return { allow: true };
<!-- /quote -->

So any MCP server the binary adds to a participant — a built-in one, or one a future feature brings — gets its tool calls approved without a person. Assumption, not measured: that a `codex_apps` tool call reaches the holder as such an elicitation at all; no turn was spent to find out.

## Work to do

- Allow a tool-call elicitation only when it names a server the mechanism configured for that participant; refuse the rest with a reason, as the other refusals do.
- Say in the drivers reference which servers a Codex participant may have approved.

## Out of scope

- Turning the `apps` feature off — PB-196 carries it.

## Verification

- A holder test where a tool-call elicitation from an unconfigured server is refused and one from the mechanism's server is allowed.
- A mutation probe: the server check removed turns that test red.
