# PB-161.4 · A Codex participant loses every bus call to codex-cli's own per-call MCP approval, which the holder declines as if it were a person's question

- **Order:** 10
- **Scope:** `lib/codex-session.js` (`decideApproval`, `approvalReply`, `serverRequestSummary`),
  `test/codex-elicitation.test.mjs`, [03-cli](../../reference/03-cli.md) § Review and
  § The Codex holder
- **Created:** 2026-09-12
- **Dependencies:** none
- **Taken:** 2026-09-12

## Context

Found while running the PB-161.3 measurement, on a live Codex reviewer — not by reading. The
reviewer did its job correctly and **could not deliver the result**. It said so itself, in its
final message:

> Delivery to the orchestrator was attempted twice, but the Promptobus MCP calls were rejected
> by the environment.

**Every** bus call of that turn failed. Four calls, four identical failures, from the holder
log (`codex-cli 0.146.0`, 2026-09-12, 00:57 MSK):

```
21:57:56.429 event item/started mcp promptobus-promptobus/promptobus_mailbox inProgress
21:57:56.433 approval deny mcpServer/elicitation/request the participant has no person to
             answer an elicitation server=promptobus-promptobus mode=form id=0
21:57:56.436 event item/completed mcp promptobus-promptobus/promptobus_mailbox failed
             {"message":"user rejected MCP tool call"}
```

and the same at `id=1`, `id=2` (mailbox) and `id=3` — the `promptobus_send` carrying the
report.

**A second live run, 48 minutes later, did the opposite on the same defect.** A mixed round
(`live-mixed`, 2026-09-12, 01:45 MSK) put a Codex reviewer through **six bus calls across two
turns, every one `completed`**, two of them `promptobus_send` carrying review reports that
reached the orchestrator. From that holder log: `grep -c elicitation` is **0** and `grep -c
approval` is **0** — no request was refused, none was ever made. The record's `methodsCalled`
holds 22 methods and not one approval or elicitation among them.

So the defect is **not universal to a Codex participant**. Two stands, one binary
(`codex-cli 0.146.0`), one model (`gpt-5.6-sol`), opposite outcomes.

### What differs between the two stands

The server name in the calls is the visible difference — `<consumer>-promptobus` in the live
run, `promptobus-promptobus` in the failing one — and it is a label of the HOST, not a cause:
the key prefix is `${host.commandName}-` (`codexMcpPrefix`). Reading it back gives the real
split, which is the **version of the mechanism**:

- the live run was driven by the consumer's CLI, whose `promptobus` is pinned to the released
  **v0.6.0** (`4349dc5`). There the bus entry goes out as a
  `ThreadStartParams.config.mcp_servers.<prefix><name>` override that **merges onto the
  owner's personal `~/.codex/config.toml`** — `shadowedUserServers()` returns `[]`, and the
  comment above it says so in as many words;
- the failing run was driven by this working tree, where a participant lifts in an **isolated
  `CODEX_HOME`** whose `config.toml` holds the mechanism's `[mcp_servers]` entries and nothing
  else (no personal set, no `[projects]` for a reviewer, no plugins, no marketplaces).

**Ruled out, each with its own evidence, rather than left as "probably not":** `approvalPolicy`
— `on-request` in both versions, same two call sites, same constant; the transport — `stdio`
in both (the live record: `type: stdio`, node plus the host's own `promptobus mcp`); the bus server's
tool set — its file is untouched in `4349dc5..HEAD` and it declares no tool annotations in
either version; and the `mcp_servers` record itself — **neither config names an approval key**.
The personal `~/.codex/config.toml` has no `approval_mode` and no
`default_tools_approval_mode` on any of its 22 servers, and `codexMcpServers` /
`codexHomeConfig` emit only transport fields plus `disabled_tools`. The difference is therefore
not inside the record; it is in what else the home does or does not contain.

### What codex-cli asks — settled, and it is not a server's elicitation

The previous revision of this card called "per-call MCP approval" the reading the evidence fits
rather than a measured fact. It is now a fact, read out of codex-cli 0.146.0 itself — the
binary the stand runs — at no cost and with no turn. In `core/src/mcp_tool_call.rs` the prompt
and its options sit together:

```
Approve app tool call?
  Run the tool and continue.                              (Allow)
  Run the tool and remember this choice for this session. (Allow for this session)
  Run the tool and remember this choice for future tool calls.
  Cancel this tool call.
__approval   __codex_mcp_decline__   codex_approval_kind   mcp_tool_call   persist/always/session
```

beside `user rejected MCP tool call` — the exact string the four dead bus calls ended on.

So `mcpServer/elicitation/request` carries **two different questions on one method**. A server's
own `elicitation/create` is one of them. The other is codex-cli asking, per call, whether the
participant may run an MCP tool — shipped over the elicitation channel because the app-server
protocol has no approval method for it (the measured `ServerRequest` list has ten arms and none
is an MCP approval), and attributed to the server whose tool is being called, which is why the
log named `promptobus-promptobus` for a question the bus server never asked. The independent
measurement stands and now reads the right way round: the bus server, started exactly as the
participant's `config.toml` starts it and driven by a client that declares the elicitation
capability, issues **zero** server→client requests and its `promptobus_send` succeeds.

`decideApproval` answered both questions with PB-41's single judgement — "the participant has no
person to answer an elicitation" — which is right for the first and fatal for the second. The
decline of a tool-call approval is not an unanswered form; it is the tool call, killed.

**This is a regression with a known author: PB-41 removed a hang and put a lost report in its
place.** That line closed PB-41, where on 2026-09-06 two Codex reviewers in a row HUNG after
`approval allow mcpServer/elicitation/request`. The trade was a hang for a silent loss, and the
loss is quieter: a hung reviewer is visible, a reviewer that finishes having delivered nothing
looks like a reviewer with nothing to say. Worth noting for what it suggests about the hang
itself — the allow of that day answered with `{ action: 'accept', content: {} }`, a blank answer
to a form whose required field is the choice.

**Why the suite was green about it.** Every check on this path is written against the Codex
stand, a stub app-server that never issues an elicitation, so the decline never had a
consequence to observe. `codex-elicitation.test.mjs` asserted that the decision function returns
`allow: false` and nothing about what happens to the call afterwards — the shape the
contributing guide warns about under "What the stands prove, and what they cannot".

## Work to do

- ~~Settle what codex-cli asks.~~ **Done**, from codex-cli 0.146.0's own strings and its
  vendored `ServerRequest` schema, without a turn: a per-call MCP tool approval carrying
  `_meta.codex_approval_kind`, a `__approval` field and the `__codex_mcp_decline__` sentinel.
- ~~Split the decline by what is asked rather than by the method name.~~ **Done.** A request
  carrying the `_meta` marker is codex-cli asking whether the participant may call a server of
  its own disposable `CODEX_HOME` — a set the lift put there and nothing else is in
  ([ADR-007](../../adr/adr-007-codex-participant-isolated-home.md)) — and is accepted for both
  roles. Everything else keeps PB-41's decline.
- ~~Log the elicitation's allowlisted shape fields at the decision point.~~ **Done**, and it is
  what makes the next live turn conclusive: the holder now writes `kind=` (which question) and
  `schema=` (whether a form was requested), never the message, prompt, schema or URL.
- ~~Move the check to where the consequence is visible.~~ **Partly done, and the rest cannot be
  done here.** The checks now assert the REPLY that goes back on the wire — its `action` and its
  `content` together — instead of the decision function's boolean. Past the holder the stand
  cannot see: it is a stub app-server and issues no elicitation, so whether codex-cli ACCEPTS
  this particular content is not provable on it. Saying so is part of the fix.
- ~~Re-measure with a live participant.~~ **Done, 2026-09-12, one paid turn on this tree** — the
  live verification PB-41's closure was owed, and it is green. A Codex reviewer of a
  standalone-host stand made three bus calls; each one raised
  `mcpServer/elicitation/request` first, logged `server=promptobus-promptobus mode=form
  kind=mcp_tool_call schema=true`; each was allowed; each call then read `item/completed mcp
  …/… completed` instead of `failed {"message":"user rejected MCP tool call"}`; and the
  reviewer's `promptobus_send` arrived in the task journal as a `result`. **So the defect does
  reproduce on this tree**: the isolated home is where codex-cli asks, once per call, and the
  failing run of 00:57 was not a one-off of that stand.
- **Still open — the accept's CONTENT is derived, not measured.** The live turn proves that
  accepting makes the call complete; it does not separate an accept with a filled form from an
  accept with a blank one, because the holder does not log the payload and that redaction stays.
  The `__approval` field name and its accept const are therefore still read off codex-cli's
  strings and the vendored schema, not off an observed message.
- **Still open — WHY the released mechanism's participant is never asked.** Both sides are now
  measured — the isolated home always asks, the personal home never did — but which of the
  personal home's contents suppresses the question is not. Candidates, none of them measured:
  approval state held outside `config.toml`; the plugin/marketplace catalog the personal home
  has and the isolated one does not (the binary carries `conflicting MCP server actions; using
  resolved catalog outcome`); or the automatic approval review, whose
  `item/autoApprovalReview/started` and `…/completed` both fired in the v0.6.0 run. It no longer
  blocks anything here: on this tree the question always comes and the holder answers it.
- **A lead, deliberately not taken this pass.** Measured free on 0.146.0: `[mcp_servers.<name>]`
  accepts `default_tools_approval_mode`, and `[mcp_servers.<name>.tools.<tool>]` accepts
  `approval_mode`; both are `auto | prompt | writes | approve` (a config with `"nonsense"` fails
  the load with `unknown variant`, while an unknown KEY is swallowed, so the refusal is what
  proves the key is real), and both round-trip into the effective config through `config/read`.
  Declaring one on the mechanism's own servers would stop codex-cli raising the question at all.
  Not shipped, for two reasons, both honest: the semantics of `auto` versus `approve` are not
  established — `config/read` and `codex mcp get` echo the value and reveal no default — and it
  would be a fix for a cause that is still the unmeasured item above.
- Phase 3.5 of the parity run — lifting the orchestration skill's ban on a Codex reviewer —
  stays blocked until that re-measurement is green.

## Out of scope

- The elicitation redaction itself. Not logging a server's prompt text is right and stays; what
  this card added is shape — which question, and whether a form came with it — never the message.
- PB-161.3's own question, which this run answered separately and positively.
- Hook trust for a participant. Same "the participant has no person to ask" theme, different
  mechanism and a different flag: PB-170.

## Verification

- A live Codex participant sends a `result` through `promptobus_send` and it arrives in the task
  journal — shown by the journal, not by the absence of an error.
- A check that fails when the bus call dies, rather than one that passes because the decision
  function returned `false`.

## Weight

Narrowed by the second live run, and the narrowing is the point. "A Codex participant cannot
reach the bus" is not what the evidence says: one live participant reached it six times out of
six on the released mechanism. What was at stake is this working tree's own configuration of one
— the isolated `CODEX_HOME` that phase 3 introduced — and there the loss was total and silent
for a worker exactly as it was for the reviewer, because `promptobus_send` is the same tool on
the same server. The third live turn closed it: on this tree the question comes on every bus
call and the holder now answers it, three calls out of three, with the report in the journal.
The parity premise was never under question; the isolated home was, and is not any more.
