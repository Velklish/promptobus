# PB-416.12 · Make shared service lock acquisition safe during owner release

- **Scope:** [Shared service ownership](../../reference/03-cli.md), [Shared service architecture](../../adr/adr-040-shared-workspace-service.md)
- **Created:** 2026-10-30
- **Dependencies:** PB-416.2
- **Cost:** major
- **Taken:** 2026-10-30

## Context

Evidence: GitHub run 41015604653, source 723a13baaf7df7a919c7df17b8d9e412052ccc78, Node 22 / macos-latest job 123931127397 failed shared-service.test.mjs: “concurrent public ensure commands succeed —  |  | Error: Shared service lock has no valid owner; inspect it before retrying”. The job passed 192/193 files; the other three jobs passed. Current main's later four-job run passed, which does not explain the earlier failure. The full failed log is retained by the coordinator.

Source inspection shows acquisition/publication protected by a gate, but the returned release callback removes the owned directory outside that gate. A contender may observe the directory before release and then miss its owner file. This is a suspected schedule, not an established cause of the historical CI failure; reproduce it with an owned deterministic barrier before claiming causality.

## Work to do

- Record two isolated shared-service runs on current source and on the CI source, with exact commands, outcomes and full failures. Do not label a successful repeat as exoneration.
- Build a controlled owned-process schedule around active-lock observation, release and owner read. Establish which interleaving produces the invalid-owner refusal, while retaining a real process birth/nonce and the existing core gate.
- Make release and acquisition safe against that schedule with the smallest change. Preserve the synchronous release interface where possible, one physical owner, nonce-safe cleanup, live/unknown owner retention and actionable refusal for a persistently corrupt or unowned lock. Do not suppress unknown-owner errors, blindly steal a lock, increase timeouts or delete a replacement generation.
- Cover successful reacquisition, replaced owner protection and true missing/corrupt proof separately. Update ADR-040/CHANGELOG with the demonstrated contract and limits; avoid claiming that a local controlled defect proves the earlier CI schedule.

## Out of scope

- Native launch/config activation, new lock APIs or generalized lock refactoring, journal ownership changes, user process cleanup and release publication. Do not weaken private-path or process-birth checks.

## Verification

- The controlled original implementation fails for the demonstrated schedule and the corrected implementation succeeds; no duplicate owners, foreign deletions or unexplained proof loss. Existing concurrent public ensure and root-admission lock ordering still work.
- Strict build, relevant focused tests, committed meaningful mutation probe and five repository gates pass on clean committed source. Fresh independent review reports zero critical/major and evidence-backed remaining minors.
