## Context

PB-406.3's plan and capacity scoring can be accepted on its own. Its live participant cap work needs one lifecycle for a seat from admission through launch, registration, link and recovery. Four isolated review rounds found these failures on the named worker heads:

- `6e524bc4f7784c685415922881bb47a5251d819f`: worker and reviewer checked the cap before taking the task lock, so concurrent lifts could both see a free sixth seat and start a seventh. A teamlead spawn bypassed the check and its record was not counted. The same review found that a huge finite capacity could overflow a score; that scoring finding belongs to the narrowed PB-406.3 and was fixed there.
- `7f62266a89077dfdc3ccc1d26887f4ad383b5aa7`: a teamlead could launch its harness before the root task's link callback checked a newly full cap; a rejected link left the extra session running.
- `2829b1b55fd3d6d48db23391d8039047198defc1`: an unconditional cleanup could free a seat while a Claude session was alive but lacked a full ID; a hard kill before child-link intent could strand a seat with no owner recovery.
- `babb6ca083a1e068edc1a2c01176099afdcb4909`: a failed OpenCode lift could delete its registry entry and leave an unreclaimable seat; a hard kill during Claude background launch could free a seat before delayed registration; an unreadable Codex registry could be mistaken for proof that no session was running.

Evidence: the four reviewer results in the PB-406.3 Promptobus task journal, each on the clean HEAD above. The source paths identified there are `lib/spawn.js`, `lib/review.js`, `lib/liftoff.js`, `lib/driver-opencode.js`, `lib/driver-codex.js` and `lib/harness-registry.js`. These heads are preserved on the local worker branch and its backup reference.

The worker's design note for the follow-up: one admission point writes a provisional seat under the task lock while checking fresh live participants. The seat records address, harness, session name/reference, owner pid and process start, token and phase. A confirmed launch advances phase; a successful child link replaces the seat. Only the path that knows the lift's terminal outcome releases a seat, and only after proving no session remains. A stale seat is reclaimed under lock only after owner liveness fails **and** a fresh harness lookup proves no session is running. A live or unknown session keeps the seat and has an explicit owner stop/recovery route. The review showed that those rules must apply across the different driver failure and registration behaviors, not just one harness.

## Work to do

- Implement one locked seat reservation and recovery lifecycle for fresh worker, reviewer and teamlead lifts across Claude, Cursor, Codex and OpenCode. Count every live participant of the task against `caps.liveParticipants.<harness>` before any harness launch.
- Make launch failure, live-but-unbound state, delayed registration, unreadable registry, process death and child-link failure explicit outcomes. Release or reclaim only on a verified stopped/dead outcome; fail closed on unknown state, with a usable owner recovery path.
- Keep `models` and dry-run decisions informative without reserving a seat. Name the cap and overlay path in a refused lift.
- Implement this card in a separate run after PB-406.3's scoring acceptance; do not mix the live-cap work back into that acceptance.

## Out of scope

- Setting account capacity values or changing plan-aware scoring, which PB-406.3 owns.
- Activating this workspace's live overlay caps before its installed runtime contains this accepted lifecycle; a separate deferred card owns activation.

## Verification

- Concurrent worker/reviewer and teamlead lifts at one remaining seat admit exactly one harness session, including the cap-one case; the tests fail on the current behavior.
- A live but unbound session retains its seat until stopped. Failed OpenCode lift cleanup permits safe retry. Delayed Claude registration after launcher death does not permit an extra launch. Malformed or unreadable Codex registry data keeps the seat until absence is proved.
- A hard kill before child-link intent does not strand a seat forever: retry reclaims only after dead owner and dead-session checks. Unknown lookup remains fail closed with an owner recovery route.
- The configured clean gate reports its exit code and gates N/green M on the committed change; post-commit mutation probes turn the named boundary tests red and restore green.

## Additional consumer of incomplete Codex registry data: participant-home sweep

Evidence at `cb06fff67efa6612fb0d41da95bbdbdcec486481`: `lib/harness-registry.ts:70-82` returns an empty list on a directory read error and skips invalid or unreadable records. `lib/driver-codex.ts:518-531` uses that list as the set of live homes when sweeping, and `:1197-1199` invokes the sweep during lift. The directory ownership, type, symlink, realpath and mode checks at `:670-678` do not validate the records inside it. A malformed record for a live session can therefore leave its home absent from the list and make it eligible for recursive removal. The audit's injected filesystem probe returned exit 0 for three cases: a valid record retained the fake home; malformed JSON and injected EACCES called the fake `rmSync` with `recursive: true` and `force: true`. EACCES reachability in an owned 0700 directory was not established. No actual home was removed and no live session was exercised.

Extend this existing task's incomplete-observation work to the sweep consumer. Distinguish a genuinely absent registry (`ENOENT`, where an empty registry may be valid) from an unreadable registry and from any malformed or unreadable entry. If the scan is incomplete, preserve every participant home and surface an incomplete observation; do not infer that a session is absent. Keep the normal orphan sweep for a complete registry. This is an additional consumer of the existing registry-observation cause, alongside the seat-reservation case above.

Acceptance: isolated fixtures for a corrupt record and a registry access error retain all homes and report the incomplete state; an absent registry follows the established empty-state contract; a complete registry preserves live homes and still removes valid orphans. Cover both the reservation and sweep consumers without weakening the existing task's acceptance criteria.

Verification after the change, from the repository root, **notRun**: `npm run build`, then `node test/promptobus-driver-codex.test.mjs`, followed by the configured project gates. No live cleanup or real deletion is evidenced by the injected probe.
