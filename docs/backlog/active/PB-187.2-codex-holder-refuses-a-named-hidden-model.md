# PB-187.2 · The holder's start-path model check refuses a named hidden model, and hidden-row retention has no live check

- **Scope:** `lib/codex-session.js`, `lib/model-routing/adapter-codex.js`
- **Created:** 2026-09-25
- **Dependencies:** found while working `PB-187`
- **Previous order:** 240
- **Taken:** 2026-09-26

## Context

The holder's start-path model check asks `model/list` with no `includeHidden`, then refuses the
hold when the named model is not among the returned ids:

<!-- quote:../../../lib/codex-session.js -->
    if (record.model) {
      try {
        const listed = await rpc.request('model/list', {}, MODEL_LIST_TIMEOUT_MS);
        const ids = listedModels(listed.result).map((m) => m.model);
        if (ids.length && !ids.includes(record.model)) {
          failHold(`model «${record.model}» is unknown to app-server (model/list)`);
          return;
        }
      } catch (err) {
        log(`model/list: ${err.message} — check skipped`);
      }
    }
<!-- /quote -->

`listedModels` itself carries the opposite contract in its own comment, immediately above it in
the same file:

<!-- quote:../../../lib/codex-session.js -->
/** `model/list` rows as names, with the mark app-server puts on hidden ones. Filtering is
 * the caller's: a hidden model a person named is still a model they named (ADR-004). */
export function listedModels(result) {
<!-- /quote -->

On codex-cli 0.156.1 (PB-196, 2026-09-25 re-triage recorded in `docs/backlog/active/PB-187-…md`),
`model/list` with no `includeHidden` answers seven rows and hides `gpt-reserve` and
`codex-auto-review`; those two names come back only under `includeHidden: true`. So a lift naming
either of those two models is refused at the start path — `ids.includes(record.model)` is `false`
for a model the account has, but hidden — even though the same file's own comment says a hidden
model a person named is still a model they named.

The adapter's preflight probe makes the identical `{}`-only call for its own, separate purpose
(availability snapshot rather than a start-path gate):

<!-- quote:../../../lib/model-routing/adapter-codex.js -->
    const listed = await ask('model/list', MODEL_LIST_TIMEOUT_MS);
    if (listed.gone) return stopped(listed);
    // **Hidden models are KEPT, with the mark on them** (ADR-004): the resolver filters them, and
    // dropping them made `models` show an inventory the harness itself contradicts.
    const models = listed.error
      ? null
      : listedModels(listed.result).map((m) => (m.hidden ? { model: m.model, hidden: true } : { model: m.model }));
<!-- /quote -->

The stand fixture that claims hidden-row retention feeds `hidden: true` rows into `listedModels`
directly and never through either call site above, so it passes without exercising the `{}`-only
request that both call sites actually send:

<!-- quote:../../../test/model-routing-adapter-codex.test.mjs -->
test('hidden is carried by the shared model parse, not filtered inside it', () => {
  // The start path checks a NAMED model against these names and must still see a
  // hidden one; the adapter is what drops them. One parse, two readings.
  const parsed = listedModels({ data: [{ id: 'a' }, { id: 'b', hidden: true }, 'c'] });
<!-- /quote -->

Two consequences follow, both live on this build and neither exercised by the fixture:

- A lift naming a model the account has, but which app-server marks hidden, is refused at the
  start path with "unknown to app-server (model/list)" — a false refusal against the comment's own
  contract.
- Hidden-row retention (`test/model-routing-adapter-codex.test.mjs:204-211`) has no live
  counterpart on this build: neither call site asks for hidden rows, so a hidden row never reaches
  either `listedModels` call in practice.

Whether app-server would actually run a turn on a hidden model — once the start-path check stops
refusing it — is unmeasured; this card does not claim an answer either way.

## Work to do

- Decide, as the owner: does the start-path check ask `model/list` with `includeHidden: true` (so
  a named hidden model is recognised and the comment's contract holds), or does the comment get
  narrowed to say filtering is the caller's only among the rows the request happens to return?
- If `includeHidden` is added at either or both call sites, re-verify the stand fixture actually
  exercises the real request shape, not only `listedModels` fed a literal object.
- Record whether a lift on a named hidden model then runs a turn, once the refusal above no longer
  blocks it.

## Out of scope

- `PB-187`'s own scope: the catalog, `models validate`, and the reference/guide text it edited.
  This card is the behavioural question those docs deliberately left to the owner.
- Whether the catalog should carry any of the currently-hidden model ids — that is a `models
  validate` / catalog-membership question, not this one.

## Verification

- A lift naming a model that is present but hidden in `model/list` is not refused at the start
  path for a reason contradicted by the file's own `listedModels` comment — or the comment is
  narrowed to match what the check actually does.
- The stand fixture for hidden-row retention exercises the real `model/list` call each site
  makes, not `listedModels` fed a hand-built object.
