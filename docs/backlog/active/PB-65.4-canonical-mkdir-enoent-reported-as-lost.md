# PB-65.4 · A canonical-directory mkdir ENOENT is reported as intent-lost while the intent remains

- **Scope:** `src/v1/messages.ts` (`materialize`), [04-protocol § Recovery](../../reference/04-protocol.md#recovery)
- **Created:** 2026-09-25
- **Dependencies:** none
- **Parent:** PB-65.2
- **Cost:** major
- **Previous order:** 65
- **Taken:** 2026-09-25

## Context

Finding discovered while working on PB-65.2. Re-filed as major: [04-protocol § Engine](../../reference/04-protocol.md#engine) says an `intent-lost` entry means the message is permanently lost and will not be retried, while the adapter prints that about a live intent the next pass delivers. An operator who believes the warning resends, and the second send is a duplicate.

Evidence: Node v25.2.1, 2026-09-25. A dangling symlink at `tasks/<id>/messages` makes mkdir return ENOENT. `openEngine` with `recover: false`, then `recover(id)`, returned failed code `intent-lost` and the note that the intent is gone and there is no canon, while the intent json was still in `intents/`. `status` exited 0 and warned that the message is lost and will not be retried. After unlinking the symlink, the next recover returned one repair and the intent was gone. Re-measured after `dirFailure`: a canonical-directory ENOENT is still returned raw, and the result is unchanged. A recipient-directory ENOENT is classified on PB-65.2 and is not this card. The measurement script exited 0.

## Work to do

- Stop reporting a live intent as `intent-lost` when mkdir of the canonical directory returns ENOENT because a symlink there is dangling. The next pass delivers once that symlink is gone.

## Out of scope

- Recipient-directory `ENOENT` and `ELOOP`, classified as `dir-occupied` on PB-65.2.

## Verification

- A regression: dangling symlink at the canonical directory, recover reports a retryable refusal while the intent file remains, and after the symlink is removed the next recover delivers and the intent is gone. `status` must not say the message will not be retried.
