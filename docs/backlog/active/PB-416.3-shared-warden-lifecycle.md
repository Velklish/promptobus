# PB-416.3 · Run task warden state machines inside the shared service

- **Scope:** [Warden](../../reference/03-cli.md), [Delivery and trust](../../guides/hooks-and-trust.md)
- **Created:** 2026-10-30
- **Dependencies:** PB-416.2
- **Cost:** major
- **Previous order:** 380
- **Taken:** 2026-10-30

## Context

Run the existing task warden state machines inside the single workspace service. Task ownership remains separate even though their physical PID is shared.

Evidence: lib/warden.ts launches one detached command per task, claims each journal seat, maintains its own watcher/snapshot/beat and clears only that task on exit. Native BB delivery has its own authority and must retain that path.

## Work to do

- Move task watchers, rounds, retries and cleanup under the shared service; prevent ensureWarden from creating per-task processes. Preserve existing journal claims and diagnostics.
- Pass explicit wake/session context through HTTP join and ownership operations. Keep task-local loop state, alias routing, deadline/stall handling and journal recovery intact.
- Count active warden work in service lifetime; one closed task must not stop another task or a live client. Keep native BB dispatch/pause/epoch authority on its existing path.

## Out of scope

- Harness config migration, native BB authority changes, account/model policy and consumer source changes.

## Verification

- Concurrent active root/child tasks share one physical service PID, maintain distinct journal seats and receive their own wakes. Closing one leaves the other working; closing all permits idle exit only without clients.
- Crash recovery restores retained delivery without crossed identities or duplicate commits. Ordinary routing/warden/E2E tests, required gates, committed probes and independent review pass.
