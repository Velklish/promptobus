## Context

PB-159.1 named five wall-clock sites. Four stopped depending on neighbours in that pass;
this one did not, because it is not one defect. The check is shared — the scenario module

```js
    const stands = stallStands(home, TASK, participantOf(WORKER), viewAfterSend?.stall);
    check('step 7: a participant that finished a turn AFTER a send is not counted as stalled',

      `turn yielded: ${idleAfterSend} · snapshot ${JSON.stringify(viewAfterSend)} · predicate ${stands}`);
```

<!-- /quote -->

**First class — the verdict races the re-knock. A candidate in the mechanism, not in the
test.** For `kind === 'unknown'` the predicate is a comparison of two stamps:

<!-- quote:../../../src/supervisor.ts -->
```ts
  if (sent === null) return !justSpawned(participant);
  return sent < since;
```
<!-- /quote -->

`since` is the participant's last activation, `sent` their last message. The check asks for
`stands === false`, that is `sent >= since`. Nothing in the file holds that order: the
warden re-knocks on its own retry threshold, and a knock landing after the participant's
reply makes `since` newer than `sent` — the predicate then says the stall stands, on sound
code. That is exactly the shape of the red PB-159.1 recorded at ~09:05 UTC on the untouched
tree at `9e44ef0`: `turn yielded: true`, snapshot `{"state":"alive","busy":false,"stall":
{"kind":"unknown","reason":"the turn ended"}}`, `predicate true`.

Stated as a hypothesis, not a fact: it is read off the two sources above and was NOT
reproduced. Reproducing it needs a machine loaded enough for a re-knock to fall between the
reply and the verdict, and the measurement was not made. What makes it worth a card rather
than a note is that the candidate is in `lib`/`src`, not in the test: if the mechanism is
right to call a fresh un-answered knock a stall, then the TEST owes the precondition a
waited-for line; if it is not, the predicate owes the send a grace of its own.

**Second class — the tmux server disappeared, and this one is not a budget at all.**
Recorded in the parent card for `8c926d5` on a clean GitHub runner, `Node 22 /
ubuntu-latest`: the same step 7, with `stall.reason: persist session cursor-… is not on the
tmux server cursor-agent — it was stopped from outside or the machine rebooted` and
`tmux panes: []` beside it. No neighbours: the runner is clean, `promptobus-mixed.test.mjs`
is in the serial group (`test/run.mjs`), concurrency 1. A re-run of that cell on the same
commit was green, all four cells `success`; locally the file passed twice in a row, 48/48,
exit 0; in eleven preceding red CI runs the file had not failed once.

The two share a title and nothing else. One is a comparison of two stamps, the other is a
vanished tmux server under a persist session. Explaining either by machine load is what
PB-159.1's own 2026-09-13 addendum forbids: the class marker it proposed — "red in the pool,
green standalone twice" — pointed at a real cause the last time it was followed, and the
cause was not load.

## Work to do

- Decide, for the first class, which side owes the precondition: the mechanism (a
  participant who has answered is not stalled by a knock that arrived after the answer) or
  the test (wait for `sent >= since` and assert it on its own line, the way PB-159.1 did for
  the `LISTED` branch). The answer decides whether the change lands in `src/supervisor.ts`
  or in `test/scenario.mjs`, so it is a decision before it is an edit.
- Establish the first class by measurement before repairing it: a forced re-knock between
  the reply and the verdict, not a loaded machine. A stub warden round driven by hand is
  enough — the stamps are in the task store.
- Give the second class its own reproduction: what took the tmux server down under a
  persist session on a clean runner. Until that is known, the step's red text cannot tell
  a reader which of the two they are looking at — the verdict prints the snapshot, and the
  two snapshots differ, but nothing names the class.
