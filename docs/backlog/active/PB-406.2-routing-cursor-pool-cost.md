# PB-406.2 · A Cursor model's routing cost follows its pool, and the owner can keep routing out of the api pool

- **Scope:** [03. CLI § Model routing](../../reference/03-cli.md#model-routing)
- **Created:** 2026-10-28
- **Dependencies:** none
- **Parent:** PB-406
- **Cost:** major
- **Taken:** 2026-10-28

## Context

Finding discovered while working on PB-406. Evidence: on `balance-fallback` (no harness paceable) the pick is `bestOf(scored)` (`lib/model-routing/resolver.js`), and `scoreOf` has no pool term; the catalog's static `quotaCost` gives `cursor-gemini-38-high` 1, so it scores about 68 against about 49 for `grok-4.7-high` from the `auto` pool, although gemini is charged to the third-party `api` pool. Even with real windows, under `balanced` the `remaining` term (15 %) loses to speed. Owner's rule for that run: use only the included `auto` pool unless named.

## Work to do

- The cost term of a Cursor tuple depends on the pool its model is charged to (`monthly-auto` vs `monthly-api`), from the adapter's bucket list.
- The fallback path keeps pool awareness: prefer the less-spent pool within a harness, and use the last known windows (PB-406.1) when present.
- An overlay rule lets the owner deny a pool for automatic selection (for example `deny.pools: ["cursor:api"]`), while an explicitly named `--model` still lifts.

## Out of scope

- Changing which models Cursor puts in which pool.

## Verification

- With the `auto` pool at 18 % and `api` at 68 %, and with Cursor windows missing, `balance` picks an `auto`-pool model; a test fails on the current code.
- With `deny.pools` naming `cursor:api`, no `api`-pool model is chosen automatically, and `--model <api model>` still lifts with a warning.
