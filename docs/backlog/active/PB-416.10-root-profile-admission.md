# PB-416.10 · Serialize approved root profiles with managed launch exclusion

- **Scope:** [Shared owner](../../reference/03-cli.md), [BB native ownership](../../reference/02-host.md)
- **Created:** 2026-10-30
- **Dependencies:** PB-416.2
- **Cost:** major
- **Parent:** PB-416.4
- **Taken:** 2026-10-30

## Context

Extract the owner-side admission state needed by the approved launch/configuration stage. Root authority comes from an explicitly approved canonical native account/session-store profile for a canonical workspace/store/runtime, never from missing role variables, a caller-selected BB origin or the first HTTP metadata value.

Evidence: the BB integration records launch intent before threads.spawn, but the durable participant-to-BB-thread binding is written after spawn returns. A native preparation or other-origin dispatch can therefore precede that publication. Ordinary BB and managed BB participants can use the same native account store. A negative lookup of the current bindings alone leaves a root-escalation window. Public BB thread/identity events establish native-to-BB correspondence but do not classify an actor's authority. The scoped design review accepted one canonical lock around root eligibility/commit and managed intent publication as the minimal ordering invariant; implementation proof is still required.

## Work to do

- Add a small private owner module for explicitly approved root profiles and durable managed-launch exclusion, using existing canonical/private-path and process-lock machinery. Profile creation is an owner operation; no public MCP tool grants a profile. Keep the module separate from protocol transport and avoid arbitrary Host serialization.
- Serialize root complete-negative lookup and its realization callback under the same canonical workspace/store lock used to persist managed launch intent before a provider can spawn. Publish the permanent denied BB thread and resolve its intent under that lock after spawn returns. Retain unresolved intent after a crash or ambiguous spawn result; never interpret it as unmanaged.
- Deny all managed binding phases and future native generations of the same BB thread, including preparation, orphan and archived states. Missing, corrupt, unavailable or ambiguous authoritative lookup is refusal. Do not use public origin, parent fields or plugin metadata as root authorization.
- Require a unique canonical native-to-BB correspondence supplied by the trusted BB lookup before root admission. The later native guard must also prove first canonical SessionMeta, an explicitly permitted root source, exact approved store, actual app-server PID/birth/nonce and singleton native binding. This module does not replace those proofs.
- Expose only the concrete private operations needed by the following native guard and BB Host bridge. Native generation classification is immutable; adopting an already admitted root as managed is refused unless its root capability has first been revoked. Do not add speculative adapters or a general authorization framework.
- Document the lock, crash and recovery invariants, with focused tests across real processes and CHANGELOG. Preserve public Host, exports and runtime paths.

## Out of scope

- CLI/profile activation, native helper/hook code, BB SDK adapter wiring and compatibility update, managed driver HTTP configs, consumer repin, stdio retirement and release. Those integrations must invoke this module in the documented order before claiming protection.

## Verification

- Approved profile succeeds only with complete eligible correspondence; wrong scope/store/runtime and unmanaged private profile refuse. Managed, unresolved, unavailable, corrupt and ambiguous cases refuse without running realization.
- Hold a negative lookup while a concurrent managed begin tries the same lock; prove there is no managed publication between that lookup and root commit. With intent published first, realization refuses. Crash before intent completion leaves the scope blocked, and permanent exclusion remains after publication and phase changes.
- Verify private state is outside reviewer grants and uses the existing private-path protections; no caller identity values become authority. Run five gates, committed mutation probes and fresh independent review with zero critical/major and evidence for remaining minor findings. Module fixtures are not native workflow proof.
