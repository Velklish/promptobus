# PB-13.1 · A catalog row keyed on a Claude alias re-points when the vendor moves the alias

- **Order:** 230
- **Scope:** [03-cli](../../reference/03-cli.md)
- **Created:** 2026-09-05
- **Dependencies:** PB-13

## Context

Finding from PB-13. The six Claude tuples in `models/catalog.json` name `opus` and `sonnet` as their `model`, not a pinned id such as `claude-opus-5`. That is not a slip: measured 2026-09-05 on `claude` 2.1.251, the binary has no non-interactive model listing at all — `claude --help` shows no `models` subcommand, and `claude --list-models` answers `error: unknown option '--list-models'`. The only names it publishes are in `--model`'s own help text, and that text says what the problem is: "Provide an alias for the latest model (e.g. 'fable', 'opus', or 'sonnet') or a model's full name (e.g. 'claude-fable-5')". The driver's own `DEFAULT_MODEL` is the alias too (`lib/driver-claude.js` line 97).

So a Claude row is a rating of "whatever `opus` points at today". When the vendor moves the alias to a new model, the row keeps its `quality`, `speed`, `quotaCost`, its `assessedAt` and its `evidence`, and starts describing a model nobody assessed. Nothing goes red: the staleness warning fires on the calendar, not on a re-point, and `models validate` has no fact to compare against — the harness publishes no inventory for it to read.

Cursor and Codex do not have this: `cursor-agent models` and `model/list` over `codex app-server` both return concrete ids, and every Cursor and Codex tuple names one.

## Work to do

- Decide what a Claude row is keyed on. Two candidates, and they cost differently: pin the full id (`claude-opus-5`) and lose the "latest" behaviour the driver deliberately uses, or keep the alias and record what it resolved to at assessment time so a later maintainer can tell a re-point from a drift.
- If the second, the recording needs a field the catalog schema does not have today, and the schema is PB-12 — that is a schema change with the ADR's supersede cost, not a data change.
- Whichever is chosen, the alias hazard belongs in [guides/model-routing.md](../../guides/model-routing.md), which today explains only the Cursor effort-suffix quirk.

## Owner's decision (2026-09-05)

Pin the full ids: the Claude rows name `claude-opus-5` / `claude-sonnet-5` (and any other id the driver accepts verbatim), not the aliases; the Claude adapter's inventory reports the same pinned ids (the alias set stays what `--model` accepts at lift). The 'latest' semantics of an alias is given up on purpose: a new model gets a new rated row. No schema change; the alias hazard is documented in the guide.

## Out of scope

- Rating any model that has no source; PB-13's rule stands.
- Making the Claude adapter probe an inventory that the binary does not expose (PB-15).

## Verification

- Whatever is decided, a check that would have caught the re-point: either the catalog names no alias at all, or a row that names one carries the resolved id and `models validate` says so.
