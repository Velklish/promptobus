# PB-234.4 · The probe's numbers and its exit code are never checked against each other, so numbers from a different run pass

- **Order:** 170
- **Area:** `schemas/v1/handover-record.schema.json`, the send-time coherence check in `lib/handoff.js`
- **Created:** 2026-09-17, finding from the PB-234 run
- **Parent:** [PB-234](../../archive/PB-234-probe-record-must-name-target-verdict/task.md)
- **Dependencies:** none
- **Cost:** major

## Measurement

A probe record carries `mutatedRunExit`, `verdicts.baseTotal`, `verdicts.passed`, `verdicts.unaccounted` and `reddened`. Each is checked for shape. None is checked against the others, and the author fills them all by hand from whatever their capture produced.

Measured during the PB-234 run itself. The author's capture wrapper overwrote one output file, so it handed back the numbers of the **restored** run instead of the mutated one: `probe.out` and `probe2.out` on `969bf742` both read "96/96, exit 0" for an invocation the tool had, at that same moment, called red. `probe3.out` on the same sha carried the real mutated numbers. Two of seven probe invocations in that run were spent discovering this.

A record built from the first capture would have passed every check the schema has. `unaccounted === 0` holds — the numbers are arithmetically perfect. They are simply about a different run.

## Why this is a third corner and not a repeat

The parent card and its siblings cover a shape with three corners, and each corner needs its own answer:

1. **The wrong thing reddened.** Closed by `expected` against `reddened` — the parent card.
2. **Not everything ran, because the file aborted.** The record can hold every declared name while the verdicts below the abort silently produced nothing. Closed in the consumer's own suite by counting executed verdicts, not here.
3. **The numbers describe a different invocation than the exit code.** Nothing looks at this, in either repository.

What makes the third the quietest: the other two leave an artefact — a name missing, a total short. This one leaves a record that is internally beautiful and externally false.

## What to do

One coherence check costs nothing and catches the measured case: a red run must show redness.

- `mutatedRunExit` non-zero while `reddened` is empty, or while `passed` equals `baseTotal` — refuse. A run that exited red with nothing reddened and nothing missing is describing two different invocations.
- The mirror also holds: `mutatedRunExit` zero is already a failed probe by definition and is named elsewhere; this card does not change that.

It does not close the corner. A wrapper can hand back a consistent set of wrong numbers, and no check inside one document will see it. Closing it properly means the numbers come from the probe tool rather than from the author's transcription — the tool knows which invocation it just ran, and the author does not.

**That half is cheaper than it first looks.** `npm run probe` already runs both invocations itself and prints `mutated → exit 1`, the list of reddened names, and `restored → exit 0`. The data the record needs is already computed; what is missing is a machine-readable output to take it from, so that a human does not retype it. Measured in this run: `probe3.out` carries all three, while two sibling captures beside it read `94/98` and `98/98` only because a wrapper was added to keep the two invocations apart — and the first two attempts at that wrapper did not, which is where the false `96/96, exit 0` came from.

## Not in scope

- Proving the probe ran at all. Out of reach of a document written after the run, and already said so in the reference.
- The release-skew seam that any new field inherits, and the probe-sha lag — both have their own records from the same run.

## Checks

- A record with a non-zero `mutatedRunExit`, a non-empty `reddened` and `baseTotal − passed − reddened.length` different from the stated `unaccounted` (the restored run's `passed === baseTotal` is one such record) is refused at `send`, with the contradiction named.
- A record where the three agree is accepted unchanged.
- A record written before this check exists keeps passing, or its migration is named explicitly.

## Re-triage, 2026-09-23

Checked on `39316bc2` from the repository root. **Cost `major`**: numbers from another invocation pass `send`, and nothing computes the arithmetic the reference says the author states.

- The fields exist (`schemas/v1/handover-record.schema.json:123` `mutatedRunExit`, `:138` `baseTotal`, `:143` `passed`, `:148` `unaccounted`, `:161` `reddened`). No code compares them: `grep -rn "mutatedRunExit\|baseTotal\|unaccounted" lib src bin` → exit 1.
- **Correction of the first check.** A record with an empty `reddened` is already refused by the schema (`"minItems": 1`, `:164`), and a stated `mutatedRunExit` of 0 by `"minimum": 1` (`:126`). What passes is the mixed record: a red exit, a non-empty `reddened`, the counts of the restored run (`passed === baseTotal`) and `unaccounted: 0` stated. The reference defines `unaccounted` as `baseTotal − passed − reddened.length` (`docs/reference/04-protocol.md:186`), and the schema checks only the stated `"const": 0` (`:150`). The first check now names that record. This is read from the schema, not sent.
- **Correction of "the data is already computed".** `npm run probe` prints the two exit codes, but it neither prints the reddened names nor computes counts. It prints at most five lines matching failure markers (`scripts/mutation-probe.mjs:103`), and it has no machine-readable mode: `grep -n -e "--json" scripts/mutation-probe.mjs` → exit 1. So the "numbers from the tool" half needs output the tool does not produce.
- Not tree-checkable: the `probe.out`/`probe2.out` captures on `969bf742`. The sha exists but is a pre-squash branch commit, not an ancestor of `HEAD`.
- PB-234.3 shares the door. PB-188.2 edits the same `scripts/mutation-probe.mjs` if the tool half is taken.
