# PB-234.1 · A card writing up a finding from a consumer's run has nowhere to name that consumer

- **Order:** 380
- **Scope:** [04-protocol § The handover record](../../reference/04-protocol.md#the-handover-record)
- **Created:** 2026-09-17
- **Dependencies:** none

## Context

`npm run audit` is red, and the two findings are both in the PB-234 card — the file that
describes the work, not the work. The card names the downstream consumer's CLI by name and
carries three of its tracker ids; `scripts/audit-public.mjs` refuses both classes in any
tracked text file, under `origin CLI name` and `origin tracker ids`.

The red is not from this change. Measured both ways on 2026-09-17:

| where | command | exit | findings |
| --- | --- | --- | --- |
| branch, with the PB-234 change | `npm run audit` | 1 | 2, both in `docs/backlog/queue/PB-234-probe-record-must-name-target-verdict.md` |
| base `c9743f57532ad08bd535d95fde775d7ca7f4e66d`, extracted with `git archive` into a tree of its own | `npm run audit` | 1 | the same 2, in the same file |

The failure sets are identical and their symmetric difference is empty, and
`git diff c9743f57 -- <that card>` is empty: the worker did not touch the file. The card was
created by the commit that opened the task.

Both offending strings appear in the card's **Created** line, in its opening measurement
paragraph, and in its **Not in scope** list, where the follow-up work is handed to the
consumer's own tracker. This file names none of them literally, for the reason the audit
exists — the same technique `scripts/audit-public.mjs` uses on its own patterns and
[the contributing guide](../../guides/contributing.md) uses on wrong refs: name the shape,
never assemble the string.

## Work to do

- Rewrite the three places in the PB-234 card so the consumer is described rather than named,
  the way this file does it, and the tracker ids are referred to by role. The card's argument
  does not need either literal: what carries it is the two failure modes, and both are
  describable without saying whose run found them.
- The same question, asked once about the whole directory: the queue and the archive are
  packed into no tarball but ARE tracked text, and the audit reads all 993 tracked files. If
  cards are expected to name the consumer while writing up a finding from its run, the audit
  needs a stated exception for `docs/backlog/` rather than a red every time; if they are not,
  the rule belongs where cards are written, not only where they are audited.

## Status after acceptance

**The first point is closed.** The card that carried the two literals was rewritten on `main`
to name the consumer generically, and `npm run audit` is clean again — 997 tracked files, 0
findings, verified on the merged tree at acceptance.

**The second point is what this card is now about, and nothing has answered it.** Cards
describing a finding from a consumer's run will keep wanting to name that consumer; either
the audit states an exception for `docs/backlog/`, or the rule lives where cards are written
rather than only where they are audited. Left unanswered, the next such card puts the audit
gate red again, and again not by the hand of whoever is working at the time.

Which of the two it should be is the owner's call: an exception widens what a public
repository may carry, and a writing-time rule costs discipline instead.

## Out of scope

- Editing the PB-234 card in this branch. Status directories belong to the approver, who
  closes tasks and edits their text; the worker reports the wording and does not move or
  rewrite a card. That boundary is what left the gate red rather than quietly fixed.
- The `mutationProbe.expected` change of PB-234 itself, which is complete, accepted, and green
  on all four gates.
