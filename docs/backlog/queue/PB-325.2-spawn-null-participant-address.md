# PB-325.2 · Spawn without --task crashes with a TypeError when the only active task holds a participant record with a null address

- **Order:** 315
- **Scope:** [03. CLI § Spawn](../../reference/03-cli.md#spawn)
- **Created:** 2026-10-28
- **Dependencies:** none
- **Cost:** major

## Context

Finding discovered while working on PB-325.

A consumer workspace's store held one active task left by a live probe, `live-hsup-nc1` ("Live N candidate 1"), whose participant record has no address: `promptobus status` prints `MAILBOX UNREAD: the record address is invalid (unknown address «null» …)` for it. A `spawn` without `--task` and without `--new-task` from another session then joins that task to pick the worker slug and crashes before any refusal:

Evidence: 2026-10-27, `promptobus spawn --repo <clone> --brief <file> --worker pb325 --harness cursor --model grok-4.7-high --dry-run` (package 0.30.0) → exit 1, `TypeError: Cannot read properties of null (reading 'includes')` at `refuseParticipantPrefix` (`lib/spawn.js`) ← `workerSlug` ← `planSpawn`. The same command with `--new-task` → exit 0. `promptobus status --task live-hsup-nc1` on 2026-10-28 still prints the null-address line.

<!-- quote:../../../lib/spawn.js -->
      const other = addressOf(participant);

The spawn contract is to refuse a join into a task another session owns and name its owner, id and title; here the user gets a stack trace instead, and it does not say that `--task` or `--new-task` is the way out.

## Work to do

- Make the participant scan in spawn tolerate a record without an address: skip it, or refuse with the task id and the invalid record named, before any slug decision.
- Check the other readers of `addressOf(participant)` on the spawn and review paths for the same assumption.

## Out of scope

- Repairing or closing the foreign task: its owner closes it.
- How the live probe left a record without an address (a separate finding if it reproduces).

## Verification

- A fixture task holding a participant with a null address: `spawn` without `--task` refuses (or proceeds per the chosen rule) with exit 1 and a message naming the task, never a TypeError; a test fails on the current code.
