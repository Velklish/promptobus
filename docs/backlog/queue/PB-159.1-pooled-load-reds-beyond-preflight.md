## Context

Observed during the 2026-09-10 backlog run, with four worker sessions running full suites on one eight-core machine and `uptime` reporting load averages between 115 and 198. PB-159 moved the preflight test into the serial group; these reds are in other files, and two of them are already serial:

- `test/promptobus-mixed.test.mjs` (serial group), the untouched tree at `9e44ef0`, `worker:store`'s baseline at ~09:05 UTC: "step 7: a participant that finished a turn AFTER a send is not counted as stalled — turn yielded: true · snapshot {"state":"alive","busy":false,"stall":{"kind":"unknown","reason":"the turn ended"}, …} · predicate true", file 47/48, exit 1; standalone `node --test test/promptobus-mixed.test.mjs` exit 0, 48/48, twice (55.2 s, 63.3 s).
- `test/model-routing-adapter-cursor.test.mjs` (pool), `worker:verify`'s run at load 174.86 on the PB-159 branch: "a logged-in account whose limit could not be read is quota_unknown with its inventory", actual `probe_timeout`, expected `quota_unknown`, at `:226`; the same file in `worker:store`'s gate at ~09:20 UTC on the PB-146.1 branch: "cursor status did not answer within the 10000 ms left of the preflight budget", actual `unknown`, expected `available`, at `:746`. Standalone: exit 0, 46/46, twice on each branch; on `main` at `9e44ef0` exit 0 twice (09:21 and 09:23 UTC, load 128–152).
- `test/promptobus-cursor-wake.test.mjs` (serial group), `worker:launch`'s gate on the PB-140.1 branch at ~09:43 UTC: 17/18, "step 5: delivery into a turn IN PROGRESS succeeds — the text is queued, not refused" answered `{ ok: false, error: "process <pid> is already writing into this session — two injections at once would glue into one message …" }`; standalone on that branch exit 0, 18/18, twice — and on `main` at `9e44ef0`, standalone, the same step 5 red **twice in a row** at load 184 (09:45 and 09:46 UTC, 61 s and 54 s), so the file goes red without any pool at all when the machine is loaded enough.
- `test/promptobus-driver-codex.test.mjs` (pool), three times: `worker:codex`'s standalone runs after its mutation probe at ~09:45 UTC (exit 1, 128/132, twice), `worker:verify`'s PB-104.1 gate at ~10:01 UTC (125/129) and the orchestrator's standalone run on `main` at `b8bd5b4` at 09:50 UTC (exit 1; the next run at 09:51 exit 0) — always the same four checks on the `long-first` fixture ("a first turn that started and never ends still confirms lift", "status calls the participant in its running first turn alive, not GONE", "a first turn that stays silent past the idle budget is a watchdog stall", "a review arriving during the running first turn is accepted into the next-turn queue"): the stub app-server did not lift within the fixture's 3000 ms and the session record was gone (`no session record in the Codex registry`, `nobody to wake`); standalone at lower load exit 0, 129/129 (twice, `worker:verify`) and 132/132 (`worker:codex`).

Each red is a wall-clock budget — a stall classifier's turn timing, a probe budget, a status answer inside a preflight budget, an inject lock still held by the previous writer, a stub app-server's 3000 ms lift window — reached because the machine's neighbours took the time, not because the mechanism under test failed. The serial group does not help when the neighbours are other suites, and `docs/guides/contributing.md` already says a second `npm test` on the same machine is the normal state of a worker run.

## Work to do

- Decide the policy for a shared machine: the runner reads the load average before the pool and the serial group and, when a red file's assertion is a wall-clock budget, says so in the summary with the load beside it (diagnostic, cheap); or the worker regulation limits full gates to one at a time per machine; or the budgets scale with a declared load factor. The second and third change how a run is scheduled and belong to the owner.
- Whichever is chosen: the five checks above either stop depending on neighbours (counted evidence, the way PB-159's card described for `ticks`) or move with an explanation.
