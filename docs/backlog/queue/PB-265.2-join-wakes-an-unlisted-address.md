# PB-265.2 · `join` presumably hands a contact point for the declared role into a task that does not list it

- **Order:** 70
- **Scope:** [01-overview § join](../../reference/01-overview.md#join--entering-a-task-hand-over-the-contact-point-and-lift-a-listener)
- **Created:** 2026-09-26
- **Parent:** PB-265
- **Cost:** minor (hypothesis)

## Evidence

Finding discovered while working on PB-265.

Evidence: src/mcp/server.ts join: ownership() answers other-address for any address but orchestrator, and mayRegister is true for it; lib/server.js joinBus then calls driver.registerWake(home, task, address) with no check that the task lists the address. A worker calling a tool with task: <another task> therefore presumably writes a contact point for its declared role into a task where that role is no participant — before PB-265 the first send registered it there, now nothing does. Read from code, not run.

## Context

Promote the original Cost: minor (hypothesis) finding to a security-boundary investigation. Current join allows other-address, and the inspected store/driver path may register a wake for an address not listed in a foreign task. Reachability through the current shared HTTP grant and a resulting unauthorized write are not established.

## Work to do

- Confirm or reject foreign-task wake registration. If reachable, require the target task to list and authorize the participant before any contact-point mutation, using the smallest existing-boundary correction.
- Document the proven path and its impact, or record the precise precondition that makes it unreachable; preserve legitimate listed-participant join and orchestrator behavior.

- Security impact remains a hypothesis until the public-route fixture demonstrates it; an internal driver test alone is not authenticated reachability proof.
