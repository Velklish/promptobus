# PB-109 · The bus-hook header tells a reader to regenerate it with `promptobus sync`, a subcommand this CLI has never had, and `02-host.md` doesn't say the shipped bin always overrides the `commandName`/`version` fields it claims `promptobus.json` controls

- **Dependencies:** PB-103

## Context

Re-verified against current HEAD (v0.5.0).

Half 1 — the hook header: `templates/bus-hook.mjs:2` reads `// Generated by __COMMAND__ sync. Edits are overwritten — the source lives in the Promptobus package.` `renderBusHook` (`src/hooks.ts:42-45`) only substitutes `__COMMAND__` → `host.commandName`; the word `sync` is baked into the template text, not derived from the host. `lib/cli.js:19`'s `SUBCOMMANDS` is `spawn, review, models, status, done, dismiss, history, prune, guard, warden, mcp, install, uninstall` — there is no `sync`. The file that actually writes this hook is `install` (`lib/install.js:315-324`, `writes.push({ ..., text: renderBusHook(hookHost) })`). The package already has the right mechanism for this exact failure mode — `host.syncHint()` (`src/standalone.ts:311`, returns `${commandName} install`) — and `lib/spawn.js:301-317`'s own comment describes fixing the identical bug class ("the package has no `tools` subcommand, and the refusal used to print one inherited from the project this package was extracted from" — this is PB-1/PB-1.1's pattern), but the fix was never applied to the hook template.

Half 2 — the host doc: `bin/promptobus.js:26-33` always passes `commandName: 'promptobus'` and `version: pkg.version` into `createStandaloneHost`. `src/standalone.ts:132-134` resolves `options.<x> ?? config.<x> ?? default`, so a `promptobus.json` setting either field is always shadowed by the bin's own values. `docs/reference/02-host.md:29` states flatly: "It reads: `commandName`, `locale`, `version`, `tools`, `rules`, `mcp`, `skills`" — with no caveat that the shipped bin ignores the first two, unlike the analogous `HostToolBin.version` gap the package already caught and wrote up (PB-15.1).
