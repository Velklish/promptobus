# ADR-008: A Codex participant runs in an isolated home, and a reviewer works in a trusted directory of its own

**Status:** Accepted
**Date:** 2026-09-11
**Deciders:** the repository owner, decision of 2026-09-11 on the harness-parity run. The reviewer directory was decided the same day.

## Context

A Codex participant that runs in the owner's `~/.codex` sees the owner's personal MCP servers, writes `[projects]` trust records into a file that outlives the session, and can have its config load killed by a field-wise merge of two transports under one server name. Measured on codex-cli 0.146.0, an MCP server child receives eleven generic variables and no harness session variable; the command path can inherit an ancestor's `CODEX_HOME`.

A reviewer has a second problem. Trusting the tree under review would let that tree's project layer into the session that is judging it. Codex had no mechanism-owned working directory for a reviewer, so only a worker's worktree was trusted.

The skills under `~/.agents/skills` are the workspace canon, addressed to the participant on purpose. The owner accepted that root as the boundary of this isolation. Replacing `HOME` was rejected because it also changes git and SSH.

## Decision

**1B.** One `CODEX_HOME` per participant, built before the lift and removed with the session. It is a directory under `$TMPDIR` at mode 0700, named by task and address. At lift, its `config.toml` holds the mechanism's `[mcp_servers]` entries and `[features] apps = false`; admitted roles also get the trust record of decision 3. The owner's `auth.json` is copied at mode 0600 when present. A linked worktree with a planned guard hooks file also gets `hooks.json` in this home; other working directories keep that file in their own `.codex/`. A Codex teamlead's home also gets `skills/` and disabled hooks; admission itself comes from `TEAMLEAD_HARNESSES`, not from this layout. The `apps` setting was added on codex-cli 0.156.1, whose `apps` feature is on by default and lifts a built-in `codex_apps` MCP server into an otherwise empty home — 52 tools, some of them account writes. With the key the thread lists the mechanism's servers and nothing else (measured 2026-09-25, no turn; [05-drivers](../reference/05-drivers.md#the-built-in-codex_apps-server-stays-off-in-the-participant-home)). The owner's home is opened for exactly one read — that credentials file — and is never written. `sessionEnv` drops an inherited `CODEX_HOME` from the base environment and then honours the one the lift names, so an ancestor's value can never put a participant back in the owner's home. The availability probe, which runs before any participant exists, is pointed at the owner's home deliberately: the account whose limit it reads is the one every participant home will copy.

**2B.** The entries live in the home's `config.toml`, and `thread/start` no longer carries `config.mcp_servers`. The override existed for a collision that the isolated home removes: it merged with the personal config by fields, not by records, so one name with two transports killed the whole config load. With no personal set in the home there is nothing to merge with, and a second source on the request would drift from the file. The key prefix stays, because the tool name the model sees is derived from the config key. `ThreadStartParams.config` always carries `bypass_hook_trust`, optionally carries `model_reasoning_effort`, and a Codex teamlead's thread adds `features.hooks = false`. Admission itself comes from `TEAMLEAD_HARNESSES`, not from that branch; the current overrides are listed in [the Codex holder](../reference/03-cli.md#the-codex-holder).

**3C.** The trust record names the participant's own working directory, by its realpath — measured: a trusted project's own `.codex/config.toml` server comes up in the thread, and the unresolved spelling of the same path does not. For a worker that effect is the point: the repository is already executing in that session, and the isolated home keeps its project layer away from the owner's set. A reviewer's working directory is the sandbox below, not the tree under review.

**4B.** The worker's worktree gets a copy of the workspace `.codex/skills` canon, plus a self-ignoring `.gitignore` inside `.codex/` so the copy stays out of the worker's diff and goes away with the worktree at `done`. Codex reads a project's `.codex/skills` always, trusted or not, so the copy alone is enough. A reviewer's copy lands in the sandbox below.

**Reviewer directory, 1B.** A Codex reviewer's working directory is `<participant settings path without .settings.json>.codex-sandbox` — beside the other participant files in the task store. Deterministic rather than `mkdtemp`, for the reason the Cursor sandbox and the participant home are: `prepare` writes and launches nothing, and `--dry-run` must print the path a real lift will use. The skills copy and its self-ignoring `.gitignore` land there, and the tree under review is attached through `addDirs`, which the driver hands to `thread/start` as `runtimeWorkspaceRoots`. Approval containment reads the session record's `cwd` and `addDirs`, so the containment roots follow the directory without a second decision. `done` sweeps the directory with the rest of the participant's files: it matches them by the address stem and asks no driver.

**Reviewer trust, 2B.** That directory is trusted, by its realpath, exactly as a worker's worktree is. What is trusted is a directory the mechanism built, filled and will delete, not the repository being judged. The tree under review is never trusted — it arrives as a read in `addDirs` and nothing else — and the driver no longer branches on role to say so. What trust grants is the project layer of that directory: its own `.codex/config.toml` and `.codex/agents`. The sandbox has neither today; the mechanism writes only the skills copy into it. The record is taken so every Codex participant's working directory is the mechanism's own, and every one of them is trusted.

**Reviewer record, 3A.** The record goes into the participant's disposable `CODEX_HOME` and dies with it at `done`, `stop`, or a failed lift. Never the owner's `~/.codex/config.toml`. The suite asserts the file the record landed in — the participant home's `config.toml` — and not merely the text of the record.

Rejected and still rejected: one shared home for every participant; trusting the tree under review; writing the trust record into the owner's config; inventing a git repository in the reviewer sandbox before a measurement required it.

## Consequences

- A Codex participant no longer sees the owner's personal MCP servers. The reviewer's mechanical deny covers every server the participant has — on codex-cli 0.156.1 only with `apps` off, since the binary's built-in `codex_apps` server is otherwise one more.
- The participant path does not write the owner's `~/.codex`. The availability probe of the routing gate still starts `codex app-server --stdio` in the owner's home before any participant exists, and `initialize` loads that home's configuration, so the marketplace snapshot refresh is not something the isolation removes.
- When the owner has `auth.json`, a copy sits on disk at mode 0600 for the life of the session. `stop` — and `done` through it — removes the home, and so does a failed lift. The removal guard only ever removes a direct child of the homes root.
- The home lives in `$TMPDIR`. A long-lived participant is exposed to the system's temporary-file reaping. The owner's decision named `$TMPDIR` rather than the mechanism's registry home.
- A worker's repository can put MCP servers and exec policies into its own participant session through its `.codex/config.toml`. The CLI flag `--dangerously-bypass-hook-trust` does not reach app-server. Trust is the `thread/start` override `bypass_hook_trust`. SessionStart runs for a worker from the participant home when its worktree is linked, otherwise from its own `.codex/hooks.json`; a reviewer uses the sandbox's `.codex/hooks.json`.
- The session rollout an operator may want to read is inside the participant home and goes away with it. `phrases.logs` names that home rather than `~/.codex`.
- A repository that tracks `.codex/skills` of its own would have it overwritten by the copy. `spawn` warns before the first write about any path Git already tracks under a directory the driver's launch files claim.
- A Codex reviewer reads the workspace skills canon. The reviewed tree gains no file from a reviewer lift. `review` prints `reviewer home: <path>` on a real lift as well as in `--dry-run`, because the `started in <repo>` line names the repository under review, which is not the session's working directory.
- The lift does not wipe the reviewer directory whole. `copyLaunchTree` erases `<sandbox>/.codex/skills` and nothing above it. Neither a wipe nor a refusal is shipped: inside the mechanism nothing else writes there. A Codex worker's writable roots are its worktree and its `addDirs`; a reviewer is `read-only` and every mutation approval is denied before containment is consulted; `done` removes the directory. The task store is the owner's own. After a reviewer lift the suite asserts that the directory holds exactly what the lift put there — its root and its `.codex/` both. Revisit when the mechanism writes anything else into a reviewer's directory, a participant gains the task store as a writable root, or the store moves somewhere shared.
- Future changes to the home's contents must move together: `codexHomeConfig`, the narrow TOML writer beside it, [03-cli § Spawn](../reference/03-cli.md#spawn) and [§ The Codex holder](../reference/03-cli.md#the-codex-holder), and this ADR. The writer's vocabulary is strings, string arrays and one level of string-valued table. Future changes to what a reviewer's directory holds must move together: the driver's `reviewSandbox` and `prepare`, the trust record in its `spawn`, [03-cli § Review](../reference/03-cli.md#review), and this file.

## Measurements

- **2026-09-12, codex-cli 0.146.0.** Codex reads a project's `.codex/skills` from a directory that is not a git repository, so the sandbox stays without a `git init`. The stand was a standalone-host workspace inside no repository, one stub skill carrying a marker, and one live reviewer turn: Codex put the sandbox first in its skill-roots table, listed the stub, and the model read `SKILL.md` and returned the marker.
- **The same turn.** Every bus call died on a declined `mcpServer/elicitation/request`. The bus server driven directly issues no elicitation. That reporting failure is closed by the resolution below; it is recorded because the skills fact and the missing channel were measured together.
- **codex-cli 0.156.1, 2026-09-25.** With `apps = false` the thread lists the mechanism's servers and nothing else. No turn was taken for that inventory.

## Current resolution

The Stop observation in the first Codex hook notes was made before later hook runs. On codex-cli 0.156.1, worker and reviewer turns recorded Stop; see [hooks and trust](../guides/hooks-and-trust.md#a-participants-hooks-are-not-the-workspaces) and [the Codex driver](../reference/05-drivers.md#codex--codex-harness-driver--the-third-production-bus-driver). The approver evidence in [ADR-024](adr-024-approver-acceptance-in-own-worktree.md) records SessionStart. It does not establish that an approver Stop hook ran.

The reporting failure of 2026-09-12 describes that turn. The holder now accepts Codex's `mcpServer/elicitation/request` only for a tool-call approval from a server configured in the participant home; other elicitations remain declined. A later live reviewer sent a bus `result` after those approvals. The current whitelist and its measured boundary are in [the Codex holder](../reference/03-cli.md#the-codex-holder).
