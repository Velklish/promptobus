# ADR-042: Verify Codex system skills against the admitted runtime

**Status:** Accepted
**Date:** 2026-11-09
**Deciders:** Project owner through the delegated repair run

## Context

Selected native delivery owns the private home's `skills` container. Codex also
generates `.system` there after installation. The ownership receipt does not name
these files, so a subsequent preparation refuses its own generated topology.
`test/native-participant-context.test.mjs` reproduces the marker refusal before
any model launch. Treating the marker as authority would admit arbitrary content;
clearing the entire container would delete harness-generated bytes.

## Options

- A static path/hash manifest rejects unknown content but requires a package
  update whenever the installed Codex generation changes.
- A fresh no-model bootstrap from the admitted launch executable supplies the
  installed runtime's reference. It adds a bounded process and filesystem check
  when retained system skills need validation.
- Trusting a marker or excluding all `.system` content from ownership checks
  cannot reject foreign files or changed bytes.

## Decision

Use a fresh owned home and the same resolved executable that will launch the
participant. Await its `initialize` response, close input and confirm terminal
process exit before reading the generated reference. No thread or turn is
started. Require the exact relative path, type and byte set, without symlinks.
Bind the in-memory reference to the executable's canonical identity and SHA-256;
do not cache it on disk or learn it from another participant home.

Resolve a bare host command through the participant's PATH and working directory
once before bootstrap. Store the canonical path for the holder's actual launch;
later PATH changes cannot select a second runtime. Recheck the admitted identity
before the holder starts, keeping the reference's absolute-path requirement.

Before replacement, reject an unavailable, incomplete or ambiguous reference and
any mismatch in the retained system subtree. Recheck the retained plan at the
write boundary and clear only the container's other children. Preserve `.system`
and its files in place. Keep other selected-context ownership checks intact.

## Consequences

Reinstall accepts the installed runtime's legitimate generated system bytes
without embedding a version-specific manifest. Reference generation receives no
participant credentials or MCP configuration and removes its temporary home only
after the owned process exits. Refusal retains the existing participant files.

A runtime update generates a new reference. If the existing home's bytes differ,
the mechanism refuses rather than silently replacing or adopting them; a fresh
participant home can use the updated runtime. Filesystem checks do not prove
model compliance or suppress independent native skill discovery. Future changes
must retain positive preservation controls, foreign-content controls and mutation
coverage for both acceptance and rejection.
