# Инвентаризация репозитория

Что искать, где искать и что считать уликой. Читается в фазе 1 скилла `backslop-seed`. Итог — четыре списка кандидатов; ничего не пишется в документацию, пока списки не собраны.

## Гейты проекта

| Где | Что брать |
|---|---|
| `package.json` → `scripts` | `test`, `lint`, `build`, `typecheck` |
| `*.csproj`, `*.sln`, `Directory.Build.props` | `dotnet build`, `dotnet test`; анализаторы из `PackageReference` |
| `pyproject.toml`, `setup.cfg`, `tox.ini`, `noxfile.py` | `pytest`, `ruff`, `mypy` — как объявлены |
| `Makefile`, `justfile`, `Taskfile.yml` | цели `test`, `lint`, `check` |
| `.github/workflows/*.yml`, `.gitlab-ci.yml` | что реально гоняет CI — самая надёжная улика: команда, которая красит пайплайн |
| `README.md`, `CONTRIBUTING.md` | команды, которые проект просит запускать перед сдачей |

В `gates` идут команды, которые проходят на чистом чекауте без ручных шагов. Команда, требующая секретов, сети или поднятой базы, в `gates` не идёт — она называется в README подсистемы как ручная проверка.

## Подсистемы

- Каталоги верхнего уровня и проекты решения: `src/*`, `services/*`, `apps/*`, `packages/*`, проекты `.csproj`.
- Точки входа: `main`, `Program.cs`, `index.ts`, `cli/`, `bin/`, `cmd/`.
- Границы по данным: миграции, схемы, `docker-compose` — что за хранилища и очереди.
- Каждая подсистема — строка «раздел → о чём» с путём к каталогу как уликой. Название раздела — по каталогу, а не по догадке о назначении.

## Термины

Кандидат — имя, которое читатель без проекта не поймёт или поймёт неверно:

- сущности домена: классы моделей, агрегаты, таблицы, коллекции;
- события и сообщения: имена очередей, топиков, типов событий;
- перечисления и статусы: `enum`, константы состояний;
- ключи конфигурации и флаги;
- слова из README и обсуждений, которые не совпадают с именами в коде — это и есть спорные термины;
- аббревиатуры, принятые в проекте.

Улика термина — путь к файлу с определением или первому использованию. Слово, встреченное один раз в комментарии, кандидатом не является.

## Решения

Кандидат в ADR — выбор, у которого была альтернатива и есть последствия:

- крупные зависимости: фреймворк, база данных, брокер, ORM, тест-фреймворк — улика в манифесте пакетов;
- «почему» в комментариях и README: строки со словами «because», «потому что», «решили», «намеренно», `NOTE`, `HACK` с объяснением;
- переезды в истории: `git log --diff-filter=R --stat`, коммиты с «migrate», «replace», «switch», «переезд», «заменить»;
- структурные соглашения: слоистость, границы модулей, формат ошибок, версионирование API.

Не кандидат: умолчание инструмента, у которого альтернативы не рассматривали; выбор, чья причина неизвестна и не восстанавливается из истории — такой идёт в список с пометкой «мотивировка неизвестна», и владелец решает, писать ли ADR со статусом «записано задним числом, причина утрачена».

## Что не документировать как факт

- Сгенерированное: `dist/`, `build/`, `bin/`, `obj/`, `node_modules/`, миграции, собранные из моделей.
- Устаревшие README: утверждение, которое противоречит коду, записывается как расхождение, а не как факт.
- Зависимости для разработки — как production-стек.
